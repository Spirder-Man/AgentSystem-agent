## 一、什么是"生命周期"？先纠正一个直觉

"瞬时态"翻译自 **Transient**（瞬态的/短暂的）。DI 的生命周期回答三个问题：

> **这个对象什么时候被创建？谁跟我共享同一个对象？我什么时候被销毁？**

三个选项就像三种"存在方式"：

| 生命周期 | 创建时机 | 共享范围 | 一句话类比 | 项目实例 |
|---|---|---|---|---|
| **Transient 瞬时** | 每次请求解析时都 new 一个 | **谁也不共享**，人手一个全新对象 | 一次性筷子 | Controller（默认）、`LlmService` 的临时产物 |
| **Scoped 作用域** | 每个"作用域"（HTTP 请求）创建一个 | 同一次请求内共享，跨请求隔离 | 酒店房间：这个客人住这间，别的客人住别的间 | 常用在 DbContext（EF Core 惯例） |
| **Singleton 单例** | 进程启动时创建一次 | **全进程所有人共享同一个** | 公司唯一的公厕/公共停车场 | `SemaphoreSlim(2,2)`（L107）、`AppConfig`（L105）、`AgentDialog`（L127） |

注意关键区别：**Transient 和 Scoped 都会"每次请求新建"**，差别只在"共享范围"——Transient 连同一次请求内都不同享（每次 `GetService` 都 new），Scoped 在请求内共享。

## 二、为什么 Controller 天生是"瞬时态"？

ASP.NET Core 框架的激活机制（MVC `DefaultControllerActivator`）不把 Controller 当普通 DI 服务管理，而是：**每个 HTTP 请求到达时，框架 `Activator.CreateInstance` 反射 new 一个 Controller → 调用方法 → 请求结束，实例被 GC 回收**。

设计意图：Controller 是"无状态的消息处理器"——它只该读取请求、调用服务、返回响应。如果它内部存了状态（比如一个累加器字段），**每次请求从 0 开始**，这反而保证了请求间不串数据。

项目里没有显式注册 Controller 到容器（只有 `AddControllers()`），所以它们全部是这种"每请求新建"的瞬时态。

> - **同一次请求内共享，请求间隔离** → **Scoped**：DbContext（一个请求一个数据库连接）、用户会话内的上下文
> - **全进程共享，必须互斥/计数/累加** → **Singleton**：锁、信号量、计数器、配置、缓存（`AppConfig`/`SemaphoreSlim`/`ResponseCacheService` 都是单例，就是这个道理）

| 锁放进 Scoped | 锁只锁同一次请求 | 同上，跨请求失效 |
| **把请求级数据放进 Singleton**（反过来错） | 全局串数据 | 用户 A 的数据被用户 B 看到——比锁失效更危险 |

## 一、真互斥的代价：它"限制"了什么？

锁的本质是**用并发能力换数据安全**。真互斥生效后，代价立现：

| 代价 | 说明 | 项目里的样子 |
|---|---|---|
| **吞吐量封顶** | 并发数被压到锁容量上限，多出来的请求只能排队 | `_llmGate` 限 2 并发 → 第 3 个请求必须等，等不到就 503 |
| **延迟增加** | 每个请求多了一段"排队时间" | 用户体感：高峰期审核变慢 |
| **排队风暴** | 排队者超时后立刻重试，重试又排队，恶性循环 | 前端拿到 503 + `retryAfter:10` 就是为此设计——**强制客户端冷却**，防止重试风暴 |
| **瓶颈转移** | 锁本身成为热点：所有人挤同一把锁，锁的竞争开销可能反超业务 | 若锁粒度太大（把不需要互斥的代码也锁了），无关请求互相拖累 |

一句话：**真互斥 = 用"最多 2 个并行"换"绝不超过 2 个并行"**。对 CPU 推理这种硬资源（llama.cpp 单机推理），这个代价是必须付的——超并发不是"慢"而是"崩"。

## 二、没锁的后果：项目里有个现成的真实案例

项目里 `ChemicalRAG._incrementalGate`（增量闸机）就是**从"没锁"修到"有锁"**的活教材（Bug-038）：

```

  管理员 09:00:01 点增量更新 → 请求A 开始扫描
  管理员 09:00:02 又点一次   → 请求B 也进来，两个任务同时跑
  请求A: 对文件 X 执行 DELETE（删旧）
  请求B: 对文件 X 执行 DELETE（删旧）→ 删 0 行

  请求B 失败不记账 → 下轮又当"新增" → 又撞 → 死循环 🔁
```

没锁的典型后果清单：
- **竞态交错**：两个请求的"先删后插"交错执行，中间态互相踩踏（上面就是）
- **重复写/唯一约束爆炸**：INSERT 撞 UNIQUE（项目实锤）
- **半写状态**：一个任务删了旧数据，另一个任务没写完就失败，DB 处于"既没旧也没新"的中间态
- **资源超载**：锁失效 → 并发无上限 → CPU/显存被打爆（如果 `_llmGate` 失效，3 个 CPU 推理同时跑，llama.cpp 直接卡死，类似 Bug-040 的服务假死模式）

**修复后（有锁）**：第二个请求 `WaitAsync(0)` 一毫秒都等不到 → 立刻 409"已有任务运行中"→ 互斥铁证（07-30 远程实测 3 个并发 curl → 1×200 + 2×409）。

## 三、同种锁的六大坑（含你问的"饿死"）

### 坑 1：锁饿死（你提到的"锁资源耗尽"）⭐ 最危险

**饿死（Starvation）**：锁的"通行证"被持续占用或丢失，导致**永远有请求拿不到锁**。

死锁和饿死的区别一句话：
- **死锁** = 两个人互相等对方的钥匙，**谁都动不了**（僵局）
- **饿死** = 钥匙一直被别人拿走，**别人一直能进，你永远等不到**（单方挨饿）

信号量场景下饿死有两种成因：

**成因 A：Release 丢失（最经典）**——拿了证不还证，计数只减不增，最终耗尽归零：

```csharp
// ❌ 错误：Release 不在 finally 里，中途 return/抛异常就漏还
if (!await _llmGate.WaitAsync(TimeSpan.FromSeconds(5))) return 503;
try {
    if (某些条件) return Ok("提前返回");   // ← 这里直接 return，下面的 Release 永远不执行
    await DoLlmInference();
} catch { return 500; }                     // ← 异常也一样漏还
_llmGate.Release();                         // ❌ 永远到不了
```

```csharp
// ✅ 正确：finally 保证"无论成败必还证"——项目现状 L134-210
try { ...业务... } finally { _llmGate.Release(); }
```

**推演饿死后果**：假设 100 个请求里有 3 个走了提前 return 的路径 → 信号量计数从 2 永久变成 -1（实际上 WaitAsync 的等待队列会越来越长）→ 后续所有请求全部拿不到锁 → 503 海啸 → **服务"假死"**（CPU 空闲但全部请求被拒）。这就是用户说"锁每次耗尽锁资源"的准确形态。

**成因 B：持锁时间失控**——持锁者业务本身跑 10 分钟，排队者 5 秒超时全部 503。不是锁坏了，是"锁的容量(2) × 单次时长"算不过业务流量。

### 坑 2：死锁（互相等钥匙）

两个任务各持一把锁、互相等对方的那把：

```
线程1: 持有 锁A → 等待 锁B
线程2: 持有 锁B → 等待 锁A     → 永远卡死
```

**项目对照**：`Program.cs#L116` 有 `Lazy<T>` 破解循环依赖的注释——这类"互相引用"一旦发生在锁上就是死锁。**规避规则**：多把锁时必须**全局固定获取顺序**（比如永远先拿 A 再拿 B），或者给 `WaitAsync` 全部加超时（本项目统一 5 秒超时，就是防死锁的保险丝——等不到就放弃，不让僵局无限持续）。

### 坑 3：SemaphoreSlim 不可重入（自锁）

`Monitor`/`lock` 可重入（同一线程重复进入没问题），但 **`SemaphoreSlim` 不可重入**——同一个逻辑里第二次 `WaitAsync` 同一个信号量，会把自己堵死：

```csharp
await _llmGate.WaitAsync();   // 计数 2→1 ✅
await _llmGate.WaitAsync();   // 计数 1→0 ✅  （还能拿到）
await _llmGate.WaitAsync();   // 计数 0 → ❌ 自己等自己 → 死锁/超时
```

场景：A 方法拿了锁，B 方法（被 A 调用）又拿同一把锁。**规避**：一个信号量只在一个层级的入口拿一次；需要重入语义就用 `AsyncLock` 包装或 `lock`。

### 坑 4：异步代码里用阻塞等待

```csharp
// ❌ 在 async 方法里同步阻塞等异步锁（配合 SynchronizationContext 会死锁）
_llmGate.Wait();                    // 或 .Result/.Wait()
// ✅ 全程 await
await _llmGate.WaitAsync(TimeSpan.FromSeconds(5));
```

本项目全用 `await WaitAsync`，没有踩这个坑——但这是异步锁最常见的隐蔽死锁源。

### 坑 5：跨进程/多实例部署 → "N 份锁"问题复现

`SemaphoreSlim` 是**进程内**的锁。如果将来 docker-compose 起了 **2 个 API 副本**，每个进程各有各的 `_llmGate`：

```
进程1 的锁 Ω₁（2 张证）  进程2 的锁 Ω₂（2 张证）
→ 全系统实际并发 = 4，2 并发限制又失效了！
```

**规避**：多实例部署时换**分布式锁**（Redis SETNX / PostgreSQL advisory lock）。单实例部署（项目现状：远程一台 AutoDL）则无此问题——这正是"进程内锁够用"的边界条件。

### 坑 6：锁粒度与重试风暴

- **粒度太大**：把不需要互斥的读操作也锁了 → 无关请求排队 → 吞吐雪崩
- **重试风暴**：503 后客户端**立刻**重试（不是等 retryAfter）→ 排队者越来越多 → 锁队列恶性膨胀。项目 `retryAfter = 10` 字段就是给前端"冷却指令"。

