# 幽灵依赖（Ghost Dependency）现象归纳与案例库

> **目的**：定义并归纳「配置上存在、物理上从未存在」的幽灵依赖现象，建立识别指纹、检测方法与预防清单，并以本项目真实案例做示例沉淀。
> **文档版本**：v1.0 | **创建日期**：2026-07-28 | **关联**：[Bug知识库.md](../project/Bug知识库.md) Bug-034 / 弱点 W23
> **命名说明**：本文档案例编号采用 `GD-XXX`（Ghost Dependency），与 Bug 知识库的 `Bug-XXX` 独立编号、互相引用。

---

## 一、现象定义

**幽灵依赖**：系统的配置、代码或架构图中**声明**了某个依赖（服务实例、端口、模型、数据表、构建目标），但该依赖在部署面上**从未被兑现**——没有部署脚本创建它、没有启动检查探测它、没有文档要求运维它。它只存在于声明层，是一个"物理上从未存在"的幽灵。

**一句话判据**：

> 配置声明了依赖 + 部署清单查无此物 + 系统却"看起来正常运行" = 幽灵依赖。

### 与相近概念的区分

| 概念 | 声明层 | 物理层 | 典型表现 |
|---|---|---|---|
| **依赖故障**（如 W5 Embedding 不稳定） | 有 | **曾经有，现在挂了** | 有报错日志、有历史成功记录 |
| **降级缺失**（W19，Bug-029/030） | 有 | 有，但失败时无兜底 | 依赖失败 → 应用崩溃或静默失效 |
| **幽灵依赖**（W23，本文档） | 有 | **从未有过** | 零报错、零成功记录、功能"看起来完成了" |
| **配置化石**（幽灵依赖的伴生现象） | 有（过时格式） | 无 | 配置值残留上一代技术栈的语法痕迹 |

关键区别：幽灵依赖的**全生命周期成功率为 0%，但监控面成功率为 100%**——这是它与所有其他依赖类问题的本质差异。

## 二、形成机制（生命周期四阶段）

```
阶段①声明        阶段②迁移断层           阶段③契约缺失              阶段④静音存活
配置/代码中    →  技术栈演进时只改了   →  部署脚本/启动检查/文档  →  错误处理把失败字符串化，
写入依赖项        声明层的一部分          三处均未收录该依赖          调用方把字符串当成功
（好意的设计）    （留下化石痕迹）        （口头协议无人兑现）        （假成功闭环，无人察觉）
```

各阶段成因归纳：

1. **声明阶段**：架构设计正确且有充分理据（如多实例端口隔离），依赖声明本身不是错误；
2. **迁移断层**：技术栈迁移（如 Ollama → llama.cpp）时，配置只做了"最小改动"（改端点端口），依赖项的部署方式没有随迁移重新落实，且残留旧栈化石（如 `:latest` 标签语法）；
3. **契约缺失**：依赖的"部署侧承诺"没有进入任何强制载体——`start_services.sh` 无它、启动健康检查无它、部署文档无它。声明变成**只存在于配置文件里的口头协议**；
4. **静音存活**：错误处理层把连接失败转成错误文案字符串、API 层对任何非空字符串返回 200 + INF"完成"日志——三层静音叠加，缺陷获得无限存活期。

> **核心洞察**：幽灵依赖能长期存活的必要条件不是"没人部署它"，而是"它的缺失被伪装成了成功"。部署缺口（阶段③）决定它存在，假成功（阶段④）决定它**不可见**。二者叠加才成灾。

## 三、识别指纹（五个信号）

| # | 指纹 | 检查方式 | 本项目案例中的表现 |
|:---:|---|---|---|
| F1 | **耗时低于物理下限** | 对比日志耗时与该操作的物理最小耗时 | 视觉推理物理下限 ~3s，日志显示 81ms（恰为 TCP 拒连的快速失败耗时） |
| F2 | **零错误 + 零成功证据** | 日志中该模块 ERR/WRN = 0，但也找不到任何真实产出（如推理内容、行数增长） | 6541 行日志 ERR=0，多模态"成功"结果实为错误文案 |
| F3 | **配置-部署对账不平** | 配置声明的每个端点/实例，在部署脚本和启动检查中逐一核对 | `MultimodalEndpoint: 8083` 在 `start_services.sh`、启动检查、部署文档中零记录 |
| F4 | **配置化石** | 配置值残留上一代技术栈语法 | `qwen-vl:latest` 是 Ollama 标签语法，llama.cpp 不消费该字段 |
| F5 | **构造/初始化永不失败** | 依赖服务的构造函数只读配置不做连通性校验，惰性连接 | `new MultimodalService()` 永远成功，缺失要到首次请求才暴露（且被静音） |

**排障口诀**：先看 F1（耗时指纹）快速起疑，再用 F3（配置-部署对账）实锤。

## 四、检测方法（三层防线）

### 4.1 静态防线：配置-部署对账（开发期/评审期）

对配置中每一个 `Endpoint` / 端口 / 外部实例声明，逐项回答三个问题：

- [ ] 谁负责启动它？（哪个脚本 / 哪份部署文档的哪一节）
- [ ] 谁负责探活它？（启动检查 / 健康检查端点）
- [ ] 它挂了会怎样？（降级路径是显式失败还是静默伪装）

三问中任何一问答不出 → 该依赖是幽灵候选。

### 4.2 运行时防线：启动探活 + 显式降级

- 启动序列对所有声明的实例端点做一次连通性探测，不可达时打 **WRN 级启动日志**（"8083 视觉实例不可达，多模态功能将返回 503"），让缺失在启动时刻即可见；
- 依赖不可达时 API 必须返回 5xx + 结构化错误分类，**禁止**把错误文案塞进成功响应的语义槽位（降级的正确形态是让调用方知道降级发生了）。

### 4.3 监控防线：时效性指纹告警

- 为每类重操作建立**物理下限阈值**（如：视觉推理 < 1000ms 即可疑、LLM 长链推理 < 500ms 即可疑）；
- 告警规则不只盯 ERR 级日志——**INF 日志中的异常耗时同样是告警信号**（本案例中假成功全部以 INF 级"完成"存在，纯级别告警全盲）。

## 五、预防清单（新增外部依赖时必查）

- [ ] 配置声明与部署脚本**同一个 PR 落地**（声明与兑现原子化）
- [ ] 启动检查中加入该依赖的探活项（不可达 → WRN 启动日志）
- [ ] 服务层失败必须结构化（Success 标志 + 错误分类），禁止裸字符串吞异常
- [ ] API 层按错误分类映射 5xx 状态码，失败打 WRN 日志
- [ ] 至少一个"依赖不存在时必须判定为失败"的反假成功回归测试
- [ ] 技术栈迁移时，用 F4 化石扫描全量配置（grep 旧栈特征语法，如 Ollama 的 `:latest`）

### 案例 GD-001：多模态视觉实例 8083 幽灵依赖（假成功三层静音）

> **关联**：Bug 知识库 [Bug-034](../project/Bug知识库.md#bug-034) | 完整多维分析报告见当次对话交付
> **溯源**：日志 `api-20260728_104206.log` L5731；配置 `Agent1/appsettings.json` L29-L30；代码 `MultimodalService.cs` / `MultimodalController.cs`

| 要素 | 内容 |
|---|---|
| **声明层** | `appsettings.json`：`MultimodalModelId: qwen-vl:latest`、`MultimodalEndpoint: http://localhost:8083/v1`；架构设计为 llama.cpp 多实例分端口（8080 主 LLM / 8081 Embedding / 8082 Reranker / 8083 视觉） |
| **物理层** | 8083 llama-server（`--mmproj` 视觉实例）**从未部署**：`start_services.sh` 无、启动检查无、部署文档无 |
| **静音链** | ① Service 层 4 个 catch 分支全部 `return "错误: ..."` 字符串（异常类型湮灭）→ ② Controller 对任何非空字符串返回 HTTP 200 → ③ 日志打 INF"多模态分析完成"（级别与事实相反） |
| **暴露指纹** | 日志 L5731 `多模态分析完成: 类型=hazard-label, 耗时=81ms` — 81ms 远低于视觉推理物理下限 3s，恰为连接被拒的快速失败耗时（指纹 F1）；全日志该模块 ERR=0、WRN=0（指纹 F2） |
| **化石证据** | `qwen-vl:latest` 为 Ollama 标签语法，项目推理栈已整体迁移 llama.cpp——配置从 Ollama 迁移时只改了端口没落实部署（指纹 F4） |
| **爆炸半径** | 多模态 API 三种分析类型全部假成功（用户把错误文案当"分析结果"，误以为模型能力差）；Agent 工具链 `LookupHazardLabel` 可能把错误文案当图片内容继续推理产生二次幻觉；审计成功率统计被污染（日志面 100%，真实 0%）。**隔离良好面**：RAG / 知识图谱 / 主 LLM 零影响——多实例端口隔离架构兑现了故障隔离价值 |
| **修复** | A（已完成）：`MultimodalResult` 结构化结果（Success + 六类 ErrorCategory）、`HttpRequestException` 专属分支内嵌 8083 启动指引、Controller 按分类映射 503/502/500 + WRN 日志、3 个反假成功回归测试；B（待远程实例开机）：部署 Qwen2.5-VL GGUF + mmproj 到 8083，并清理 `qwen-vl:latest` 化石配置 |
| **验证** | `MultimodalServiceTests` 6/6 通过，其中 `AnalyzeImageDetailed_ServiceUnreachable_FailsWithServiceUnavailable` 直接锁定"本地无 8083 时必须判定失败"的反假成功行为 |

**本案例思维链摘要**（完整版见 Bug-034）：

```
现象确认: INF"完成"但 81ms << 物理下限 3s → 判定"完成"不可信
L1 追问: 为什么 81ms 就完成？ → Service 层 4 个 catch 全部字符串化吞异常
L2 追问: 为什么连接被拒？   → 配置-部署对账：8083 在所有部署载体中零记录 + Ollama 化石命名
L3 追问: 为什么伪装成 INF？ → Controller 无成败判定，任何字符串一律 200 + LogInformation
方案分支: 只修代码(治不可见) / 只部署(治不可用) / A+B 全套 ✅
```

## 七、归纳：幽灵依赖的通用教训

1. **声明与兑现必须原子化**：配置里每写一个端点，同一次变更里必须有部署脚本/启动检查/文档三者之一承接，否则就是在制造口头协议；
2. **降级不等于伪装**：依赖缺失时的正确降级是"显式失败 + 指引"（503 + 启动说明），把错误塞进成功语义槽位是本现象最核心的边界违约；
3. **INF 日志也要能报警**：基于日志级别的告警对假成功全盲，必须补充时效性指纹（耗时物理下限）维度；
4. **技术栈迁移要做化石扫描**：迁移收尾时 grep 全量配置中的旧栈特征语法，化石是幽灵依赖最廉价的探测器；
5. **绿色信号需要定期审计**：长期 100% 成功率且零流量证据的模块，比报错的模块更值得怀疑。
