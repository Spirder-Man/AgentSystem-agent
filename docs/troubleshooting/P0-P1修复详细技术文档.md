## 一、修复背景

### 1.1 项目定位

本项目是面向**化工园区危化品合规审核**的企业级 AI Agent 系统，基于 .NET 8 + Semantic Kernel + Ollama 构建，核心能力包括：

- RAG 检索增强生成（BM25 + pgvector 混合检索）
- CoT 思维链推理（流式/标准双模式）
- ReAct 交互式推理（Thought → Action → Observation 循环）
- Reflection 自我反思纠错
- 化工合规自查（国标/园区规则/历史案例三级知识库）

### 1.2 核心问题：功能错位

项目最初的模板代码来自**工业制造场景**（机床主轴温度监控），后来转向化工合规领域，但大量代码**残留了工业工具的硬编码引用**。典型症状：

| 场景 | 用户提问 | 系统实际调用 | 问题 |
|------|----------|-------------|------|
| 储存合规 | "氧化剂和易燃液体能一起存吗" | `GetSpindleTemperature()` | 返回随机主轴温度 190-220℃，与化工无关 |
| 危险分类 | "苯属于什么危险类别" | `GetTemperatureThreshold()` | 返回"主轴安全温度阈值 ≤ 180℃" |
| 安全距离 | "储罐之间的安全距离是多少" | `GetSpindleTemperature()` | 返回机床主轴温度，牛头不对马嘴 |

**根本原因**：RAG 模块的 Prompt 已经切换为化工合规专家角色，但底层工具调用链路仍然绑定 `IndustrialTools`（机床温度/主轴阈值），形成了"化工问题 + 工业工具"的功能错位。

---

### 1.3 根本原因深度追溯

> ▸ **v2.0 深度分析**

#### 1.3.1 为什么会犯这个错误？——四层因果链

这个"功能错位"不是单一疏忽造成的，而是一条四层因果链的必然结果：

```
【表层症状】用户问"苯属于什么危险类别" → 系统返回"主轴温度 190℃"
        ↑
【第1层：代码残留】IndustrialTools.cs 未被删除，多处硬编码引用
        ↑
【第2层：领域切换】项目从"工业制造"模板转向"化工合规"时，
                 只改了 Prompt 文案，未穿透到底层工具调用链路
        ↑
【第3层：架构缺陷】工具注册散布在 RAG/LlmService/AgentDialog/
                 RunReflectionStreamTools 四个文件中，无统一入口
        ↑
【第4层：模板污染】项目初始使用工业场景脚手架模板，
                 领域切换时未进行全量"领域边界扫描"
```

**第4层（模板污染）详解**：

项目最早基于一个"工业设备诊断 Agent"模板搭建，该模板包含：
- `IndustrialTools.cs`：`GetSpindleTemperature()` / `GetTemperatureThreshold()`
- `SmartDialogSystem.cs`：硬编码工业 Prompt（"工业设备诊断专家"）
- `RAG.cs`：`LoadIndustrialKnowledgeBase()` 读取主轴故障案例.txt

当项目转向化工合规领域时，开发者做了以下操作：
1. 修改了 `SmartDialogSystem.cs` 中的 Prompt 文案 ✅
2. 创建了新的化工知识库目录 ✅
3. **但遗漏了底层工具调用链路的同步切换** ❌

遗漏的原因在于：**工具调用链路是跨文件的隐式依赖**。开发者修改 Prompt 后，LLM 开始按化工领域思考，但 CallTool 方法中的 switch 语句仍然映射到工业工具——这个映射关系被埋藏在字符串匹配中，编译器无法检测。

**第3层（架构缺陷）详解**：

修复前，工具注册和调用散布在至少 4 个文件中：

| 文件 | 职责 | 工业残留 |
|------|------|----------|
| `LlmService.cs` | SK 插件注册 | `AddFromType<IndustrialTools>()` |
| `AgentDialog.cs` | Prompt + CallTool | 硬编码工业工具名 switch |
| `RAG.cs` | ReAct 循环 + CallTool | 硬编码工业工具名 switch |
| `RunReflectionStreamTools.cs` | Reflection 循环 + CallTool | 硬编码工业工具名 switch |

这形成了**"分布式耦合"**——同一个工具集 `IndustrialTools` 被 4 个文件分散引用，领域切换时需要逐一修改，遗漏任何一处都会造成功能错位。

#### 1.3.2 架构坏味道 → Bug 的必然性

| 架构坏味道 | 表现形式 | 导致的 Bug |
|-----------|---------|-----------|
| **分布式耦合** | 工具注册散布在 4 个文件 | 领域切换时遗漏 → 功能错位 |
| **字符串契约** | 工具名通过字符串 switch 匹配，无编译时检查 | LLM 输出的工具名与 switch case 不匹配 → 调用失败 |
| **隐式依赖** | RAG 模块依赖 IndustrialTools 但未通过接口声明 | 删除 IndustrialTools 时编译错误迫使保留残留代码 |
| **硬编码配置** | 工具触发关键词硬编码在 ToolService 中 | 新增化工工具需要修改 ToolService 源码 → 违反开闭原则 |

#### 1.3.3 教训总结

> **核心教训**：领域切换（domain pivot）时，必须执行"全量领域边界扫描"——追踪所有与旧领域相关的字符串常量、类名、方法名、Prompt 文案、文件路径，确保无一遗漏。编译器无法检测语义层面的领域错位，只能靠人工审查。

### 2.1.1 多方案对比与决策分析

> ▸ **v2.0 深度分析**

面对"工业工具→化工合规工具"替换需求，存在三种可行方案。以下是系统性对比：

| 维度 | 方案A：全量替换 | 方案B：适配层包装 | 方案C：配置驱动映射 |
|------|:---:|:---:|:---:|
| **策略描述** | 新建 ChemicalComplianceTools，删除 IndustrialTools，所有引用全量替换 | 保留 IndustrialTools 接口，创建 ChemicalAdapter 适配层，将化工问题翻译为工业工具调用 | 创建配置文件定义工具映射，运行时动态加载 |
| **代码侵入性** | 🔴 高 — 6 个文件 33+ 处修改 | 🟡 中 — 新增适配层，少量引用修改 | 🟢 低 — 仅新增配置类 |
| **编译安全性** | 🟢 高 — 编译时检测所有遗漏 | 🔴 低 — 适配层内部仍可能调用错误工具 | 🟡 中 — 部分运行时绑定 |
| **语义正确性** | 🟢 高 — 每个工具方法语义明确 | 🔴 低 — 适配层需要"翻译"工业工具语义到化工领域，极易出错 | 🟡 中 — 依赖配置准确性 |
| **扩展性** | 🟢 高 — 新增化工工具只需新增方法 | 🟡 中 — 需同时维护适配层 | 🟢 最高 — 新增工具仅需配置 |
| **可测试性** | 🟢 高 — 每个工具方法可独立测试 | 🔴 低 — 适配逻辑复杂，测试困难 | 🟡 中 — 配置驱动测试 |
| **工作量** | 3-4 小时 | 5-6 小时 | 2-3 小时 |
| **风险** | 修改文件多，合并冲突风险 | 适配层设计不当导致语义错位 | 运行时错误难以提前发现 |

**最终决策：选择方案A（全量替换），附带方案C的部分思路（配置驱动关键词触发）**

决策理由：
1. **语义正确性优先**：化工合规工具的输入输出语义与工业工具完全不同（如 `CheckHazardCategory` vs `GetSpindleTemperature`），适配层"翻译"方案本质上是将错误语义包装成正确语义，埋下更深层的 bug 隐患
2. **编译安全性不可妥协**：方案A 的"高侵入性"反而是优势——编译器会检测到所有遗漏的引用，强制开发者逐一处理，确保零遗漏
3. **融合方案C 的优势**：在 ToolService 层面引入配置驱动的关键词触发机制（见 2.4），既保留了方案A 的语义正确性，又获得了方案C 的扩展性

**方案B 被否决的关键原因**：

```
适配层的语义翻译困境示例：

用户问："苯属于什么危险类别"
→ 适配层翻译：调用 GetSpindleTemperature()？❌ 无可翻译
→ 适配层翻译：调用 GetTemperatureThreshold()？❌ 无可翻译
→ 适配层翻译：调用 WebSearch("苯 危险类别")？⚠️ 降级为网络搜索，丢失了化工工具的专业性

结论：工业工具的语义空间与化工合规工具完全不重叠，适配层"翻译"不可行。
```

### 2.2 新增文件：ChemicalComplianceTools.cs

#### 设计思路

`ChemicalComplianceTools` 是面向化工合规场景的全新工具集，替代工业制造场景的 `IndustrialTools`。核心设计原则：

1. **领域专一**：每个工具对应一项化工合规审查能力
2. **法规对齐**：工具返回结果直接引用具体国标编号
3. **Semantic Kernel 兼容**：使用 `[KernelFunction]` 属性标注，支持 SK 自动发现和注入
4. **知识库兜底**：无法精确匹配时，引导用户查阅 `knowledgebase/` 目录下的标准全文

#### 完整代码实现

```csharp

    {

            ["易燃气体"] = "GB 30000.3-2013",

            ["氧化性固体"] = "GB 30000.15-2013",
            ["急性毒性"] = "GB 30000.18-2013",
            ["致癌性"] = "GB 30000.23-2013",
```

#### 五个工具方法详解

**工具 1：CheckHazardCategory(string substanceName)**

- **功能**：查询危化品属于哪个危险类别，返回对应的 GB 30000 系列标准号
- **参数演变**：`substanceName` — 从用户自然语言中提取的危化品名称（由后续 `ExtractSubstance()` 预处理）
- **匹配逻辑**：双向模糊匹配（`substanceName.Contains(kvp.Key) || kvp.Key.Contains(substanceName)`），兼顾"苯"匹配"易燃液体"的场景
- **兜底策略**：未匹配时引导查阅 `knowledgebase/国标/` 目录下的完整标准文件

```
修复前（IndustrialTools.GetSpindleTemperature）:
  → 返回随机主轴温度值（190-220℃），化工问题完全无法使用

修复后（ChemicalComplianceTools.CheckHazardCategory）:
  → 输入"苯" → 输出"属于「易燃液体」类别，适用标准：GB 30000.7-2013"
```

**工具 2：CheckStorageCompatibility(string substanceA, string substanceB)**

- **功能**：检查两种危化品是否可以同库储存，依据 GB15603-1995 第4.2.2条
- **参数演变**：两个危化品名称（由 `ExtractTwoSubstances()` 从"氧化剂和易燃液体能一起存吗"中拆分提取）
- **判断逻辑**：
  1. 遍历 `StorageIncompatibilities` 字典
  2. 检查 `substanceA` 是否匹配某禁忌类别、`substanceB` 是否在该类别的禁忌列表中
  3. 匹配成功 → 返回 `⚠️ 禁用` + GB15603 条款引用
  4. 匹配失败 → 返回 `✅ 未发现直接冲突` + 建议核实

```
修复前（IndustrialTools.GetTemperatureThreshold）:
  → 返回"主轴安全温度阈值：≤ 180℃"

修复后（ChemicalComplianceTools.CheckStorageCompatibility）:
  → 输入("氧化剂", "易燃液体") → 输出"⚠️ 禁用：氧化剂类不可与之同库贮存。依据：GB15603-1995 第4.2.2条"
```

**工具 3：GetSafetyDistance(string facilityType)**

- **功能**：查询设施间的安全间距要求
- **参数演变**：设施类型字符串（由 `ExtractFacilityType()` 从"储罐之间的安全距离是多少"中推断为"储罐-储罐"）
- **两级匹配**：
  1. 精确匹配 `SafetyDistances.TryGetValue(key, out distance)`
  2. 模糊匹配 `SafetyDistances.Keys.Where(k => k.Contains(key) || key.Contains(k))`
- **兜底**：引导查阅 GB50160 和 GB50016 全文

**工具 4-5：GetCurrentTime() / Calculate(string expression)**

- 保留自 `IndustrialTools`，属于通用工具，化工场景同样适用
- `Calculate` 使用 `System.Data.DataTable().Compute()` 安全计算数学表达式

### 2.4 重写文件：ToolService.cs

#### 核心变更：关键词匹配从硬编码改为配置驱动

```csharp
// ── 修复前（硬编码工业关键词）──
public async Task<ToolPlan> AnalyzeAndPlanToolsAsync(string userInput, string history)
{
    if (userInput.ToLower().Contains("温度") || userInput.ToLower().Contains("temperature"))
    {
        plan.ToolNames.Add("GetSpindleTemperature");
        plan.ToolNames.Add("GetTemperatureThreshold");
    }
    // ... 更多硬编码判断
}

// ── 修复后（配置驱动匹配）──
public async Task<ToolPlan> AnalyzeAndPlanToolsAsync(string userInput, string history)
{
    var lowerInput = userInput.ToLower();
    foreach (var tool in _toolDefinitions)
    {
        // 遍历 ToolDefinition.KeywordTriggers，任一词匹配即触发
        if (tool.KeywordTriggers.Any(kw => lowerInput.Contains(kw.ToLower())))
        {
            plan.NeedsTools = true;
            plan.ToolNames.Add(tool.Name);
            return plan;  // 首次匹配即返回
        }
    }
    plan.NeedsTools = false;
    return plan;
}
```

## 四、Bug 修复

### 4.1 修复 1：ParseToolCalls 误匹配问题（🔴 严重）

#### 问题场景

用户提问："储罐之间的安全距离是多少"

LLM 在 Step1 Thought 中分析道：
```
CheckHazardCategory：用于查询危化品危险类别...（不适用）
CheckStorageCompatibility：检查两种危化品是否可以同库储存...（不适用）
GetSafetyDistance：查询设施间安全间距要求...这个正好适用
因此，只需要调用 GetSafetyDistance 这个工具。
```

旧版 `ParseToolCalls` 使用 **全文 Contains 匹配**：
```csharp
// ── 修复前：全文本扫描 ──
foreach (var toolName in toolNames)
{
    if (modelOutput.Contains(toolName))  // 危险！LLM 思考列举了所有工具名
    {
        tools.Add(toolName);
    }
}
// 结果：CheckHazardCategory, CheckStorageCompatibility, GetSafetyDistance, GetCurrentTime, Calculate
//       全部 5 个工具被误匹配！
```

**后果链**：
```
5 个工具全被调用 → 参数全是完整问句 → CheckHazardCategory("储罐之间的安全距离是多少") 无法匹配
→ GetSafetyDistance("储罐之间的安全距离是多少") 精确匹配失败
→ 最终 LLM 因缺乏真实数据而编造答案
```

#### 修复方案：标记行限制匹配

```csharp
// ── 修复后：只在 需要调用的工具： 标记行中匹配 ──
string marker = "需要调用的工具：";
int markerIndex = modelOutput.IndexOf(marker, StringComparison.OrdinalIgnoreCase);

if (markerIndex >= 0)
{
    // 提取标记行内容（只取第一行）
    string afterMarker = modelOutput.Substring(markerIndex + marker.Length);
    int newlineIndex = afterMarker.IndexOf('\n');
    string toolLine = newlineIndex >= 0 ? afterMarker.Substring(0, newlineIndex) : afterMarker;
    
    // 检查是否明确为"无"
    string cleanLine = toolLine.Trim().Replace("。", "").Replace(".", "").Trim();
    if (cleanLine == "无" || string.IsNullOrEmpty(cleanLine))
        return new string[0];
    
    // 只在标记行内匹配工具名
    foreach (var toolName in toolNames)
        if (toolLine.Contains(toolName, StringComparison.OrdinalIgnoreCase))
            tools.Add(toolName);
}
else
{
    // 没找到标记行 → 保守返回空，不让无关工具被误调用
    return new string[0];
}
```

**同时强化 Thought Prompt 格式约束**，在 prompt 末尾增加：
```
请分析是否需要调用工具。注意：你的思考可以自由发挥，但最后一行必须是以下格式（二选一）：
需要调用的工具：工具名1,工具名2
需要调用的工具：无
```

这样 LLM 会在输出末尾产生明确的标记行，ParseToolCalls 可以精确捕获。

**1. ExtractSubstance(string userInput)** — 提取单个危化品名称

```csharp
private string ExtractSubstance(string userInput)
{
    return userInput
        .Replace("属于什么危险类别", "").Replace("是什么类别", "")
        .Replace("的危化品", "").Replace("是什么", "")
        .Replace("属于什么", "").Replace("什么", "")
        .Replace("是多少", "").Replace("能不能", "")
        .Replace("吗", "").Replace("？", "").Replace("?", "").Trim();
}
// "苯属于什么危险类别" → "苯"
// "氧化剂和易燃液体能一起存吗" → "氧化剂和易燃液体能一起存"
```

**2. ExtractTwoSubstances(string userInput)** — 提取两个危化品名称

```csharp
private (string a, string b) ExtractTwoSubstances(string userInput)
{
    var separators = new[] { "和", "与", "跟", "、" };
    foreach (var sep in separators)
    {
        if (userInput.Contains(sep))
        {
            var parts = userInput.Split(new[] { sep }, 2, StringSplitOptions.RemoveEmptyEntries);
            if (parts.Length >= 2)
            {
                string a = CleanSubstance(parts[0]);  // "氧化剂"
                string b = CleanSubstance(parts[1]);  // "易燃液体能一起存吗" → "易燃液体"
                if (!string.IsNullOrWhiteSpace(a) && !string.IsNullOrWhiteSpace(b))
                    return (a, b);
            }
        }
    }
    return (ExtractSubstance(userInput), "");  // 兜底
}
```

**3. CleanSubstance(string text)** — 清理物质名中的问句残留

```csharp
private string CleanSubstance(string text)
{
    return text.Replace("能一起存", "").Replace("可以一起", "").Replace("能不能", "")
               .Replace("可以", "").Replace("吗", "").Replace("？", "").Replace("?", "")
               .Replace("怎么", "").Replace("如何", "").Trim();
}
```

**4. ExtractFacilityType(string userInput)** — 推断设施类型

```csharp
private string ExtractFacilityType(string userInput)
{
    if (userInput.Contains("液化烃")) return "液化烃储罐-储罐";
    if (userInput.Contains("仓库") && userInput.Contains("明火")) return "甲类仓库-明火点";
    if (userInput.Contains("仓库") && userInput.Contains("建筑")) return "甲类仓库-建筑";
    if (userInput.Contains("储罐") && userInput.Contains("建筑")) return "储罐-建筑";
    if (userInput.Contains("储罐") && userInput.Contains("消防")) return "储罐-消防通道";
    if (userInput.Contains("储罐") && userInput.Contains("边界")) return "储罐-厂区边界";
    if (userInput.Contains("储罐")) return "储罐-储罐";  // 默认
    return userInput;  // 兜底
}
```

**5. CallStorageCheck(ChemicalComplianceTools, string)** — 包装方法

```csharp
// switch 表达式不支持内联变量声明 (var a,b = ...)，故抽离为独立方法
private string CallStorageCheck(ChemicalComplianceTools tools, string userInput)
{
    var (a, b) = ExtractTwoSubstances(userInput);
    return tools.CheckStorageCompatibility(a, b);
}
```

### 4.3 修复 3：校验 Prompt 格式约束（🟡 中等）

#### 问题场景

Step5 校验阶段，LLM 收到的 prompt 包含 `{initialConclusion}`（初步回答的全部内容），但没有明确的格式约束。LLM 倾向于**重新复述一遍初步回答**，而非执行校验。

```
实际表现：
  → LLM输出包含"好，我现在要解决用户的问题..."开头的完整分析
  → 校验逻辑被稀释，失去了纠错意义
  → 产生大量冗余 token，增加了后续 Step6 的上下文负担
```

#### 修复方案：三重格式约束

```csharp
string validatePrompt = $@"【任务】校验下面【需要校验的回答】是否基于真实资料，禁止复述或重新分析！

重要：请严格区分三类信息：
1. 用户的假设问题（用户说的）
2. 真实知识库资料（系统提供的）
3. 真实工具数据（系统实际调用工具返回的）

...（检查要点）...

输出要求（严格遵守）：
- 不要复述初步回答的内容        ← 约束1：禁用自我复制
- 不要重新分析问题              ← 约束2：禁用二次推理
- 只输出一行：通过/不通过 + 一句简短原因  ← 约束3：强制单行输出
- 示例：通过，所有数据均来自工具调用结果
- 示例：不通过，回答中引用了知识库中不存在的温度数值";
```

**三个约束的作用机制**：

| 约束 | 解决的问题 | 实现原理 |
|------|-----------|----------|
| "不要复述初步回答的内容" | LLM 自我复制（输出 = 输入） | 通过显式否定指令打断复制倾向 |
| "不要重新分析问题" | LLM 把校验当成了第二轮推理 | 限定角色为"校验员"而非"分析师" |
| "只输出一行 + 示例" | LLM 产生冗长的解释性输出 | 格式示例是 LLM 最有效的约束方式 |

### 5.5 业务逻辑层面权衡

> ▸ **v2.0 深度分析**

#### 5.5.1 硬编码字典 vs 数据库动态加载

`ChemicalComplianceTools` 中的三个核心数据字典（`HazardCategories`/`StorageIncompatibilities`/`SafetyDistances`）目前采用硬编码方式：

| 维度 | 硬编码字典（当前方案） | 数据库动态加载（远期方案） |
|------|:---:|:---:|
| **数据新鲜度** | 🔴 低 — 法规更新需重新编译部署 | 🟢 高 — 数据库 UPDATE 即时生效 |
| **查询性能** | 🟢 极高 — 内存 Dictionary O(1) | 🟡 中 — 需数据库查询 + 缓存层 |
| **部署复杂度** | 🟢 极低 — 无外部依赖 | 🔴 高 — 依赖 PostgreSQL 可用 |
| **数据量上限** | 🟢 适合当前 ~30 条规则 | 🟢 可扩展至百万级 |
| **审计追溯** | 🔴 无 — 修改历史不可见 | 🟢 有 — 数据库可记录变更历史 |
| **多环境一致性** | 🔴 低 — 各环境需独立编译 | 🟢 高 — 数据与代码分离 |

**当前权衡**：选择硬编码方案，因为：
1. 法规数据相对稳定（GB 国标修订周期 5-10 年）
2. 数据量极小（~30 条规则），性能最优
3. 避免引入数据库依赖到工具层（工具方法应是"纯函数"）
4. 降低部署复杂度（无需数据库迁移脚本）

**演进路径**：当数据量超过 100 条或法规更新频率超过每月 1 次时，迁移到数据库方案。

#### 5.5.2 规则匹配参数提取 vs AI NER 参数提取

| 维度 | 规则匹配（当前方案） | AI NER（远期方案） |
|------|:---:|:---:|
| **准确率** | 🟡 ~80%（简单问句高，复杂问句低） | 🟢 ~95%（LLM 语义理解） |
| **延迟** | 🟢 <1ms | 🔴 ~200ms（额外 LLM 调用） |
| **成本** | 🟢 零 | 🔴 每次查询额外 token 消耗 |
| **可解释性** | 🟢 规则透明可调试 | 🔴 LLM NER 黑盒 |
| **可维护性** | 🔴 需手工维护规则库 | 🟢 自动适应新问法 |

**当前权衡**：选择规则匹配方案，因为：
1. 化工合规查询的问法相对固定（"XX 属于什么类别"、"XX 和 YY 能一起存吗"）
2. 零延迟对用户体验至关重要
3. AI NER 需要额外的 LLM 调用，在当前 CPU 推理环境下延迟不可接受

**演进路径**：GPU 推理就绪后，添加 AI NER 作为规则匹配的降级兜底。

#### 5.6.1 C# switch 表达式重构

修复前的 switch 语句问题：

#### 5.6.2 `[KernelFunction]` 属性标注规则

```csharp
// ✅ Semantic Kernel 通过反射发现 KernelFunction
[KernelFunction]
[Description("查询危化品属于哪个危险类别，返回对应的 GB 30000 系列标准号")]
public string CheckHazardCategory(string substanceName)
{
    // ...
}

// 关键规则：
// 1. 方法必须是 public
// 2. 必须标注 [KernelFunction] 属性
// 3. [Description] 属性会被 SK 用作 LLM 的函数描述
// 4. 方法参数名会作为 LLM 的 parameter name
// 5. 返回类型 string 会被 SK 序列化后传回 LLM
```

#### 5.6.3 配置类 POCO 模型设计

```csharp
// ✅ POCO 设计原则：
// 1. 属性 public get/set，支持 Configuration.Bind() 自动映射
// 2. 集合属性初始化为空集合，避免 null 引用
// 3. 使用 List<T> 而非数组，支持配置热加载

public class ChemicalToolConfig
{
    public List<ToolDefinition> Tools { get; set; } = new();
}

public class ToolDefinition
{
    public string Name { get; set; } = string.Empty;      // 非空默认值
    public string Description { get; set; } = string.Empty;
    public List<string> KeywordTriggers { get; set; } = new();
}
```

#### 5.6.4 字符串处理安全模式

```csharp
// ✅ C# 字符串 Substring 前必须判空/判长
private string ExtractSubstance(string userInput)
{
    // 使用 Replace 链式调用（每次返回新字符串，不修改原串）
    return userInput
        .Replace("属于什么危险类别", "")  // 安全：Replace 不抛异常
        .Replace("？", "")                 // 即使输入为 null，?.Replace 也可用
        .Trim();                            // Trim 处理空字符串安全
}

// ⚠️ 注意：Substring 在索引越界时抛 ArgumentOutOfRangeException
// 正确做法：先检查长度
int newlineIndex = afterMarker.IndexOf('\n');
string toolLine = newlineIndex >= 0 
    ? afterMarker.Substring(0, newlineIndex)  // 安全：已验证 newlineIndex >= 0
    : afterMarker;                              // 兜底：返回全部
```

## 八、修复方法论深度总结

> ▸ **v2.0 深度分析**

### 8.1 项目级 Bug 修复方法论

本项目的 Bug 修复遵循以下六阶段方法论：

```
┌─────────────────────────────────────────────────────┐
│  阶段 1：症状识别 — 从用户反馈/日志/测试中定位问题    │
│  阶段 2：根因分析 — 追溯到最深层的原因              │
│  阶段 3：方案设计 — 给出至少 2 种修复方案并对比       │
│  阶段 4：方案收敛 — 选择最优方案并论证其合理性       │
│  阶段 5：实施修复 — 编写代码并验证                   │
│  阶段 6：防御加固 — 添加测试用例防止回归              │
└─────────────────────────────────────────────────────┘
```

### 8.1.1 六阶段详解

#### 阶段 1：症状识别

**输入**：
- 用户报告（日志/测试结果）
- 系统监控指标
- LLM 输出异常

**处理**：
1. 收集所有症状信息
2. 分类整理，确定问题类型（P0/P1/P2）
3. 建立问题基线

**输出**：
- 问题描述文档
- 修复优先级列表

#### 阶段 2：根因分析

**输入**：
- 问题描述
- 代码上下文

**处理**：
1. 追溯问题到最深层次原因：
   - 架构设计问题
   - 编码错误
   - 配置问题
   - 依赖问题

2. 识别问题类型：
   - 功能错位
   - 语义不匹配
   - 领域不完整

**输出**：
- 根因分析报告
- 分类结论

#### 阶段 3：方案设计

**输入**：
- 至少 2 种候选方案
- 每种方案的优缺点

**处理**：
1. 对比分析：
   - 方案 A vs 方案 B vs 方案 C
   - 决策矩阵表格

2. 评估标准：
   - 代码质量
   - 可维护性
   - 可测试性
   - 安全性
   - 日志规范

**输出**：
- 推荐方案及理由
- 方案收敛结论

#### 阶段 4：方案收敛

**处理**：
1. 选择最优方案
2. 论证该方案为什么是最优的

**输出**：
- 决策记录

### 8.1.2 关键原则

1. **先定位，再分析**：不要急于修复。先理解问题的全貌，确定问题类型，再设计方案。
2. **多方案对比**：给出至少 2 种方案，对比优劣。
3. **选择最优方案并论证**：说明为什么选择该方案。
4. **实施修复**：动手写代码前，先想清楚要改什么、怎么改。
5. **验证修复**：改完后再测试，确保真的修好了。
6. **防止再次出现同样的问题**：添加回归测试，防止修好的 bug 再次出现。

### 8.1.3 十四个关键教训

1. 编译器不能检测语义错误 → 需要人工审查。
2. 字符串契约（String Contract）：用 switch 匹配工具名，但这是隐式依赖（Implicit Dependency），不是显式声明。
3. 开闭原则（OCP）：新增工具不改源码，只改配置。
4. 分布式耦合：同一个工具集被 4 个文件分散引用。
5. 硬编码配置：不是硬编码 if-else，而是配置驱动。

### 8.2 系统性修复经验提炼

从本项目 80+ 个文档的 Bug 修复实践中，提炼出以下可复用的方法论：

#### 原则 1：Bug 是特征，不是异常

每一个 Bug 都是系统的特征信号，代表了系统设计中的某个缺陷或不足。修复 Bug 的过程，就是逐步消除这些特征信号的过程。

**核心认知**：
- Bug = 系统设计缺陷的显式表达
- 修复 = 消除缺陷的工程过程

#### 原则 2：修复需要方法

不是所有的 Bug 都需要修复。有些 Bug 是特性（Feature），不是缺陷（Defect）。修复 Bug 需要方法（Method），而不是凭感觉。

**工程方法**：
1. 先理解问题的本质
2. 再设计方案
3. 然后实施修复
