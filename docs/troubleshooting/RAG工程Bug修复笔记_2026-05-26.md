## 修复详情

### Bug 1 — 重排序 key 对不上

**文件**: `ChemicalRAG.cs` — `SearchAsync`

```csharp
// ❌ priorityLevels key 是 "国标"/"园区规则"/"历史案例"（RegulationType 值）
// 但查找的是 Metadata["Priority"]，值是 "高"/"中"/"低"
r.Metadata["Priority"]   // "高" → 字典里没有 → priority 永远为 0

// ✅ 修复
r.Metadata["RegulationType"]   // "国标" → 字典里有
// 同时补上 "企业制度" → 500
```

> ▸ **v2.0 深度分析**

#### Bug 1 多方案对比

| 维度 | 方案A：修改查找 key（采用） | 方案B：修改字典 key | 方案C：自动映射层 |
|------|:---:|:---:|:---:|
| **策略** | 调用方改查 `RegulationType` 而非 `Priority` | 字典 key 从 `RegulationType` 改为 `Priority` 值 | 新增映射方法，自动将 Priority 转 RegulationType |
| **正确性** | 🟢 Metadata 语义正确（RegulationType 是法规类型） | 🔴 Priority 语义错误（"高/中/低"不是法规类型） | 🟡 需维护映射表 |
| **影响范围** | 🟡 所有读取 Metadata["RegulationType"] 的调用方 | 🔴 所有写入 Priority 的调用方 | 🟡 调用方 + 映射层 |
| **工作量** | 1 行修改 | 多处字典 key 修改 | 新增类 + 多处调用修改 |
| **语义自解释** | 🟢 代码自说明 | 🔴 违反直觉（法规类型用"高/中/低"） | 🟡 增加抽象层 |

**选择方案A的理由**：`Metadata["RegulationType"]` 的语义是"法规类型"，用于区分国标/园区规则/历史案例。而 `_priorityLevels` 字典的语义也是"按法规类型给予不同权重"。两者的 key 空间天然应一致。方案B 将字典 key 改为 "高/中/低" 违反了字典的语义设计意图。

**架构教训**：当两个数据结构的 key 空间不同时，一定是设计阶段的语义不统一。应该在设计文档中明确每个字段的语义和值域，而非在代码中靠"试"来匹配。

### Bug 8 — BM25/向量数量级不一致导致加权失效

**文件**: `HybridKnowledgeBaseService.cs` — `HybridRetrieveAsync`

```csharp
// ❌ BM25 分 0~150，向量分 0~1，差 100 倍 → 向量权重形同虚设
hybridScore = bm25Score * 0.4 + vectorScore * 0.6
// 50*0.4=20 碾压 0.6*0.6=0.36
```

**修复**: BM25 分先除以本批次最大值归一化到 0~1。

> ▸ **v2.0 深度分析**

#### Bug 8 数学原理分析：为什么加权求和需要归一化

**加权求和公式**：

\[S_{hybrid} = w_b \cdot S_{bm25} + w_v \cdot S_{vector}\]

**问题**：当 \(S_{bm25} \in [0, 150]\) 且 \(S_{vector} \in [0, 1]\) 时：

\[50 \times 0.4 + 0.6 \times 0.6 = 20 + 0.36 = 20.36\]

BM25 分完全碾压了向量分，向量权重 \(w_v = 0.6\) 形同虚设。

**两种修复方案的数学对比**：

| 方案 | 公式 | 优点 | 缺点 |
|------|------|------|------|
| **方案A：Min-Max 归一化** | \(S'_{bm25} = \frac{S_{bm25} - S_{min}}{S_{max} - S_{min}}\) | 保留分布形状 | 需要知道批次 min/max |
| **方案B：RRF（Reciprocal Rank Fusion）** | \(S_{rrf} = \sum_{i} \frac{1}{k + rank_i}\) | 不依赖原始分数量纲 | 丢失分数强度信息 |
| **方案C：Z-Score 标准化** | \(S'_{bm25} = \frac{S_{bm25} - \mu}{\sigma}\) | 统计学标准方法 | 小批次不稳定 |

**选择方案A（Min-Max归一化）**：当前批次大小 topK=10，Min-Max 归一化在已知批次范围内可控。RRF 更适用于混合不同检索器的排序结果，但丢失了分数强度信息（"有多相关"），不适合本场景。

**架构演进**：后续 Sprint 4 中，团队将加权求和整体替换为 RRF（k=60），作为更成熟的融合方案。这体现了架构演进的典型路径：先快速修复（归一化），再架构升级（RRF）。

## 审查经验总结方法论 v2.0

> ▸ **v2.0 深度分析**

### 一、九条审查检查清单的实战应用

基于本项目 30 个 Bug 的实战经验，将上述 9 条审查维度扩展为可操作的检查清单：

#### 1. Key 一致性（Bug 1、Bug 30）

| 检查点 | 方法 | 典型案例 |
|--------|------|---------|
| 字典 key 和 Metadata key 是否同语义空间 | grep 所有 `[\"xxx\"]` 和 `new Dictionary` | Bug 1：RegulationType vs Priority |
| 两处 key 的来源是否一致 | 追溯 key 的赋值点 | Bug 30：_priorityLevels vs Metadata["Priority"] |

**核心原则**：当两个数据结构的 key 空间不同时，一定是设计阶段的语义不统一。

#### 2. 子系统完整性（Bug 2、Bug 9）

| 检查点 | 方法 | 典型案例 |
|--------|------|---------|
| 类有几个存储后端 | 搜索类中所有 `Add`/`Clear`/`Delete` 方法 | Bug 2：BM25 + pgvector 双存储 |
| `Clear()` 是否清除了所有后端 | 逐后端验证 | Bug 2：只清了 BM25 |
| `Add()` 是否写入了所有后端 | 逐后端验证 | Bug 9：只写了 BM25 |

**核心原则**：多存储后端的子系统必须有对称的写/清操作。

#### 3. 降级副作用（Bug 3、Bug 6）

| 检查点 | 方法 | 典型案例 |
|--------|------|---------|
| catch 返回的兜底值会进数据库吗 | 追踪返回值的使用路径 | Bug 3：随机向量写入 pgvector |
| 降级结果会被二次使用吗 | 检查降级值是否参与后续计算 | Bug 6：BM25 降级结果被重复融合 |

**核心原则**：降级逻辑的副作用往往比失败本身更危险。

#### 4. 计数器守恒（Bug 4）

| 检查点 | 方法 | 典型案例 |
|--------|------|---------|
