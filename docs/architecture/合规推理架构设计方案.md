## 一、当前架构全景

### 1.1 主推理管线

```
用户输入
  │
  ▼
IntentRouter.Route()                           ← static 纯逻辑，关键词匹配
  │
  ├─ ChemicalCompliance → ExecuteChemicalComplianceAsync
  │    │
  │    ├─ SK Auto Function Calling              ← LLM 自主选择工具
  │    │    ├─ CheckHazardCategory              → ChemicalDatabaseService
  │    │    ├─ CheckStorageCompatibility        → ChemicalDatabaseService + KB
  │    │    ├─ GetSafetyDistance                → ChemicalDatabaseService
  │    │    ├─ GetMajorHazardThreshold           → ChemicalDatabaseService
  │    │    ├─ LookupChemicalProperties          → ChemicalDatabaseService
  │    │    ├─ CheckRegulationVersion            → ChemicalDatabaseService
  │    │    └─ GetCurrentTime / Calculate        → 系统工具
  │    │
  │    ├─ ApplyDecoupledPipeline()              ← ★ 双通道解耦核心
  │    │    ├─ FC=Required 违约检测              （toolCalls==0 → 丢弃全部LLM输出）
  │    │    ├─ ComplianceFactExtractor.Extract   （正则提取工具返回值中的结构化事实）
  │    │    ├─ OutputSanitizer.Sanitize          （白名单硬拦截非工具返回的法规引用）
  │    │    ├─ FactAssembler.Build               （确定性C#模板渲染查询结果）
  │    │    └─ ResponseMerger.Merge              （合并事实通道 + 解释通道）
  │    │
  │    └─ 返回 (answer, toolCalls, warnings)
  │
  └─ GeneralChat → ExecuteGeneralChatAsync
```

### 1.2 双通道解耦架构（当前已实现）

**问题**：SK Auto Function Calling 模式下，LLM 可能不触发工具，直接用"幻觉知识"编造合规结论和法规编号。

**方案**：将"查了什么"和"怎么说"拆成两条独立通道。

| 通道 | 职责 | 实现 | LLM参与 |
|------|------|------|---------|
| **事实通道** | 提取工具返回值中的结构化事实，确定性渲染 | ComplianceFactExtractor → FactAssembler | 否 |
| **解释通道** | LLM 生成专业解读和建议 | LLM（经 PromptSanitizer 消毒 + OutputSanitizer 硬拦截） | 是 |

**四层硬拦截防线**：

| 防线 | 组件 | 机制 | 确定性 |
|------|------|------|--------|
| ① Prompt消毒 | `PromptSanitizer.SanitizeSystemPrompt` | 移除"引用法规编号"指令，替换【法规依据】→【专业解读】 | ✅ |
| ② 工具结果消毒 | `PromptSanitizer.SanitizeToolResult` | 剥离 `[REGULATIONS:...]` 标签，LLM看不到原始法规编号 | ✅ |
| ③ 输出消毒 | `OutputSanitizer.Sanitize` | 白名单匹配——不在工具返回列表中的法规编号直接硬删除 | ✅ |
| ④ FC违约检测 | `ApplyDecoupledPipeline` 首行 | `toolCalls.Count == 0` → LLM输出全部丢弃，返回确定性兜底 | ✅ |

**配置开关**：

```csharp
// AppConfig.cs — 默认开启
public bool UseDecoupledArchitecture { get; set; } = true;

// 解耦后的 LLM 输出模板（只要求专业解读，不要求引用法规）
public string OutputTemplateDecoupled =>
    "【专业解读】基于已知事实给出专业分析\n" +
    "【操作建议】具体的行动建议（如有）\n" +
    "【注意事项】需要人工关注的风险点";
```

## 二、反思机制设计（双层架构）

### 2.1 当前状态：只判对错

`ReflectionVerifier` 现在做的事：

```
LLM输出 → 正则提取GB编号 → KB反向检索 → ✓存在 / ✗幻觉
                                           ↓
                                    只标记对错，不纠正、不补全
```

**问题**：在化工安全场景下，"这个编号不存在"是无效输出。用户需要的是"正确的编号是什么，从哪能查到"。

### 2.2 目标架构：双层反思

#### Tier 1：知识库缺失 → 联网检索建议

```
LLM输出中出现工具未返回的GB编号
          │
          ▼
   ① KB反向检索 → 未找到
          │
          ▼
   ② 输出替代方案和检索途径（非简单删除）:
      ├─ ⚠️ 建议查阅: 国家标准全文公开系统
      │    https://openstd.samr.gov.cn/
      ├─ 保留工具返回的正确编号列表
      └─ 可选: 异步触发外部检索 Agent
```

**不是"判错就完了"，而是给出补救路径。**

#### Tier 2：编号正确但结论单薄 → Agentic Review

```
LLM初始回答（编号正确但信息不完整）
          │
          ▼
   ① Agentic Review（独立LLM调用 / Plan模型）:
      ├─ 检查完整性: 缺了什么维度？
      ├─ 补充风险分析: 为什么这个结论成立？
      ├─ 补充操作细节: 具体怎么整改？
      └─ 补充交叉引用: 还有哪些相关标准？
          │
          ▼
   ② 结构化富化:
      ├─ 【合规判定】保持原判
      ├─ 【风险分析】为什么要这样判
      ├─ 【整改措施】具体操作步骤
      ├─ 【法规交叉】关联的其他标准
      └─ 【数据可信度】知识库命中率 / 是否联网补充
```

## 三、Multi-Agent 演进路线（行业参考+本系统映射）

### 3.1 真实化工安全 Agent 标准架构

工业界（国内化工园区数字化平台）主流模式：

```
┌─────────────────────────────────────────────────────────┐
│                    Multi-Agent 架构                        │
├─────────────────────────────────────────────────────────┤
│                                                           │
│  ① 检索 Agent (Retriever)               ← 已实现          │
│     ├─ 内部 KB: PostgreSQL + pgvector                     │
│     ├─ 法规库: GB/GB-T 标准全文                           │
│     └─ 化学品库: CAS号 / UN编号 / GHS分类                 │
│                                                           │
│  ② 合规判定 Agent (Judge)               ← 已实现          │
│     ├─ SK Auto FC: ChemicalComplianceTools                │
│     └─ 二元判定 + 法规条款引用                             │
│                                                           │
│  ③ 安全顾问 Agent (Advisor)             ← Tier 2 目标     │
│     ├─ 基于判定结果，富化操作层信息                        │
│     ├─ 风险分析 + PPE要求 + 应急措施                       │
│     └─ 关联法规交叉引用                                    │
│                                                           │
│  ④ 审核 Agent (Reviewer)                ← Tier 1 目标     │
│     ├─ 完整性检查: 缺了什么维度？                          │
│     ├─ 一致性检查: 判定和引用法规是否自洽？                │
│     └─ 有问题 → 回退给 Advisor 或触发人工工单              │
│                                                           │
│  ⑤ 外部检索 Agent (External)            ← Tier 1 目标     │
│     ├─ 内部 KB 未命中时触发                                │
│     ├─ 联网检索权威源（标准公开系统、应急管理部）          │
│     └─ 结果标注来源 + 置信度                               │
│                                                           │
│  ⑥ 人机协作网关 (Human-in-the-Loop)     ← 后续扩展        │
│     ├─ 高风险场景自动生成工单                              │
│     ├─ 知识库未覆盖的化学品 → 安环部门审核                 │
│     └─ 审核结果回流到 KB（持续学习）                       │
│                                                           │
└─────────────────────────────────────────────────────────┘
```

## 五、关键设计决策记录

### 决策1: 双通道解耦而非单通道加强

**备选方案**: 在 prompt 中更强调"不要编造法规编号"  
**选择原因**: prompt 约束无法100%防止 LLM 幻觉；双通道将法规引用从 LLM 输出路径中物理隔离，是确定性方案

### 决策2: 评测判定用后置校验而非前置 prompt 注入

**备选方案**: 修改 prompt 让 LLM 输出更精确的结论  
**选择原因**: 前置方案依赖 LLM 行为，不可靠；后置方案（CheckConclusion + ValidateGbNumberHallucinations）是确定性逻辑

### 决策3: 反思机制分层设计（Tier 1 + Tier 2）而非单一纠正

**备选方案**: 当前 ReflectionVerifier 的"只判对错"模式  
**选择原因**: 化工安全场景下"判错"无业务价值；必须补充"正确的替代方案"（Tier 1）和"富化操作建议"（Tier 2）

### 决策4: 结论准确率目标 65% → 80%，采用分阶段验证

**路径A+B先行**: 低风险、小改动，在 CheckConclusion 中集成 ValidateGbNumberHallucinations  
**路径C后备**: 在 OutputSanitizer 后增加 GB 纠正层  
**验证方式**: 远程GPU评测集全量跑分，而非本地模拟
