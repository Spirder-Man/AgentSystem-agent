### 1.2 LLM 调用链路分析

基于 [LlmService.cs](../Agent1/Services/LlmService.cs) 的关键调用特征：

```
用户输入 → InvokePromptStreamingAsync (SK Auto Function Calling)
         ├── OpenAIPromptExecutionSettings { ToolCallBehavior = AutoInvokeKernelFunctions, Temperature = 0.3 }
         ├── CancellationTokenSource(3min)  // 显式超时
         ├── <think> 标签过滤 (DeepSeek-R1 专有)
         ├── 失败重试: MaxRetries=3, RetryDelayMs=1000
         └── 向量嵌入: POST /api/embeddings → nomic-embed-text
```

**模型能力需求清单**（由调用链路推导）：

| 能力要求 | 说明 | 当前满足度 |
|----------|------|-----------|
| Function Calling / Tool Use | SK Auto Function Calling 依赖模型原生支持工具调用 | 中等（DeepSeek-R1:7b 不稳定） |
| 流式输出 | `InvokePromptStreamingAsync` 逐块消费 | 满足 |
| 中文指令遵循 | 合规审核 Prompt 全中文 | 良好 |
| 结构化输出 | Prompt 要求输出"是否合规/法规依据/整改建议"格式 | 中等（格式不总能稳定遵循） |
| 低延迟推理 | ComplianceCheckModule 实时审核场景 | 中等（7B 模型约 3-8 秒/次） |
| Embedding 生成 | 768 维向量，与 pgvector 表结构绑定 | 满足 |

## 二、五维模型选型评估框架

### 维度一：业务场景匹配度（权重 30%）

#### 1.1 评估子维度

| 子维度 | 评估方法 | 量化指标 |
|--------|----------|----------|
| **化工术语覆盖率** | 构建术语测试集（GB 30000 28 类危险类别 + 50 种常见危化品名），统计模型在 zero-shot 下的术语识别准确率 | 准确率 ≥85% 为合格 |
| **法规条款引用精度** | 选取 20 条典型合规查询，评估模型是否能正确关联到对应 GB 标准编号 | 标准编号正确率 ≥70% 为合格 |
| **结构化输出遵循度** | 测试模型在给定 Prompt 模板下输出"是否合规/法规依据/整改建议"三段的成功率 | 格式遵循率 ≥80% 为合格 |
| **幻觉控制能力** | 测试模型在无知识库支撑时是否诚实声明"不确定"而非编造法规 | 诚实率 ≥90% 为合格 |

#### 1.2 化工领域评测集构建指南

```
评测集结构（建议 50 条）：
├── 类别查询（15条）："过氧化氢属于什么危险类别？"
├── 储存兼容（15条）："苯和丙酮可以同库储存吗？"
├── 安全距离（10条）："甲类仓库与明火点的最小安全距离是多少？"
└── 综合审核（10条）："仓库有2吨甲醇和1吨硝酸相邻存放，是否合规？"
```

#### 1.3 打分卡

| 分值 | 含义 | 化工场景表现 |
|------|------|-------------|
| 5 分 | 卓越 | 能区分 GB 30000.7（易燃液体）与 GB 30000.14（氧化性液体）的细微差别 |
| 4 分 | 良好 | 能正确引用 GB 编号，偶尔混淆相近类别 |
| 3 分 | 可用 | 能理解危险类别概念但引用不够精确 |
| 2 分 | 勉强 | 只能给出通用安全建议，无法关联具体法规 |
| 1 分 | 不适用 | 完全无法理解化工合规语境 |

### 维度二：模型分类策略（权重 20%）

#### 2.1 ModelScope 模型分类导航

ModelScope 平台分类体系与本项目需求的映射：

```
ModelScope 分类              →  本项目对应需求
─────────────────────────────────────────────
自然语言处理 → 文本生成      →  LLM（合规结论生成 + 工具调用规划）
自然语言处理 → 文本表示      →  Embedding 模型（RAG 向量检索）
自然语言处理 → 信息检索      →  Reranker 模型（检索结果重排序）
多模态 → 图像理解            →  化工设备图像/安全标识识别（预留）
科学计算 → 分子性质预测      →  危化品理化性质辅助判断（远期规划）
```

#### 2.2 LLM 选型三条路径对比

| 路径 | 代表模型（ModelScope） | 优点 | 缺点 | 适用条件 |
|------|----------------------|------|------|----------|
| **通用底座 (Base)** | Qwen3-8B, DeepSeek-V3 | 生态成熟、部署文档丰富、社区活跃 | 化工领域知识依赖 RAG 补充 | 知识库质量高时首选 |
| **垂直微调 (Fine-tuned)** | 暂无化工合规专用模型 | 理论上可内化领域知识 | 微调成本高、需标注数据、有过拟合风险 | 知识库无法覆盖隐性知识时考虑 |
| **领域蒸馏 (Distilled)** | 通用模型的小型化版本 | 低延迟、低资源消耗 | 能力折损、中文化工场景未验证 | 边缘设备部署或极致成本控制 |

**推荐策略**：**通用底座 + RAG 增强** 作为主路径，原因有三：
1. 当前知识库已收录 GB 30000、GB15603、GB50160 等全套国标，RAG 检索可覆盖显性知识
2. 化工合规审核高度依赖法规原文精确引用，RAG 的溯源能力优于模型记忆
3. 通用底座模型生态更新快，跟随升级成本低

#### 2.3 Embedding 模型选型路径

| 模型 | 维度 | MTEB 中文 | Ollama 支持 | 与当前架构兼容 |
|------|------|-----------|-------------|---------------|
| **nomic-embed-text**（当前） | 768 | ~60 分 | 原生 | 完全兼容 |
| **gte-large-zh** | 1024 | ~72 分 | 需自行转换 | 需 ALTER TABLE 改维度 |
| **BGE-M3** | 1024 | ~75 分 | 需自行转换 | 需 ALTER TABLE 改维度 |
| **Qwen3-Embedding-0.6B** | 1024 | ~78 分 | 需自行转换 | 需 ALTER TABLE 改维度 |

**当前约束**：pgvector 表结构 `embedding vector(768)` 硬编码，更换非 768 维模型需重建全部向量索引。

#### 2.4 Reranker 模型引入决策

| 是否引入 | 场景 | 收益 |
|----------|------|------|
| 暂不引入 | 当前知识库 2000-5000 chunk，topK=3 | 混合检索的 BM25 关键词纠偏已够用 |
| 建议引入 | 知识库增长到 10000+ chunk 或 topK=5+ | 可显著提升检索精度 |

ModelScope 可选 Reranker：`gte-reranker`、`BGE-Reranker-v2-m3`。

### 维度三：技术指标权衡（权重 25%）

#### 3.1 响应时间 SLA 分析

基于 [ComplianceCheckModule.cs](../Agent1/Modules/ComplianceCheckModule.cs) 的实时审核流程：

```
合规自查全链路耗时分解：
  1. RAG 检索（BM25 + 向量混合）  → 约 0.5-1.5 秒
  2. LLM 工具调用规划（可选）      → 约 2-5 秒
  3. LLM 合规结论生成（流式）      → 约 3-8 秒
  4. 审计日志记录                 → 约 0.1 秒
  ─────────────────────────────────────────
  总计                           → 约 5-15 秒
```

**响应时间 SLA 建议**：

| 场景 | P50 | P95 | P99 | 严重性 |
|------|-----|-----|-----|--------|
| 合规自查（交互式） | ≤8 秒 | ≤15 秒 | ≤20 秒 | 用户体验可接受 |
| 批量巡检报告生成 | ≤30 秒 | ≤60 秒 | ≤90 秒 | 异步处理可接受 |
| 紧急应急咨询 | ≤5 秒 | ≤10 秒 | ≤15 秒 | 需要优化 |

#### 3.2 模型规模与推理延迟映射（Ollama 本地部署参考值）

| 模型规模 | 代表模型 | 内存占用 | 首 Token 延迟 | 生成速度 | 适用场景 |
|----------|----------|----------|-------------|----------|----------|
| 0.5B-3B | Qwen3-1.8B | 2-4 GB | 0.5-1 秒 | 30-50 tok/s | 工具调用规划、关键词提取 |
| 7B-8B | DeepSeek-R1:7B, Qwen3-8B | 6-10 GB | 1-3 秒 | 15-25 tok/s | **当前主路径（合规结论生成）** |
| 14B-32B | Qwen3-32B | 20-40 GB | 3-8 秒 | 8-15 tok/s | 复杂综合审核、多轮推理 |
| 72B+ | DeepSeek-V3 | 80+ GB | 5-15 秒 | 3-8 tok/s | 非本地部署场景 |

#### 3.3 精度-速度权衡矩阵

```
                    高精度
                      │
         Qwen3-32B    │    Qwen3-72B
         (批处理)     │    (云端API)
                      │
  ──────────────────────────────────→ 低延迟
                      │
     Qwen3-1.8B       │    Qwen3-8B
     (工具规划)       │    ★ 推荐区域
                      │
                    低精度
```

**本项目推荐区域**：7B-8B 区间，兼顾可接受的精度和交互式响应延迟。

#### 3.4 精度评估指标定义（化工合规场景）

| 指标 | 定义 | 计算方式 |
|------|------|----------|
| **法规引用准确率** | 模型引用的 GB 编号是否与知识库中对应条款一致 | 正确引用数 / 总引用数 |
| **结论正确率** | "是否合规"判断是否正确 | 正确判断数 / 总判断数 |
| **整改建议可行性** | 给出的整改建议是否具体可操作 | 人工评定（1-5 分） |
| **幻觉率** | 编造不存在法规或数据的比例 | 幻觉次数 / 总输出数 |

### 维度四：部署兼容性（权重 15%）

#### 4.1 与 Ollama 本地部署的兼容矩阵

| 部署要素 | 要求 | 当前状态 | 切换影响 |
|----------|------|----------|----------|
| **模型格式** | GGUF（Ollama 原生支持） | deepseek-r1:7b 为 GGUF | ModelScope 模型需转换为 GGUF 才能本地 Ollama 部署 |
| **Embedding API** | `POST /api/embeddings` | nomic-embed-text 通过此 API 调用 | 须确认新模型兼容 Ollama Embeddings API |
| **Chat API** | `POST /api/chat` (OpenAI 兼容) | SK `AddOllamaChatCompletion` 封装 | 绝大多数 Ollama 模型兼容 |
| **Function Calling** | 工具调用需模型原生支持 | 当前依赖 SK Auto Function Calling | 优先选择明确支持 tool_use 的模型 |

#### 4.2 ModelScope 模型接入 Ollama 的两种路径

```
路径 A：ModelScope 已有 GGUF 版本
  ModelScope 下载 GGUF → 创建 Modelfile → ollama create → ollama run
  例：modelscope.cn/models/Qwen/Qwen3-8B-GGUF

路径 B：需自行转换
  ModelScope 下载 safetensors → 使用 llama.cpp convert 转 GGUF → ollama create
  成本：约 30-60 分钟，需 llama.cpp 工具链
```

#### 4.3 向量维度迁移成本估算

若从 nomic-embed-text (768维) 切换到 BGE-M3 (1024维)：

| 步骤 | 操作 | 预估耗时 |
|------|------|----------|
| 1. ALTER TABLE | `ALTER COLUMN embedding TYPE vector(1024)` | <1 秒 |
| 2. 重新嵌入 | 对全部 ~3000 chunk 重新生成向量 (3000 × 200ms) | ~10 分钟 |
| 3. 重建索引 | `REINDEX INDEX chemical_documents_embedding_idx` | ~30 秒 |
| 4. 更新配置 | 修改 `appsettings.json` 中 `EmbeddingDimension: 1024` | <1 分钟 |
| **总计** | | **约 12 分钟** |

#### 4.4 与 Semantic Kernel 的兼容性

| 兼容维度 | 说明 |
|----------|------|
| **Function Calling** | SK 通过 `OpenAIPromptExecutionSettings.ToolCallBehavior = AutoInvokeKernelFunctions` 启用，要求模型遵循 OpenAI function calling 协议 |
| **Ollama 连接器** | SK 的 `AddOllamaChatCompletion` 封装了 HTTP 调用，更换模型只需修改 `ModelId` 配置项 |
| **ChemicalComplianceTools** | 工具定义为 C# 类 `[KernelFunction]` 特性标注，与模型无关，切换模型无需改代码 |

### 维度五：成本效益分析（权重 10%）

#### 5.1 部署模式成本对比

| 成本项 | Ollama 本地部署（当前） | ModelScope API 调用 |
|--------|------------------------|---------------------|
| **硬件成本** | 需 GPU（≥8GB VRAM）或 CPU（≥16GB RAM） | 无硬件要求 |
| **推理成本** | 仅电费（约 0.5-2 元/小时） | 按 token 计费（约 0.5-2 元/百万 token） |
| **网络成本** | 零 | 需稳定互联网连接 |
| **运维成本** | 需维护 Ollama 服务进程 | 零运维 |
| **数据安全** | 数据不出本地，满足等保三级 | 数据传输至云端，需评估合规性 |

#### 5.2 成本平衡点计算

```
估算公式：
  月调用次数 × 平均 token 数 × API 单价 = 月 API 成本

假设场景：
  - 日均合规自查 50 次
  - 每次平均 2000 token（输入+输出）
  - 月调用量：50 × 30 × 2000 = 3,000,000 token
  
  API 成本（以 Qwen API 约 2 元/百万 token 计）：约 6 元/月
  本地 GPU 电费（RTX 3060 12GB，200W，0.6 元/度，日均运行 2 小时）：约 7.2 元/月
  
  → 低调用量下两者成本接近，本地部署的数据安全优势显著
```

#### 5.3 模型切换一次性迁移成本

| 迁移项 | 工作量 | 风险等级 |
|--------|--------|----------|
| LLM 切换 | 修改 `appsettings.json` 中 `ModelId`，无需改代码 | 低 |
| Embedding 切换 | 修改配置 + 重建向量索引（约 12 分钟） | 中 |
| 模型下载 | GGUF 文件 4-10 GB，视网速 10-60 分钟 | 低 |
| 功能验证 | 运行 50 条评测集验证准确率 | 中 |
| Prompt 调优 | 新模型可能需要调整 Prompt 模板 | 中 |

#### 5.4 业务价值量化参考

| 价值维度 | 量化方式 | 参考值 |
|----------|----------|--------|
| 审核效率提升 | 人工审核 vs AI 审核耗时比 | 人工 30 分钟/次 → AI 10 秒/次（180× 提升） |
| 法规覆盖率 | AI 可检索国标数量 vs 人工记忆范围 | 30+ 国标全量覆盖 vs 人工 5-8 个 |
| 合规风险降低 | 审核遗漏率对比 | 需实际业务数据验证 |

## 四、可操作的选型决策流程

### 4.1 决策树

## 五、推荐路径与阶段规划

### 5.1 立即可执行（零成本改进）

| 优先级 | 行动 | 预期收益 |
|--------|------|----------|
| P0 | 构建 50 条化工合规评测集 | 建立可量化的选型基准 |
| P1 | 在当前 DeepSeek-R1:7b 上基线评测 | 明确当前能力天花板 |
| P2 | 优化 ComplianceCheckModule 的 Prompt 模板 | 无需换模型即可提升格式遵循率 |

### 5.2 短期推荐（1-2 周验证）

| 优先级 | 行动 | 说明 |
|--------|------|------|
| **P0** | **LLM 切换为 Qwen3-8B** | 解决 DeepSeek-R1 Function Calling 不稳定问题，原生支持 SK Auto Function Calling；如果 ModelScope 有 GGUF 版本则可直接 Ollama 部署 |
| P1 | 进行 A/B 测试验证 Qwen3-8B 效果 | 使用评测集 + 打分卡量化对比 |

### 5.3 中期储备（按需启用）

| 优先级 | 行动 | 触发条件 |
|--------|------|----------|
| P2 | Embedding 切换为 gte-large-zh 或 BGE-M3 | 当前向量检索召回率不满足业务需求 |
| P2 | 引入 Reranker（BGE-Reranker-v2-m3） | 知识库增长至 10000+ chunk |
| P3 | Qwen3-1.8B 作为工具调用规划专用模型 | 需要将工具规划与合规生成分离以降低延迟 |

### 5.4 长期演进方向

| 方向 | 说明 |
|------|------|
| 多模态集成 | 当业务需要处理化工设备巡检图像时，启用 qwen-vl 或升级为 Qwen2.5-VL |
| 科学计算模型 | 如需危化品理化性质预测（沸点、闪点等），可引入 ModelScope 分子性质预测模型 |
| 模型蒸馏 | 当积累足够业务数据后，可考虑蒸馏专用小模型降低部署成本 |

## 六、附录：ModelScope 模型获取与集成速查

### A.1 ModelScope 模型下载命令

```bash
# 安装 ModelScope CLI
pip install modelscope

# 下载模型（以 Qwen3-8B 为例）
modelscope download --model Qwen/Qwen3-8B

# 下载 GGUF 版本（如果存在）
modelscope download --model Qwen/Qwen3-8B-GGUF
```

### A.2 Ollama 模型导入流程

```bash
# 步骤 1: 下载 GGUF 文件到本地
# 步骤 2: 创建 Modelfile
cat > Modelfile << EOF
FROM ./qwen3-8b.Q5_K_M.gguf
PARAMETER temperature 0.3
PARAMETER num_ctx 4096
TEMPLATE """{{ if .System }}<|im_start|>system
{{ .System }}<|im_end|>
{{ end }}{{ if .Prompt }}<|im_start|>user
{{ .Prompt }}<|im_end|>
{{ end }}<|im_start|>assistant
"""
EOF

# 步骤 3: 创建 Ollama 模型
ollama create qwen3-8b -f Modelfile

# 步骤 4: 修改 appsettings.json
# "ModelId": "qwen3-8b"
```

### A.3 配置切换清单

更换模型时需修改的配置项（均在 `appsettings.json`）：

```json
{
  "Llm": {
    "ModelId": "qwen3-8b",           // 切换 LLM
    "MultimodalModelId": "qwen-vl:latest"
  },
  "VectorSearch": {
    "EmbeddingModelId": "bge-m3",    // 切换 Embedding
    "EmbeddingDimension": 1024        // 同步修改维度
  }
}
```
