01 缺陷复盘 · StoreToolFacts 双重质量漏洞

从这个缺陷中提取出两个独立的质量缺失，只有同时理解它们才能构建正确的防御体系：

漏洞 A  写入时不区分质量等级

现象：StoreToolFacts() 将工具返回的所有文本（含"未找到/建议查阅"）无差别写入 KeyFacts 字典。

根因：缓存层没有响应质量标记机制。任何从工具方法返回的字符串都被视为"领域事实"。

类比：数据库写入时不校验字段约束 → 脏数据永久污染索引。

漏洞 B  读取时不检查可信度

现象：TryAnswerFromMemory() 仅做关键词子串匹配（Contains），命中即返回，不验证内容质量。

根因：没有信任分级——"上次工具返回了有效法规编号"和"上次返回了兜底文本"被同等对待。

类比：搜索引擎返回缓存结果时不检查页面是否已 404。

🔑 核心教训
这是典型的 "信任链断裂"缺陷：写入方不告诉读取方"这条数据的质量如何"，读取方默认信任所有数据。在分布式缓存系统（如 Redis）中这个问题通过 TTL + 版本号 + 校验和 解决；在 AI 响应缓存中，等价物是 质量等级标签 + 工具调用签名 + 置信度阈值。

03 五层质量防护体系 · 从代码到运行时的全链路
L1
编译期类型约束  Cursor 模式
目标：工具返回值从裸 string 升级为带质量标签的 ToolResult 结构体，编译期强制下游必须处理质量字段。
现状问题：所有 [KernelFunction] 返回 Task<string>，调用方无法区分"有效法规数据"和"兜底建议"。
改造：
public class ToolResult { public string Content { get; init; } public QualityLevel Quality { get; init; } // 编译期强制字段 public List<string> Regulations { get; init; } // 提取到的法规编号 public bool IsFallback => Quality == QualityLevel.Fallback; } public enum QualityLevel { RAG_HIT, // RAG 检索命中，有原文支撑 DATABASE_HIT, // 结构化数据库命中 DICTIONARY_HIT, // 硬编码字典命中 FALLBACK, // 兜底诚实声明 ERROR // 异常 }
L2
规则引擎检查  Trae 模式
目标：声明式规则文件 quality-rules.json，缓存写入前逐条检查，不合格的拒绝写入。
规则示例：
{ "rules": [ { "id": "R001", "name": "禁止缓存兜底文本", "trigger": "StoreToolFacts", "condition": "result.Quality == FALLBACK", "action": "REJECT", "reason": "兜底文本不可作为领域事实缓存" }, { "id": "R002", "name": "兜底文本模式匹配", "trigger": "StoreToolFacts", "condition": "matchesAny(result.Content, FallbackPatterns)", "action": "REJECT_AND_WARN", "patterns": [ "未在常见.*中直接匹配", "建议查阅.*全文", "未找到.*数据", "建议参考.*查询" ] } ] }

04 缓存质量门禁清单 · Gate Checklist

每条门禁对应一个明确的"触发时机 → 检查条件 → 动作"，可逐步实现：

✅ P0
G1 · 写入质量门禁
StoreToolFacts / PostInferenceAsync 写入缓存前
result.Quality != FALLBACK
AND result.Regulations.Count > 0
✅ P0
G2 · 读取质量门禁
TryAnswerFromMemory / PreInferenceAsync 返回缓存前
cached.Quality >= DICTIONARY_HIT
OR cached.ToolsUsed.Count > 0
⚠️ P1
G3 · 兜底文本模式门禁
任何工具返回值在写入缓存前
!Regex.IsMatch(content, FallbackPattern)
⚠️ P1
G4 · 缓存TTL质量衰减
低质量缓存比高质量缓存更快过期
TTL_FALLBACK=1min / TTL_DICT=5min / TTL_RAG=10min
📋 P2
G5 · 交叉验证门禁
缓存命中后异步验证：当前知识库是否已有更新数据
background: re-query RAG → diff → invalidate stale
📋 P2
G6 · 用户反馈闭环
用户对缓存回答点踩 → 该条缓存立即失效 + 规则调整
feedback.thumbs_down → cache.Invalidate(key)
