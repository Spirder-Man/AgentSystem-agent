### Bug-042：不可证伪锚点致探针永远满分盲区（强标记正则族缺驼峰类名）

| 项目 | 内容 |
|------|------|
| **修复日期** | 2026-08-12 |
| **位置** | DriftMonitor 测量链路，`DriftMatcher.cs` 强标记正则族 |
| **现象** | 探针 probe_a4（乱码闸门锚点）无论 LLM 回答正确/错误/未作答，漂移量恒为 0——探针强制断言打在没有刻度（不可证伪）的锚点上，永远满分，测不出认知漂移。 |

| **修复方案** | ① DriftMatcher 新增第 5 类强标记 CamelToken 正则 `\b[A-Z][a-z]+[A-Z][A-Za-z0-9]*\b`（排除场景：全大写前缀 SQLite/SHA256 归 UpperToken 管、无第二大写 Vite/Level1、数字嵌首 Agent1.Api——避免产品名/通用词/版本号误伤）；② 新增 5 条单测（驼峰提取/产品名防误伤/可证伪性/答对答错区分）；③ 远程真实 LLM 三态验证：正确回答 drift=0、错误回答 drift=1、未作答 drift=1，全部通过。 |
| **思维链路** | 1. 发现：q8 E2E 中 probe_a4 报"锚点不可证伪"→ 2. 定位：GarbledTextDetector 类名不匹配任何强标记正则 → 3. 分析：MatchScore 无标记默认 1.0 是"不制造噪音"设计，但与探针强制断言组合成盲区 → 4. 方案三选（扩展评分器/停用替换/暂不处理）→ 用户选根治：扩展评分器 → 5. 修复：CamelToken 正则 + 防误伤排除 → 6. 验证：50 条锚点中 ~10 条从不可证伪变可证伪，probe_a4 三态全部通过；顺带实证探针幂等覆盖（turn=4 被末次 POST 覆盖）。 |
| **影响** | 影响面：50 条锚点中 15 条含驼峰、~10 条可证伪性升级（前端器官/主存储/图谱门面/命名陷阱/配置入口/出口闸门链/双通道验证/FC策略/FC契约/乱码闸门），被动抽取将新增断言；既有测试核对安全（SQLite/Level1 不匹配新正则，无回归）。 |

| **修复方案** | ① `_incrementalGate = SemaphoreSlim(1,1)` + `WaitAsync(0)`（已被占立即抛异常，不排队）→ 两个调用方（KnowledgeBaseController + Program.cs）catch → HTTP 409「已在运行」。② 增量循环绑定 `ApplicationStopping` 令牌 → SIGTERM 后在当前文件边界收手。③ 插入前无条件防御性删除（不由内存 tracker 推断 DB 残留）→ 即使上次异常退出，本次也能从干净状态开始。 |
| **思维链路** | 1. 发现：两次快速点击加载按钮 → DB 中出现重复分块 → 2. 定位：没有互斥机制 → 3. 设计：用 SemaphoreSlim 零等待模式（已在跑就拒绝，不排队）→ 4. 加固：增加取消令牌 + 防御性删除 → 5. 残留：SaveFileTracker 仍批末落盘（逐文件落盘未实施），但优雅取消已在文件边界保进度。 |

### Bug-037：nomic-embed 向量嵌入 ubatch-size 缺失导致静默降级

| 项目 | 内容 |
|------|------|
| **修复日期** | 2026-07-29 |
| **位置** | 动脉 A，向量嵌入服务 :8081 启动参数 |
| **现象** | 600+ token 的条款块做向量嵌入时返回 HTTP 500，系统静默降级为 BM25-only 模式（只用关键词检索，不用向量相似度）。搜索结果质量下降但无告警。 |

## 三、反直觉陷阱（不是 Bug，但容易踩坑）

> 遵循工程宪法第二条流程 2：将违背直觉的底层陷阱固化为长期知识。

### 陷阱 1：Controller 是瞬时态，内部 new SemaphoreSlim 完全失效

| 项目 | 内容 |
|------|------|
| **来源** | 工程宪法 第二条流程 2 示例 |
| **现象** | `new SemaphoreSlim(1,1)` 写在 Controller 方法内 → 每次请求 new 一个新锁 → 并发控制完全失效。 |
| **正确做法** | 锁必须是单例（注入 Singleton 服务或 static 字段）。 |

### 陷阱 2：SemaphoreSlim 不可重入，漏写 finally.Release 锁永久耗尽

| 项目 | 内容 |
|------|------|
| **来源** | 工程宪法 第二条流程 2 示例 |
| **现象** | 异步方法中 `await semaphore.WaitAsync()` 后抛异常 → 未执行 `Release()` → 锁计数永久 -1 → 服务假死。 |
| **正确做法** | `await semaphore.WaitAsync(); try { ... } finally { semaphore.Release(); }` |

### 陷阱 3：单进程信号量在多实例 Docker 部署下完全失去互斥效果

| 项目 | 内容 |
|------|------|
| **来源** | 工程宪法 第二条流程 2 示例 |
| **现象** | Docker Compose 起 3 个 API 实例，每个实例有自己的 SemaphoreSlim → 全局最多 3 个并发，而非预期的 1 个。 |
| **正确做法** | 跨实例互斥必须用分布式锁（如 PostgreSQL advisory lock 或 Redis）。 |
