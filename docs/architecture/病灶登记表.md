### Bug-041：OCR 失败固化为永久薄文本降级

| 项目 | 内容 |
|------|------|
| **修复日期** | 2026-07-29 |
| **位置** | 动脉 A，`ProcessPdfFileAsync` |
| **现象** | 扫描件 PDF OCR 瞬时失败后，薄文本结果仍被写入 PG 和 file_tracker.json。下次增量更新时 tracker 认为"已处理"，跳过重试，导致 OCR 故障永久固化为低质量入库。 |
| **根因** | 缺少 OCR 质量门——失败时没有阻断入库流程。 |
| **修复方案** | 增加质量门：扫描件（`ExtractionMethod == OCR_NEEDED`）OCR 彻底失败或 `PagesOcred / PagesTotal < 0.5`（或质量 failed）→ `ProcessPdfFileAsync` 返回 false → 不入库、不记 tracker → 下轮增量自动重试。 |
| **思维链路** | 1. 发现：增量更新后搜索质量下降 → 2. 定位：某扫描件 OCR 当天服务抖动失败 → 3. 分析：tracker 记录了"已处理"所以不再重试 → 4. 修复：增加质量门，不合格不入 tracker → 5. 验证：重启 OCR 服务后增量自动重灌。 |

### Bug-039：增量加载端点可重入 + 优雅取消缺陷

| 项目 | 内容 |
|------|------|
| **修复日期** | 2026-07-29 |
| **位置** | 动脉 A 增量支线，`ChemicalRAG.cs` |
| **现象** | 用户快速连续调用增量加载接口 → 两个并发同时写 PG 和 file_tracker.json → 数据重复、tracker 状态混乱。服务收到 SIGTERM 时增量循环不感知取消信号 → 写了一半的文件留下僵尸行。 |
| **根因** | 缺少互斥锁 + 取消令牌未绑定。 |
| **修复方案** | ① `_incrementalGate = SemaphoreSlim(1,1)` + `WaitAsync(0)`（已被占立即抛异常，不排队）→ 两个调用方（KnowledgeBaseController + Program.cs）catch → HTTP 409「已在运行」。② 增量循环绑定 `ApplicationStopping` 令牌 → SIGTERM 后在当前文件边界收手。③ 插入前无条件防御性删除（不由内存 tracker 推断 DB 残留）→ 即使上次异常退出，本次也能从干净状态开始。 |
| **思维链路** | 1. 发现：两次快速点击加载按钮 → DB 中出现重复分块 → 2. 定位：没有互斥机制 → 3. 设计：用 SemaphoreSlim 零等待模式（已在跑就拒绝，不排队）→ 4. 加固：增加取消令牌 + 防御性删除 → 5. 残留：SaveFileTracker 仍批末落盘（逐文件落盘未实施），但优雅取消已在文件边界保进度。 |

### Bug-037：nomic-embed 向量嵌入 ubatch-size 缺失导致静默降级

| 项目 | 内容 |
|------|------|
| **修复日期** | 2026-07-29 |
| **位置** | 动脉 A，向量嵌入服务 :8081 启动参数 |
| **现象** | 600+ token 的条款块做向量嵌入时返回 HTTP 500，系统静默降级为 BM25-only 模式（只用关键词检索，不用向量相似度）。搜索结果质量下降但无告警。 |
| **根因** | nomic-embed 使用非因果注意力（non-causal attention），需要整段文本进入单个物理批次（ubatch）。默认 `-ub 512` 的物理批次上限只有 512 token——遇到 600+ token 的块超出上限，服务报错。启动脚本中只写了 `--batch-size 2048`（逻辑批次），缺少 `-ub 2048`（物理批次）。 |
| **修复方案** | 启动参数同时设置 `-b 2048 -ub 2048`（逻辑批次和物理批次都设为 2048），确保系统中最长的条款块（~2000 token）也能单批次处理。两处必须同调：`start_services.sh` + `scripts/zh-diag.sh#L242`。 |
| **思维链路** | 1. 发现：搜索结果部分问题查不到 → 2. 定位：BM25-only 日志 → 3. 深挖：nomic-embed 的 attention 机制需要整段进 ubatch → 4. 对比：llama.cpp 的 `-b` vs `-ub` 参数含义 → 5. 修复：双参数对齐 2048。 |

### Bug-035 / W24：SQLite 种子脚本被 Split(';') 截断

| 项目 | 内容 |
|------|------|
| **修复日期** | 2026-07 中旬 |
| **位置** | 动脉 C，`ChemicalDatabaseService.InitializeAsync` |
| **现象** | SQL 种子脚本含多语句（CREATE TABLE + 多个 INSERT），原代码用 `Split(';')` 拆分后逐条执行。SQL 语句内部的字符串值含分号时（如 `"浓度≥50%;"`）被误拆，导致 SQL 语法错误、种子写入失败。 |

| **思维链路** | 1. 发现：SQLite 种子数据不完整 → 2. 查日志：SQL 语法错误 → 3. 定位：分号在字符串值中被误拆 → 4. 修复：去掉 Split 逻辑，整段执行。 |

## 三、反直觉陷阱（不是 Bug，但容易踩坑）

> 遵循工程宪法第二条流程 2：将违背直觉的底层陷阱固化为长期知识。

### 陷阱 1：Controller 是瞬时态，内部 new SemaphoreSlim 完全失效

| 项目 | 内容 |
|------|------|
| **来源** | 工程宪法 第二条流程 2 示例 |
| **现象** | `new SemaphoreSlim(1,1)` 写在 Controller 方法内 → 每次请求 new 一个新锁 → 并发控制完全失效。 |
| **正确做法** | 锁必须是单例（注入 Singleton 服务或 static 字段）。 |

### 陷阱 2：SemaphoreSlim 不可重入，漏写 finally.Release 锁永久耗尽

| 项目 | 内容 |
|------|------|
| **来源** | 工程宪法 第二条流程 2 示例 |
| **现象** | 异步方法中 `await semaphore.WaitAsync()` 后抛异常 → 未执行 `Release()` → 锁计数永久 -1 → 服务假死。 |
| **正确做法** | `await semaphore.WaitAsync(); try { ... } finally { semaphore.Release(); }` |

### 陷阱 3：单进程信号量在多实例 Docker 部署下完全失去互斥效果

| 项目 | 内容 |
|------|------|
| **来源** | 工程宪法 第二条流程 2 示例 |
| **现象** | Docker Compose 起 3 个 API 实例，每个实例有自己的 SemaphoreSlim → 全局最多 3 个并发，而非预期的 1 个。 |
| **正确做法** | 跨实例互斥必须用分布式锁（如 PostgreSQL advisory lock 或 Redis）。 |
