# 同源拷贝联动手册

> 本文档记录系统中"改一处必须同步修改全部位置"的拷贝组。
> 核心目的：防止你改了 A 忘记改 B，导致数据不一致的隐蔽 Bug。
>
> 配合 `系统血谱.md` 使用——血谱告诉你数据从哪来到哪去，本文档告诉你哪些数据有多份拷贝。
>
> 最后更新：2026-08-05（从系统血谱拆分独立）

---

## 阅读指南

**每条拷贝组包含**：
- **拷贝点列表**：同一份数据在哪些地方存在
- **教训**：历史上因为漏改导致的 Bug
- **验证方式**：修改后如何自检是否全部同步

**使用方式**：修改任一组内数据时，先查本表找到全部拷贝点，逐一同步后自检。

---

## 拷贝组 1：化学品基础数据（安全距离 / 物质 / 配伍禁忌 / 法规版本）

这是系统中**最危险**的拷贝组——同一份化学品数据在四个地方独立维护，任意一处不同步都会导致不同消费者看到不同数据。

| 拷贝点 | 位置 | 形态 | 消费者 |
|--------|------|------|--------|
| ① SQLite 种子 | `ChemicalDatabaseService` 四个 Seed 方法 | C# 代码内嵌 SQL | 三级降级 Level 1 |
| ② PG 迁移脚本 | `db/migrations/002_chemical_knowledge_graph.sql` | SQL INSERT 语句 | 知识图谱（Level 2，**仅影响新建库**） |
| ③ 硬编码字典 | `ChemicalComplianceTools` 内部常量 | C# 字典常量 | 三级降级 Level 3（兜底） |
| ④ 测试桩 | `Stubs/StubChemicalKnowledgeGraph.cs` | C# 假数据 | xUnit 测试（仿真动脉 B） |
| ⑤ PG 存量数据 | `chemical_incompatibilities` 等表实际行 | 运行库数据 | 知识图谱（Level 2，**已存在的库不会被 002 迁移重放**） |

**教训**：
- Bug #3——硬编码字典新增了物质但没有同步到种子和迁移脚本，导致该物质只在兜底路径（Level 3）可查到，Level 1/2 查不到。现已加 FIX 注释自证同源。
- 王水 #25（2026-08-13）——硝酸↔盐酸标兼容错误存在于 ①②⑤ 三处（③④ 无此边）。改 ② 只影响新建库，存量 PG 必须单独 UPDATE（`fix_25_aqua_regia.sql` UPDATE 1）才完成修复；① SQLite 种子只影响空库，存量 SQLite 文件需删库重建（见病灶 4）。

**验证方式**（修改任一组数据后）：
1. 检查五个拷贝点是否都新增/修改/删除（② 只影响新建库，存量 PG 需另行 UPDATE）
2. 运行 `ChemicalComplianceToolsTests` + `ChemicalDatabaseTests` + `ChemicalSubstanceDatabaseTests`
3. 运行 `DatabaseIntegrationTests`（需要 PG 环境）

## 拷贝组 2：GB 白名单（OutputValidator 三源并集）

| 拷贝点 | 位置 | 形态 |
|--------|------|------|
| ① PG 图谱法规版本 | 动脉 B，`regulation_versions` 表 | 数据库记录 |
| ② SQLite 种子法规版本 | 动脉 C，Seed 方法 | C# 代码内嵌 SQL |
| ③ 硬编码字典法规版本 | 动脉 C/静脉 1，Level 3 | C# 字典常量 |

**教训**：Bug-027——OutputValidator 的 GB 白名单漏了 SQLite 种子源，导致合法编号被误判为"库外"标记为【待核实】。

**验证方式**：修改法规版本数据后，检查 OutputValidator 的库白名单构建逻辑是否覆盖了所有三个数据源。

## 拷贝组 3：评测集格式

| 拷贝点 | 位置 | 消费方式 |
|--------|------|---------|
| ① EvalEngine 加载 | `EvalEngine.cs` | 按 `EvalCase` 模型反序列化 |
| ② ResponseCacheService 预热 | `ResponseCacheService.cs` | 按相同格式解析，但只取问题文本 |
| ③ 评测流水线脚本 | `scripts/run_eval_pipeline.ps1` | 经 `--eval-set` 参数传给 EvalEngine |

**教训**：Bug #7——评测集从 v1.0 升级到 v1.1 wrapper 格式后，只改了 EvalEngine 的加载逻辑，忘了同步改 ResponseCacheService 的预热逻辑，导致预热功能静默失败。

**验证方式**：修改评测集格式后：
1. 运行 `EvalEngineTests` 确认加载正常
2. 运行 `QueryCacheServiceTests` 确认预热正常
3. 在远程环境执行 `run_eval_pipeline.ps1` 确认脚本兼容

## 拷贝组 4：前后端字段契约

| 拷贝点 | 位置 | 形态 |
|--------|------|------|
| ① C# 模型 | `Agent1/Models/` | C# 类属性 |
| ② TypeScript 类型 | `agent1-web/src/types/` | TS interface/type |
| ③ MSW Mock 数据 | `agent1-web/src/mocks/` | JS 对象 |

**教训**：多次出现后端改了字段名/类型，前端 MSW mock 不同步 → 开发模式下（Mock 模式）看起来正常，切到真实 API 立即报错。

**验证方式**：修改 API 响应模型后：
1. 同步更新前端 `src/types/` 中的 TS 类型定义
2. 同步更新 `src/mocks/` 中对应 handler 的假数据
3. 运行 `npm run test`（vitest）
4. 运行 e2e 测试（MSW mock 模式）

## 拷贝组 5：embedding 服务启动参数（-b 2048 -ub 2048）

| 拷贝点 | 位置 | 脚本类型 |
|--------|------|---------|
| ① `start_services.sh` | 项目根目录 | bash 启动脚本 |
| ② `scripts/zh-diag.sh#L242` | scripts/ | bash 诊断脚本 |

**教训**：Bug-037——诊断脚本 `zh-diag.sh` 只写了 `--batch-size 2048`（逻辑批次），缺少 `-ub 2048`（物理批次），导致诊断脚本启动的 embedding 服务参数不完整，难以复现问题。

**验证方式**：修改 embedding 启动参数后，全文搜索 `-b` 和 `-ub` 和 `--batch-size` 确保所有出现点一致。

## 拷贝组 6：认证账号

| 拷贝点 | 位置 | 形态 |
|--------|------|------|
| ① 环境变量 | `.env` 中的 `AUTH_ACCOUNTS_JSON` | JSON 字符串 |
| ② 代码常量 | `AppConfig` 绑定 | C# 对象 |
| ③ E2E 测试凭证 | `agent1-web/e2e/` + `e2e-real/` | Playwright 配置 |

**教训**：修改测试账号密码后，E2E 测试因凭证不匹配全部失败（登录 401）。

**验证方式**：修改认证配置后，运行 E2E 测试确认登录流程正常。

## 拷贝组 7：API 端点路由

| 拷贝点 | 位置 | 形态 |
|--------|------|------|
| ① Controller 路由 | `Agent1.Api/Controllers/` | `[Route]` / `[HttpGet]` 特性 |
| ② 前端 API 调用 | `agent1-web/src/api/` | axios 请求 URL |
| ③ MSW Mock handler | `agent1-web/src/mocks/` | handler URL 匹配 |
| ④ Benchmark 客户端 | `Benchmark/Program.cs` | HTTP 请求 URL |

**教训**：修改 API 路由后，前端在 Mock 模式下正常（MSW handler 匹配的是旧路由），切真实 API 后 404。

**验证方式**：修改 API 路由后：
1. 全文搜索旧路由字符串
2. 运行 Benchmark 确认 HTTP 200
3. 运行 e2e-real 确认真实 API 可达
