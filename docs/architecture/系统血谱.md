## 零、核心概念速览

> **设计意图**：在读到任何架构图之前，你必须已经认识图中出现的每一个符号。这是宪法第一条"先概念、后全景"的落地——图中出现"API""RAG""图谱"等词之前，先告诉你它们是什么。

### 系统由三个"器官"组成

> 类比：一个饭店。前端是前台，API是传菜口，核心引擎是厨房。

| 器官 | 一句话职责 | 饭店类比 | 技术形态 |
|------|-----------|----------|----------|
| **agent1-web** | 展示界面、收集用户输入、发送HTTP请求 | **饭店前台**：顾客在这看菜单、点菜 | Vue 3 + TypeScript，Vite 开发服务器（端口 5173） |
| **Agent1.Api** | 接收HTTP请求、验证身份与权限、限流保护、转发给核心引擎 | **饭店传菜口**：检查点菜单是否有效，递进厨房 | ASP.NET Core Web API（端口 5001），15 个 Controller，JWT 认证 |
| **Agent1** | AI推理、知识检索、合规判断、最终回答生成 | **饭店厨房**：真正做菜的地方——翻菜谱、查配方、炒菜 | .NET 控制台/类库，Semantic Kernel 编排 LLM 推理 |

### 数据放在三个"存储"里

| 存储 | 一句话职责 | 饭店类比 | 存什么 |
|------|-----------|----------|--------|
| **PostgreSQL** | 主数据库，存所有需要持久化的数据 | **饭店大冰柜**：容量大、什么都能往里放 | 知识文档元数据、分块向量、知识图谱（五张表）、审计日志 |
| **SQLite** | PG 不可用时的备胎，单文件、永远在线 | **厨师口袋里的配方卡**：随身带、不依赖冰柜、永远可用 | 化学品基础数据（35 物质 / 21 安全距离 / 20 配伍禁忌 / 7 法规版本） |
| **进程内存** | 启动时加载热数据，毫秒级访问 | **厨师的脑子**：最快，但也最"小"，重启就忘 | BM25/向量检索索引、知识图谱缓存、配置对象 |

### 一条请求的完整旅程

> 类比：顾客点了一道"苯"的合规检查 → 前台（前端）把单子递给传菜口（API）→ 传菜口检查身份后递进厨房（核心引擎）→ 厨师翻菜谱（RAG 搜索知识库）、查配方卡（SQLite）、参考大冰柜（PG 图谱）→ 做好菜先尝一口（出口闸门验证）→ 经传菜口递回前台。

```
[用户浏览器] ──HTTP请求──▶ [Agent1.Api] ──服务调用──▶ [Agent1 核心引擎]
      ▲                          │                           │
      │                   检查：身份/限流/权限          推理线路：
      │                          │                    IntentRouter 路由
      │                          ▼                    → LLM 推理（大模型思考）
      └──── JSON 响应 ──────── 返回 ◀────────────── → 工具调用（RAG检索/数据库查询）
                                                        → 出口闸门（验证+清洗）
                                                        → 回答返回
```

### 请求主干道（一句话版）

```
用户输入 → 前端发请求 → API 中间件检查身份 → Controller → AgentDialog
→ IntentRouter 判断意图 → LLM 推理 + 工具调用(RAG/数据库/字典)
→ 出口闸门验证 → 回答返回 → 审计记录
```

两条路径的区别只在末端验证策略，主干完全一致：
- **API 路径**（Web 页面）：合规检查经过"解耦管线"（FC 违约闸门 → FactExtractor → OutputSanitizer → FactAssembler → ResponseMerger），外加法规验证（ConclusionVerifier）
- **CLI 路径**（控制台）：6 步线性流水线（预处理 → 路由 → 上下文 → 执行 → 保存 → 格式化），输出端经过 OutputValidator 库白名单

## 二、L0 大动脉（数据端到端链路）

> **设计意图**：每条动脉 = 一个完整的数据旅程。先告诉你"正常态是什么样"，再画链路图，最后标注关键分岔点。
> 异常处理（降级、重试、Bug）不写在主链路中——它们属于病灶登记表。

---

### 动脉 A：知识文档 → RAG 检索

**正常态**：系统启动时，扫描知识库目录下的所有文档 → 提取文本 → 清洗 → 切成小块 → 每块转成向量 → 存入 PostgreSQL → 构建内存检索索引 → 等待用户提问时搜索。

> 类比：饭店开门前，厨师把所有菜谱（PDF/Word/TXT）翻一遍 → 把每道菜的做法摘出来 → 切成小卡片 → 每张卡片贴上编号（向量）→ 放进大冰柜 + 记在脑子里 → 客人点菜时快速翻出相关卡片。

```
knowledgebase/ 五子目录（国标 / 化工专业条例 / 园区规则 / 历史案例 / H166）
    │
    ├── 入口①：全量加载（启动时）
    └── 入口②：增量加载（运行中，POST /api/knowledgebase/incremental-load）
    │
    ▼
ProcessSingleFileAsync（统一单文件管线，按扩展名分派）
    │
    ├── PDF → PdfExtractor 提取文本
    │   └── 文本层过薄时 → PdfOcrService 视觉 OCR（调用 :8083 多模态模型看图识字）
    │       → NormalizeOcrText 源头归一化（清理 OCR 产生的乱码字符）
    ├── DOC/DOCX → DocExtractor
    └── TXT → 直接读取
    │
    ▼
TextCleaner 清洗（把零散的换行重组成完整段落）
    │
    ▼
SemanticChunker 切块（条例按条款切、长段落强制切）
    │
    ▼
GarbledTextDetector 乱码闸门（三规则确定性拒收——乱码块不准入库）
    │
    ▼
存入 PostgreSQL
  ├── knowledge_documents 表（文档元数据，source_path 唯一）
  └── knowledge_chunks 表（分块文本 + 向量，外键关联文档）
    │
    ▼
向量嵌入：调用 :8081 nomic-embed 服务，把文本块转成数字向量
  （启动参数 -b 2048 -ub 2048：模型一次最多处理 2048 token 的文本）
    │
    ▼
HybridKnowledgeBaseService 构建内存索引（BM25 关键词索引 + 向量相似度索引）
    │
    ▼
消费者：ChemicalComplianceTools 的 RAG 工具 / KnowledgeBaseController 检索接口
```

**关键分岔点**：
- **全量 vs 增量**：启动时如果库中已有分块（count > 0），走快速模式跳过文件扫描直接充血；否则走全量管道。增量通过 file_tracker.json 记录每个文件的上次修改时间，只处理变更文件。
- **路径解析**：`ResolveKnowledgeBasePath` 多锚点探测——先找环境变量，再找运行目录，最后找上级目录，确保不同启动位置都能找到知识库。
- **⚠️ 存量病灶**：快速模式使早期入库的乱码块常驻（约 60 条），闸门只拦增量不拦存量。详见 `病灶登记表.md` 第 1 条。

### 动脉 B：迁移脚本 → 知识图谱（结构化主链路）

**正常态**：部署时执行 SQL 迁移脚本建表并写入化学品知识数据 → 启动时从 PG 全量加载到内存 → 构建图结构 → 等待查询。

> 类比：饭店装修时，先把"哪些食材不能一起用""炉灶离水池至少多远"这些规则刻在冰柜门上的铜牌上（SQL 迁移）→ 厨师上班时把这些规则背下来（加载到内存）→ 做菜时随时查阅。

```
db/migrations/002_chemical_knowledge_graph.sql（数据写死在 INSERT 里）
    │ psql 执行（部署期，一次性）
    ▼
PostgreSQL：图谱五张表
  ├── substances          化学品基础信息
  ├── aliases             别名映射（"苯"也叫"纯苯""安息油"）
  ├──禁忌边               配伍禁忌关系（哪两种物质不能放一起）
  ├── safety_distances    安全距离要求
  └── regulation_versions 法规版本信息
    │ EnsureInitialized → LoadFromDatabase 全量 SELECT
    │ ⚠️ PG 不可用 → 直接报错（无内置种子兜底——因为这是"官方铜牌"，不能乱编）
    ▼
内存图 ChemicalKnowledgeGraph
    ▼
门面 ChemicalSubstanceDatabase（81 行纯转发，统一对外接口）
    ▼
消费者（6 个）：
  ChemicalComplianceTools / OutputSanitizer（法规版本检索） / EvalEngine /
  ReflectionVerifier / EmergencyResponseService / KnowledgeGraphService
```

**关键分岔点**：
- **PG 必须可用**：图谱没有 SQLite 兜底。PG 连不上 → 系统启动失败。这是有意设计——图谱的数据必须在"官方铜牌"上，不能从配方卡（SQLite）临时编。
- **ChemicalSubstanceDatabase 命名陷阱**：名为"Database"实为 PG 门面（纯转发），不是独立数据库。与动脉 C 的 ChemicalDatabaseService（SQLite）是两个完全不同的东西。

### 动脉 C：C# 种子代码 → SQLite 兜底血库

**正常态**：首次启动时，C# 代码中的种子方法在 SQLite 文件中建表并写入化学品基础数据 → 后续启动发现数据已存在则跳过 → 内存常驻等待查询。

> 类比：厨师口袋里永远放着一沓手写的配方卡（SQLite 文件）。第一次上班时自己写好（种子代码建表写数据），以后直接掏出来看。

```
db/chemical_substances_v2.sql（仅表结构 + 视图，无数据）
  +
C# 四个 Seed 方法（35 物质 / 21 距离 / 20 配伍 / 7 法规版本）
    │ ChemicalDatabaseService.InitializeAsync
    │ 整段 ExecuteNonQuery（禁止 Split(';')——分号分割会破坏 SQL 语句完整性）
    │ _initialized 仅成功后置位，失败下次启动重试
    ▼
SQLite：Data/chemical_substances.db（单文件，不依赖 PG）
    ▼
消费者：ChemicalComplianceTools 三级瀑布的 Level 1
```

**关键分岔点**：
- **只在空库时写种子**：`COUNT(*) == 0` 才写入。已存在的 SQLite 库补充新数据需要删库重建。
- **整段执行不拆分**：SQL 脚本含多语句（CREATE TABLE + INSERT），必须整段传给 SQLite 引擎执行。若用 `Split(';')` 拆分会导致语句截断。

appsettings.json（非敏感信息：端口、路径、模型参数）

Config/AppConfig.cs（类型安全配置对象，全系统唯一配置入口）

## 三、L1 静脉（模块级关键保护机制）

> **设计意图**：静脉不是数据主干道，而是"保护性机制"——它们确保数据在流动过程中不丢失、不错乱、不过载。

---

### 静脉 1：结构化查询三级降级瀑布

**正常态**：用户问"苯的安全距离是多少" → 先查 SQLite（字段最全）→ 没找到查 PG 图谱 → 还没有用硬编码字典 → 都没有返回兜底话术"暂无数据"。

> 类比：厨师接到"苯的安全距离"问题，先掏出配方卡（SQLite）查——配方卡上记得最全。找不到？去大冰柜（PG）翻官方铜牌。还找不到？翻口袋里的手写小便签（硬编码字典）。都没有？老实告诉客人"这个我不确定"——不能说瞎话。

```
查询请求（如"苯的安全距离"）
    │
    ▼
Level 1  SQLite 兜底库（_chemDb）         ← 动脉 C 供血
         [命中标记：DATABASE_HIT]
         字段最全（含 clause 条款原文）
    │ 未命中
    ▼
Level 2  内存知识图谱（ChemicalSubstanceDatabase） ← 动脉 B 供血
         [命中标记：DATABASE_HIT]
         ⚠️ 名称为 Database 实为 PG 门面
    │ 未命中
    ▼
Level 3  硬编码字典（ChemicalComplianceTools 内部常量）
         [命中标记：DICTIONARY_HIT]
         质量降级——只含基础字段，无条款原文
    │ 未命中
    ▼
兜底     返回"暂无数据"话术
         质量规则 R001 禁止将此结果写入缓存
```

**⚠️ 反直觉**：SQLite（备胎）排 Level 1，PG 图谱（主库）排 Level 2。原因：SQLite 种子数据字段更全（含 clause 条款原文），PG 图谱字段较精简。

---

### 静脉 2：出口双通道闸门（回答离开系统前的最后血管）

**正常态**：LLM 生成原始回答 → 第一道闸：检查大模型是否按规矩调用了工具（FC 违约检查）→ 第二道闸：从工具返回结果中提取确定性事实（不走 LLM，防止幻觉）→ 第三道闸：用白名单清洗输出内容 → 合并成最终回答 → API 路径额外经过法规验证。

> 类比：厨师做完菜，先检查有没有偷工减料（FC 违约闸门——大模型必须调用了工具才算合格，没调用工具=没查菜谱直接瞎编）→ 从菜谱卡片上摘出确切信息（不走厨师发挥）→ 对照白名单检查有没有用错料（OutputSanitizer）→ 拼成最终成品 → 如果是正式上菜（API 路径），主管再尝一口确认（ConclusionVerifier 法规验证）。

```
LLM 原始输出
    │
    ▼
① FC（Function Calling，大模型调用工具的能力）=Required 违约闸门
    toolCalls == 0（大模型没有调用任何工具）？
    → 丢弃 LLM 输出，走 FactAssembler.BuildNoResult() 生成"无法确定"回答
    ⚠️ 耦合声明：此检查依赖 FC=Required 契约。如果未来改为 Auto/None 模式，必须同步移除此闸门
    │
    ▼
② FactExtractor 事实提取（从工具返回的数据库结果中摘出关键字段）
    │
    ▼
③ OutputSanitizer 动态白名单清洗（当次查询返回的合法值才放行，其余标记为"待核实"）
    │
    ▼
④ FactAssembler 确定性事实渲染（不用 LLM 二次加工——防止大模型在事实基础上添油加醋）
    │
    ▼
⑤ ResponseMerger 合并多工具结果
    │
    ├── [API 路径] → ConclusionVerifier.VerifyAsync 法规版本验证
    └── [CLI 路径] → OutputValidator.EnforceLibraryWhitelist 库白名单
                    （动脉B ∪ 动脉C ∪ 硬编码字典 三源并集）
```

### 静脉 3：记忆缓存旁路（绕过 LLM 的短路血管）

**正常态**：工具查询结果写入缓存 → 下次相同问题直接读缓存（短路，不走 LLM）→ 低质量缓存（如兜底话术）不得直接作答。

> 类比：厨师做完一道菜，把结果记在脑子里。下次同样的菜直接端出去——不用重新做。但如果上次做的是"不确定"（兜底话术），不记——因为这是失败记录，不能当答案重复用。

```
工具结果
    │
    ▼
写入检查：IsFallbackContent（R001 正则匹配 + ToolQualityContext）
    │ 兜底话术（"暂无数据"等）→ 拒绝写入
    │ 正常结果 → 写入缓存
    ▼
读取：TryAnswerFromMemory
    │ R002 置信度门禁 → 低质量缓存不得直接作答
    ▼
保鲜：GetEffectiveTtl 分级 TTL（过期时间）
    RAG/数据库命中 → 10 分钟
    字典命中       → 5 分钟
    兜底结果       → 0（不缓存）
预热：WarmupFromEvalSet ← 动脉 D 评测集（启动时预加载高频问题缓存）
```

### 静脉 4：推理防御链

**正常态**：调用方显式声明本次推理的 FC 策略 → LLM 按策略执行推理（流式输出 + 死循环检测）→ 评测路径额外裁剪工具集以控制变量。

> 类比：厨师接到不同任务用不同规矩——正式上菜（默认）必须查配方（FC=Required）；考试时（评测）可以自由发挥（FC=Auto）；内部尝试（HyDE/反思）禁止查配方（FC=None），防止自己问自己陷入死循环。

```
FC 策略由调用方显式声明（不是全局默认，而是每次调用带参数）：
  默认 FC=Required   → 主链路：大模型必须调用工具
  评测 FC=Auto       → 评测：允许大模型自主决定是否调工具
  HyDE/反思 FC=None  → 内部生成：禁止调工具（防止递归调自己 → 死循环）
    │
    ▼
LLM 推理（流式输出）
    │ 三维死循环检测：复读同一句话 / 符号喷射 / 长度超限
    ▼
工具裁剪（仅评测路径）：
  EvalEngine 按意图分配工具白名单
  info_query → 6 个工具 / compliance_judgment → 5 个工具
  InvokeEvalWithToolsAsync 临时 Kernel 只注册白名单子集
  日志标记「工具裁剪: n/9」（全量 9 个工具，本次只注册 n 个）
```

### 静脉 5：API 层长任务血管

**正常态**：用户触发耗时扫描 → API 立即返回 202（已接受）+ scanId → 后台异步执行 → 前端每 2 秒轮询状态 → 完成后拉取结果。

> 类比：客人点了"全场巡检"（耗时大菜）→ 传菜口不干等着，先回"知道了，单号 42"→ 厨房慢慢做 → 前台隔一会问"42 号好了没？"→ 好了就端走。

```
POST /api/dashboard/scan
    │ 已在跑？→ 返回 HTTP 409（Conflict）
    │ 未在跑 → Task.Run 后台启动
    ▼
立即返回 HTTP 202 + scanId（Accepted，已接受但不保证完成）
    │
后台执行扫描...
    │ ScanProgressService 单例更新进度快照
    ▼
GET /api/dashboard/scan/status
    │ 前端每 2 秒轮询一次
    ▼
running=false → 前端拉取最终结果
```

## 四、检测与辅助系统（非血管——只抽血化验，不参与供血）

> 判定标准：参与运行时数据流的是**器官**（入 L0/L1）；只消费生产代码/API/数据做验证的是**检测设备**（登记于此）；与运行时无关的是**死组织**（见第五节）。

| 检测设备 | 接入点（抽谁的血） | 变更联动规则 |
|---------|-------------------|-------------|
| `DriftMonitor` 认知漂移监测（锚点注册表 + 测量链路 + 探针调度器） | 消费 `drift_anchors`（004 建表+50条种子）、`drift_probes` + `drift_details`（005 建表）、`drift_probe_templates`（006 建表+23 条黄金问题种子，覆盖 4 大动脉+5 静脉+约束）；锚点源=本图+配置+代码事实；测量链路=抽取断言→比对锚点→加权漂移率 D=Σ(sev·err)/Σsev；探针链路=DriftProbeScheduler（后台服务，60min 轮询/每轮 5 条/失败退避）问被测 LLM→BuildProbeClaims 强制断言（答错与未作答都计漂移，不留盲区）→落库（session="probe"，幂等覆盖）；API：POST /api/drift/measure、GET /api/drift/current+trend+anchors/stats、GET /api/drift/probes、POST /api/drift/probes/{key}/answer、POST /api/drift/probes/run | 血谱校准（本图更新）→ 锚点版本递增 + 新增/修正锚点（Upsert）；敏感值禁止落库；改锚点 canonical_value 需同步核对强标记可证伪性；探针模板 anchor_key 必须引用存在的锚点键名（006 种子与 004 锚点同批校准，改锚点键名需同步改探针） |
| `Agent1.Tests/`（xUnit，1500+ 条） | 直接引用 Agent1 + Agent1.Api；`Stubs/` 四个桩仿真动脉 B/存储 | 任何 L2/L3 契约变更必查对应测试；**StubChemicalKnowledgeGraph 在同源拷贝登记表内** |
| `ArchitectureTest/`（架构收敛门禁） | 引用 Agent1 程序集，7 项检查（收敛/IntentRouter 纯分类/统一分发/线性管线/无硬编码等） | 删改 Agent1 文件结构 / 管线编排时必跑；重命名文件会击穿它 |
| `Benchmark/`（性能基准） | 纯 HTTP 客户端打 API（:5000），登录 → 压测健康/认证/业务端点 | 只耦合 API 契约（路由/登录字段）；改 AuthController 响应结构会击穿它 |
| `agent1-web/e2e/` + `e2e-real/`（Playwright） | e2e 打 MSW Mock；e2e-real 经 SSH 隧道打真实 API | 前后端字段契约变更时联动 MSW mock |
| `scripts/run_eval_pipeline.ps1` | 驱动 EvalEngine 吃动脉 D 评测集 | 评测集格式升级时联动（#7 教训的第三个消费者） |
