### Bug-036：OCR 全文入库分块退化 + 目录点线误杀（🔴P0，`edf34051`）

| 维度 | 内容 |
|------|------|
| **① 现象与根因** | **现象**：扫描件 GPU OCR 产出 2 万字全文，日志三行自相矛盾——`OCR 20/20页成功 20405字(good)` + `乱码块拒收 chunk0` + `28页→1块`，实际入库 **0 个可检索分块**。**根因（两处叠加，单修任一处都不够）**：(a) `SemanticChunker` 的 switch 缺 `化工专业条例` 分支 → 落 default `ChunkByParagraph`（按 `\n\n` 分段），但 `TextCleaner` L145 用**单 `\n`** 重组全文，产物中根本没有 `\n\n` → 整篇 2 万字变成一个"段落"，且旧 `ChunkByParagraph` 对超长单段无强切 → 1 块；(b) `GarbledTextDetector` 规则①（同字符连续≥4 拒收）把 OCR 如实转写的目录点线「第一章……1」误判为乱码 → 仅有的 1 块也被拒 → 入库 0 |
| **② 设计思路** | 三件套且**不放松乱码防线**：(a) `化工专业条例`→`ChunkByClause`（本质是 GB 系列标准，含"4.1.2"式条款号，条款正则+超长强切双保险）；(b) `ChunkByParagraph` 增加 while 超长强切（优先在 `\n`/`。`/`；` 断，边界≥MaxChunkSize/2 才采用）；(c) 在 **OCR 源头**新增 `NormalizeOcrText` 归一化点线/表格线/横线。关键决策：不改 TextCleaner（影响所有文档类型，回归面不可控）；不放松检测器规则（会削弱对"书书书书"类真乱码的防线） |
| **③ 代码位置** | [SemanticChunker.cs](file:///d:/桌面/agent/项目/Agent1/Agent1/Services/Knowledge/SemanticChunker.cs)（+40行：switch 新增分支 + ChunkByParagraph while 强切）、[PdfOcrService.cs](file:///d:/桌面/agent/项目/Agent1/Agent1/Services/Knowledge/PdfOcrService.cs)（+22行：`NormalizeOcrText` 点线串→"…"、表格线→" --- "）；测试把断言退化行为的旧用例 `Chunk_SingleLargeParagraph_NotSplitWithoutBreaks` 改名重写为 `_ForceSplitBySize` |
| **④ 验证** | 远程重跑同一文件：`28页 → 80块 (质量:good)`（修复前 1 块），零 `'…'` 拒收；本地筛选测试 33/33 通过（含点线放行/表格线放行/"书书书书"真乱码仍拦截三测）；07-30 远程定向回归 KnowledgePipelineTests 全绿 |
| **⑤ 边界与风险** | 强切边界要求 ≥MaxChunkSize/2 才采用——极端无标点长文本会切在任意位置损伤语义；`NormalizeOcrText` 白名单式归一化只覆盖已见过的三类模式（点线/表格线/横线），OCR 新数据分布（如公式、竖排表格）可能再次触发误杀；**残留风险**：`TextCleaner` 上下游 `\n\n` 隐式契约断裂仍在（血谱 W25 已登记），未来新增依赖 `\n\n` 的切分器会再次踩坑 |
| **⑥ 教训与预防** | ① 管线环节间的格式契约必须显式化——各环节单测都"正确"，断裂只在集成链路暴露；② **断言缺陷行为的测试是负资产**（"这是当前实现限制"注释把 Bug 固化成规格）；③ 确定性拒收规则必须针对新数据源重新校准；④ 验收标准落在最末端（分块数+检索命中），不被上游成功日志麻痹 |

**设计理据三问检验**：为什么不新写切分器而走已有 ChunkByClause？——追问后发现`化工专业条例`本质是 GB 系列标准（含 "4.1.2" 条款号），与"国标"同构，**复用现有设施而非新写切分器**（对照 Bug-033 案例中 E1 新写正则的反面教材，这次做对了）。

**根治 vs 症状？** → **根治**。追问深度达 L4（1块→段落切分→单换行重组消灭\n\n→乱码规则误杀），两处独立根因都被定位并修复。唯一妥协是 `TextCleaner` 隐式契约未显式化，但已登记血谱、有意识保留（改动面失控风险 > 收益）——属**知情的技术债**，非遗漏。

### Bug-037：nomic-embed 物理批次 512 上限（🟡P1，`0446206f`）

| 维度 | 内容 |
|------|------|
| **① 现象与根因** | **现象**：Bug-036 修好后重灌，80 块中长条款块反复 `input (527/620 tokens) is too large... batch size: 512` 500 报错 → 向量静默缺失、降级 BM25-only。**根因**：nomic-embed 是非因果注意力模型，llama.cpp 要求嵌入整段进单个**物理批次**（`-ub`，默认 512）；旧管线从未产出过 >512 token 的块所以潜伏至今——**Bug-036 的条款聚合长块（520~620 token）首次击穿上限**。关键机制：`-b`（逻辑批次）单调大**无效**，必须同时调 `-ub`（物理批次） |

| **③ 代码位置** | **非代码修复，是基础设施配置**：[start_services.sh](file:///d:/桌面/agent/项目/Agent1/start_services.sh#L68-L70)（`-b 2048 -ub 2048` + 注释说明为什么）、`scripts/zh-diag.sh` L242（同批同步——此前它只写 `--batch-size 1024` 缺 `-ub`，实际无效） |
| **④ 验证** | 重启 8081 后 802 token 长文本返回 768 维向量（修复前必 500）；后续批次零 `向量请求失败`；07-30 远程 E2E 中 Hybrid-RRF 检索 5 条结果全部带向量得分 |
| **⑤ 边界与风险** | **隐性边界：2048 是 nomic 的上下文极限**。若未来切分策略再变（如整章聚合产出 >2048 token 块），会再次击穿且无参数可调，只能回到代码侧截断——这个边界当前没有任何监控或断言守着。同源拷贝风险已闭环：血谱同源拷贝登记表第 5 行已登记两处必须同调（已核实 start_services.sh L68-70 确带参数 ✅） |

**根治 vs 症状？** → **根治（配置层），但 2048 边界是一颗静默的种子**。建议在 SemanticChunker 加块长上限断言（>1800 token 告警）。根因是对 llama.cpp 物理批次机制的认知补齐，非临时调参撞运气（追问 L2 明确区分了物理 vs 逻辑批次）。属架构边界规则允许的「基础设施前置依赖声明」，未触碰红线。
