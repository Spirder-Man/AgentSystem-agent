## 二、前因分析

### 2.1 设计初衷与架构定位（按问题分组）

**A 组：确定性兜底层（#1 / #3）**

- 设计初衷：化工安全铁律"确定性优先"——SQLite 兜底库是无 PostgreSQL 环境下的离线确定性数据源，保证化学品属性/安全距离/存储兼容三类查询**永远不依赖 LLM 概率输出**。
- 架构定位：`ChemicalDatabaseService` 位于工具层之下，是 `DeterministicRuleEngine` 与 `ChemicalComplianceTools` 的共同数据后端；`ChemicalKnowledgeGraph`（内存图）与其构成双源互备。
- 出问题的环节：#1 出在"schema 执行"这一最底层步骤——`SplitSqlStatements` 用 `sql.Split(';')` 拆分脚本，而 `db/chemical_substances_v2.sql` L109 视图定义中的 `GROUP_CONCAT(..., '; ')` 字符串字面量内含分号，语句被拦腰截断产生孤立引号；#3 出在"数据覆盖面"——种子清单按早期评测集编写，未随评测集 v1.1 新增设施对（氢气长管拖车/氨气储罐/气柜）同步扩充。

**B 组：输出可信层（#2）**

- 设计初衷：双通道架构中 `OutputValidator` 是输出末端最后一道确定性闸门。
- 出问题的环节：修复前校验采用 `String.Contains` 宽松包含匹配，对"主编号在库、子编号编造"（如 GB 30000.x 超界）的变体无硬校验，LLM 训练记忆回填的编号得以漏网。

**C 组：API 交互层（#4 / #6）**

- #4 设计初衷：Dashboard 扫描最初资产数少、单次耗时秒级，同步返回是当时最简单正确的实现；随资产扫描接入 LLM 推理链路（单资产 ~65s），同步模型被数据规模击穿。
- #6 设计初衷：告警通道采用"环境变量缺失→功能静默关闭"的宽容降级，避免开发环境因无邮箱配置而启动失败；代价是生产环境缺配时只有一行启动 WRN，极易被忽略。

**D 组：数据质量层（#5）**

- 设计初衷：知识库入库管道（`ChemicalRAG.LoadKnowledgeBaseAsync`）此前只做切块与嵌入，默认"上游 PDF 提取器输出可信"。
- 出问题的环节：扫描版 PDF 经文本提取产生 CID 映射失败乱码（"书书书!!!!"是典型的字体子集 CID 乱码指纹），管道无守门员，乱码块与正常块同权入库。

**E 组：性能/配置层（#7 / #8）**

- #7：评测集从纯数组升级为 v1.1 wrapper（`{ name, version, test_cases: [...] }`）时，`EvalEngine` 加载器同步升级，但 `ResponseCacheService.WarmupFromEvalSet` 这条**旁路消费者**被遗漏——同一份数据的两个消费者反序列化逻辑未收敛。
- #8：`QualityRules.Load()` 按 `AppContext.BaseDirectory` 查找，但 csproj 缺 `<Content CopyToOutputDirectory>` 项，源文件存在却不随构建分发——"配置文件存在性"与"配置文件可达性"是两回事。

**F 组：代码卫生 / FC 就绪（#9 / #10）**

- #9：`LastToolResults/LastToolPlan` 已标记 `[Obsolete]` 引导外部迁移到 `CliExecutionResult`，但 `AgentDialog` 内部 17 处自引用未同步改造，Obsolete 属性自己警告自己。
- #10：FC 就绪性自检设计为 5 条诊断用例全触发即满分；GetCurrentTime 是其中唯一的通用（非领域）工具。

### 3.2 连锁问题分析

1. **#1 → #3 链**：兜底库不可用时安全距离查询落到硬编码字典（覆盖面更小）→ 未命中率进一步升高 → LLM 自行推断 → 与 #2 叠加产生"编造距离值 + 编造法规出处"的复合幻觉——**三个 P1 构成一条幻觉放大链**。

## 五、心理模型分析（设计理据追问法）

对四个最具设计张力的问题，按"设计意图 → 为何是当前方案 → 边界条件"三问展开：

### 5.1 #1 SplitSqlStatements：为什么会存在一个天真拆分器？

- **设计意图是什么**：让 SQLite 能执行多语句 schema 脚本。方法注释声称"SQLite 不支持批量执行"，即作者认为必须先拆分再逐条执行。
- **为什么选当前方案**：作者对 Microsoft.Data.Sqlite 能力的认知错误——`ExecuteNonQuery` 原生支持多语句命令文本，拆分器解决的是一个**不存在的问题**。备选方案（引号感知状态机拆分器）同样被否决：既然限制不存在，任何拆分器都是多余复杂度。
- **边界条件是什么**：`Split(';')` 仅在"脚本中所有分号都是语句分隔符"时正确——schema 引入含 `'; '` 字面量的视图定义（GROUP_CONCAT 分隔符）当天即越界。**教训固化**：写下"X 不支持 Y"注释前必须查证官方文档，错误的能力认知注释会把临时拐杖固化成"必要设计"（Bug-035 教训②）。

### 5.2 #2 白名单硬校验：为什么用"替换标注"而不是"直接删除"或"概率打分"？

- **设计意图**：阻断库外法规号流向用户，同时不破坏输出可读性。
- **为什么选当前方案**：删除会造成语句残缺且用户无感知（静默篡改输出比标注更危险）；概率打分违反项目确定性铁律（用户确定性偏好：只接受 100% 可验证路径）。纯正则 + 集合查找的"替换为【待核实】"是唯一同时满足确定性、可见性、可读性的方案。
- **边界条件**：白名单必须含数据库源全集（吸取 Bug-027 教训：C# 硬编码字典源的编号不是幻觉），否则硬校验会误杀真编号——白名单数据源 = regulation_versions 种子 ∪ 知识图谱法规版本 ∪ 硬编码字典源三者并集，缺一即产生误杀。

### 5.3 #4 同步扫描：当初为什么不直接做成异步？

- **设计意图**：扫描接口初期资产少、秒级返回，同步是当时复杂度最低的正确方案（YAGNI 合理应用）。
- **为什么当时排除后台任务**：引入任务状态管理、并发控制、进度存储对秒级操作是过度设计。
- **边界条件**：同步模型的隐含前提是"单次耗时 ≪ HTTP 超时阈值"。扫描链路接入 LLM 推理（单资产 ~65s）时该前提被击穿，但**没有任何机制在前提失效时报警**——这是比"没做异步"更深的教训：隐含前提要么写成断言/告警（慢请求告警事后捕获了它，L1846），要么写进文档。修复采用 202+scanId+轮询、并发返回 409，是前提失效后的标准应对。

### 5.4 #10 GetCurrentTime：为什么"不修"反而是正确决策？

- **设计意图**：FC 就绪性自检用 5 条用例验证 FC 管线通路，GetCurrentTime 代表"通用工具"类别。
- **为什么排除"调 prompt 提升触发率"**：本系统 system prompt 高度领域化（化工合规审核），时间类闲聊意图触发率低是领域化的**预期收益副作用**；调 prompt 属概率性手段，违反确定性铁律，且可能损害主业务工具（危险类别/安全距离/存储兼容）的路由精度——为一个不参与合规结论的工具冒主链路风险，收益/风险严重倒挂。
- **边界条件**：该取舍仅在"GetCurrentTime 不参与合规结论推导"成立时有效；若未来出现依赖当前时间的合规规则（如证书有效期审核），需重新评估并将其升格为关键工具。取舍理由已按可追溯原则标注于评测报告与测试方案（#10 修复内容）。
