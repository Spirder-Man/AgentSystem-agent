# 工程质量防御体系 Skill

> 适用场景：当项目从功能开发阶段进入生产级质量保障阶段时，使用本体系系统性构建防御能力。  
> 核心理念：**不依赖人的记忆和谨慎，而是用自动化门禁、故障注入、数据验证编织一张让 Bug 无法存活的铁网。**

---

## 一、整体防御蓝图

```
                          ┌─────────────────┐
                          │   生产环境       │
                          │   混沌工程       │
                          │   主动攻击验证   │
                          └────────┬────────┘
                                   │
                          ┌────────▼────────┐
                          │   测试环境       │
                          │   韧性测试       │
                          │   故障注入验证   │
                          └────────┬────────┘
                                   │
                          ┌────────▼────────┐
                          │   CI/CD 流水线   │
                          │   架构收敛测试   │
                          │   单元/集成测试   │
                          │   安全扫描       │
                          └────────┬────────┘
                                   │
                          ┌────────▼────────┐
                          │   开发环境       │
                          │   本地 Git Hook  │
                          │   代码规范检查   │
                          └─────────────────┘
```

**核心原则**：**每一层都必须是硬卡口，不通过就永远停在当前层，不能进入下一层。**

## 二、第一道防线：架构收敛测试

### 2.1 核心思想
**把你的设计意图和架构约束写成自动化测试，让 CI 每次提交都替你验证。**  
人类会疲劳、会遗忘、会妥协，但测试永远勤勉。

### 2.2 何时使用
- 定义了模块间调用规则（如“所有 CLI 入口必须通过 Dispatcher”）
- 强制了横切关注点（如“所有模块必须注入安全检测”）
- 规定了输出契约（如“所有返回必须是 CliExecutionResult”）
- 约束了编码规范（如“禁止 Console.Write，必须用 Serilog”）

### 2.3 实践清单

| 检查类型           | 验证内容                                                    | 实现方式                     |
| ------------------ | ----------------------------------------------------------- | ---------------------------- |
| **接口实现完整性** | 所有 `IInferenceModule` 实现都有 `RunWithResultAsync`       | 反射扫描程序集，断言方法存在 |
| **依赖注入强制**   | 所有模块构造函数必须有 `ISafetyGuardService` 参数           | 反射分析构造函数参数         |
| **调用链路约束**   | 所有 CLI Command 必须调用 `_dispatcher` 而非直接 `new` 模块 | Roslyn 语法树分析或约定检查  |
| **输出契约统一**   | 所有公开方法返回 `Task<CliExecutionResult>`                 | 反射检查返回类型             |
| **枚举完整性**     | `ModuleType` 枚举覆盖所有 `ModuleFactory` 的 case 分支      | 计数比对                     |
| **编码规范**       | 禁止 `Console.Write`、`async void`、空 catch                | Roslyn Analyzer 或正则扫描   |

### 2.4 落地示例
```csharp
[Fact]
public void 所有IInferenceModule实现_必须注入_ISafetyGuardService()
{
    var modules = typeof(IInferenceModule).Assembly.GetTypes()
        .Where(t => typeof(IInferenceModule).IsAssignableFrom(t) && !t.IsAbstract);
    
    foreach (var type in modules)
    {
        var hasSafetyGuard = type.GetConstructors()
            .SelectMany(c => c.GetParameters())
            .Any(p => p.ParameterType == typeof(ISafetyGuardService));
        
        Assert.True(hasSafetyGuard, $"{type.Name} 缺少 ISafetyGuardService 注入");
    }
}
```

### 2.5 常见陷阱
- **测试项目未独立**：架构测试应与单元测试分项目，可独立运行、快速反馈。
- **规则太宽松**：用 `Any` 而不是 `All` 会漏掉部分违反者。
- **只增不删**：新规则加入后，旧代码可能大量违反，需有修复计划或 `[Skip]` 过渡期。

## 三、第二道防线：韧性测试（故障注入）

### 3.1 核心思想
**不要祈祷外部依赖不出问题，主动让它坏掉，看你的系统能否优雅降级。**

### 3.2 何时使用
- 有外部服务调用（LLM、数据库、API）
- 有缓存/熔断/重试/降级逻辑
- 需要验证“系统挂了会怎样，能不能自己恢复”

### 3.3 测试清单

| 故障类型             | 注入方式                               | 验证目标                   |
| -------------------- | -------------------------------------- | -------------------------- |
| **外部服务宕机**     | Mock 连续抛出 `HttpRequestException`   | 熔断器打开，快速失败       |
| **外部服务超时**     | Mock 设置 `Task.Delay(超时)`           | 重试策略生效，超时后降级   |
| **数据库连接断开**   | 使用 `TestContainers` 或 Mock 断开连接 | 降级到缓存或返回友好错误   |
| **依赖返回畸形数据** | Mock 返回格式错误的 JSON               | 异常处理健壮，不崩溃       |
| **资源耗尽**         | 填满线程池或内存                       | 限流生效，核心功能不受影响 |
| **配置错误**         | 注入错误的连接字符串                   | 启动时快速失败并明确报错   |

### 3.4 落地示例（熔断器验证）
```csharp
[Fact]
public async Task 熔断器_连续三次失败后_第四次直接拒绝请求()
{
    // Arrange: 模拟 LLM 服务宕机
    var mockLlm = new Mock<ILlmService>();
    mockLlm.Setup(x => x.InvokeAsync(It.IsAny<string>()))
           .ThrowsAsync(new HttpRequestException("连接被拒"));
    
    var dialog = new AgentDialog(mockLlm.Object, /* 其他依赖 */);
    
    // Act: 连续调用 4 次
    for (int i = 0; i < 3; i++)
        await Assert.ThrowsAsync<HttpRequestException>(() => 
            dialog.ExecuteAsync("测试", session));
    
    // Assert: 第 4 次被熔断器拦截，不再去调 LLM
    await Assert.ThrowsAsync<CircuitBreakerOpenException>(() =>
        dialog.ExecuteAsync("测试", session));
}
```

### 3.5 常见陷阱
- **只测正常路径**：大多数测试默认依赖服务正常，应专门设计异常测试用例。
- **测试和生产环境不一致**：Mock 行为需贴近真实失败模式（如连接超时 vs 拒绝连接）。
- **忘记测恢复**：熔断器在冷却期后应允许试探请求，这个也要测。

## 四、第三道防线：混沌工程

### 4.1 核心思想
**韧性测试验证“已知的故障模式”，混沌工程探索“未知的风险边界”。**  
在生产或类生产环境中主动制造混乱，观察系统是否仍能维持核心能力。

### 4.2 何时使用
- 系统已通过架构测试和韧性测试
- 有完善的监控和告警体系（知道“正常”长什么样）
- 有快速回滚能力（搞坏了能一秒恢复）

### 4.3 实验类型

| 实验类型     | 具体手段                   | 化工安全 Agent 示例                   |
| ------------ | -------------------------- | ------------------------------------- |
| **网络延迟** | 注入 5000ms 延迟到 LLM API | 验证用户端体验是否可接受              |
| **依赖宕机** | 停止 llama-server 进程     | 验证是否返回“服务暂不可用”            |
| **数据损坏** | 知识库返回过期或矛盾的法规 | 验证合规结论是否会被误导              |
| **资源耗尽** | 占满 GPU 显存              | 验证 CPU 降级路径是否真的生效         |
| **时钟偏移** | 修改系统时间               | 验证 Session 过期、审计时间戳是否错乱 |
| **流量冲击** | 瞬间涌入 1000 个合规查询   | 验证限流排队是否保护核心服务          |
| **磁盘故障** | 日志目录只读               | 验证审计日志写入失败时的降级方案      |

### 4.4 执行原则
1. **先假设后实验**：明确“如果 X 坏了，系统应该 Y”。
2. **最小爆炸半径**：先在测试环境做，再生产灰度 5% 流量。
3. **自动终止**：一旦核心指标（错误率、延迟）超过阈值，自动停止实验并回滚。
4. **记录与复盘**：每次实验生成报告，发现的问题转化为韧性测试或架构约束。

### 4.5 常见陷阱
- **没有监控就混沌**：不知道正常状态，就不知道是否异常。
- **实验半径过大**：一次性关掉所有服务，而不是先关一个节点。
- **做完不管**：发现问题后不跟进修复，混沌就只是破坏。

## 五、第四道防线：可观测性验证

### 5.1 核心思想
**运维数据不是“顺便看看”，而是系统正确性的可度量证据。**  
日志、指标、追踪三者构成完整的可观测性三角形，并且它们的存在本身就需要被验证。

### 5.2 三个支柱

| 支柱           | 做什么                     | 化工安全 Agent 示例                                   |
| -------------- | -------------------------- | ----------------------------------------------------- |
| **结构化日志** | 记录带键值对的事件         | Serilog + Seq，每步耗时、TraceId、安全检测结果        |
| **指标**       | 聚合数值（计数器、仪表盘） | Prometheus 采集合规检查次数、不合规率、LLM 延迟       |
| **分布式追踪** | 串联一次请求的全链路       | OpenTelemetry，TraceId 贯穿 CLI→Dispatcher→Module→LLM |

### 5.3 可观测性的测试验证
可观测性本身需要被验证：

```csharp
[Fact]
public async Task 合规查询_必须输出完整TraceId()
{
    // 使用 Serilog TestSink 捕获日志
    var sink = new TestSink();
    var logger = new LoggerConfiguration().WriteTo.Sink(sink).CreateLogger();
    
    // 执行一次合规查询
    await agentDialog.ExecuteAsync("苯的储存条件", session);
    
    // 断言：必须有 TraceId
    var logEvents = sink.Events;
    Assert.Contains(logEvents, e => 
        e.Properties.ContainsKey("TraceId") && 
        e.MessageTemplate.Text.Contains("管道"));
}

[Fact]
public void 熔断器打开时_必须记录审计事件()
{
    // 执行熔断触发，断言 AuditService 收到了 CircuitBreakerOpened 事件
}
```

### 5.4 常见陷阱
- **日志太少**：只能看到“请求来了”和“请求走了”，中间黑盒。
- **日志太多**：存储成本爆炸，且有效信息被淹没。
- **日志无结构**：纯文本 Console.Write，无法检索聚合。
- **TraceId 丢失**：异步调用或异常路径中未传递上下文。

## 六、分层防御的 CI/CD 实现

```
┌──────────────────────────────────────────────────────────────┐
│                    CI/CD 流水线                               │
│                                                              │
│  ┌─────────┐  ┌──────────┐  ┌───────────┐  ┌────────────┐  │
│  │ 编译    │→│ 架构测试  │→│ 单元测试   │→│ 韧性测试    │  │
│  │         │  │ 8项检查   │  │ 148 pass  │  │ 熔断/降级  │  │
│  └─────────┘  └──────────┘  └───────────┘  └────────────┘  │
│                                                    │        │
│  ┌─────────┐  ┌──────────┐  ┌───────────┐        │        │
│  │ 部署    │←│ 镜像扫描  │←│ 集成测试   │←───────┘        │
│  │ 灰度    │  │ Trivy     │  │ 日志验证   │                 │
│  └─────────┘  └──────────┘  └───────────┘                 │
│       │                                                     │
│       ▼                                                     │
│  ┌────────────┐                                             │
│  │ 生产监控    │ ← 混沌工程实验（持续）                       │
│  │ 自动告警    │                                             │
│  └────────────┘                                             │
└──────────────────────────────────────────────────────────────┘
```

**每一层的失败都会阻止流水线继续**：
- 架构测试失败 → PR 不能合并
- 韧性测试失败 → 镜像不能构建
- 镜像扫描发现漏洞 → 不能部署
- 混沌实验指标异常 → 自动回滚

## 七、落地步骤清单

### 已有项目加固（你现在的 Agent1）
1. [ ] 架构测试独立成项目，至少 8 项检查
2. [ ] 熔断器故障注入测试至少 2 个
3. [ ] 结构化日志验证测试至少 1 个
4. [ ] CI 流水线配置 `.github/workflows/ci.yml`
5. [ ] 镜像构建 + Trivy 扫描（P1）
6. [ ] 测试环境混沌实验（1 个实验起步，如停掉 llama-server）

### 新项目启动
1. [ ] 项目搭建时立即创建 `ArchitectureTests` 项目
2. [ ] 定义第一个架构约束（如“所有 Service 必须有接口”）
3. [ ] 配置本地 Git Hook（`pre-commit` 跑架构测试）
4. [ ] 第一个外部依赖接入时，同步写它的故障注入测试
5. [ ] 第一个关键业务流程上线前，设计 1 个混沌实验

## 八、模式速查表

| 你担心什么           | 用什么防线           | 什么时候做        |
| -------------------- | -------------------- | ----------------- |
| 有人绕过安全检测     | 架构收敛测试         | 每次提交          |
| 外部服务挂了系统崩溃 | 韧性测试             | 每次构建          |
| 并发请求出现竞态     | 压力测试 + 架构收敛  | 每次构建          |
| 未知的故障模式       | 混沌工程             | 定期 / 生产变更前 |
| 出了事查不到原因     | 可观测性验证         | 每次构建          |
| 依赖包有已知漏洞     | 安全扫描（SAST/SCA） | 每次构建          |
| 基础镜像有漏洞       | 镜像扫描（Trivy）    | 每次发布前        |
| 新版本性能退化       | 性能回归测试         | 每次发布前        |

---

**最后叮嘱**：这套体系不是一次性建成的。从架构收敛测试开始（你最擅长的），然后加一个熔断器测试，然后配好 CI 让它们自动跑。**每加一道防线，你的系统就少一种死法。** 把这个 Skill 放在手边，每当你发现一个新 Bug，问自己：“这个 Bug 能不能被某道防线在 CI 阶段就拦住？”——如果可以，就把这个检查点加到对应防线中。这就是从“修 Bug”到“让 Bug 无法存活”的质变。
