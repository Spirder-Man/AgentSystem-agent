# 架构师认知框架 Skill

> 适用场景：当需要从零散现象中识别结构性矛盾，制定长期演进策略，并在技术诱惑与业务价值间做取舍时使用。  
> 核心理念：**代码是思想的投影。架构师的职责不是写最多代码，而是确保任何代码都难以破坏系统。**

---

## 一、架构诊断：从“点状问题”到“模式缺陷”

### 1.1 诊断四步法
1. **溯源**：点状Bug的背后，往往是模块边界模糊或职责重叠。
2. **归类**：将同类问题聚合，寻找共同的根因（如“三种执行范式并存”）。
3. **对照**：与业务核心约束（安全、审计、合规）比对，判断哪些是致命缺陷。
4. **优先**：用风险高低（安全缺失 > 架构腐败 > 体验不佳）决定修复顺序。

### 1.2 常见模式缺陷速查
| 表面症状                       | 可能的模式缺陷                |
| ------------------------------ | ----------------------------- |
| 同一功能有多个实现，行为不一致 | 缺失统一入口/契约             |
| 硬编码散落各处                 | 配置外部化不足 + 缺乏架构约束 |
| 调用链路时断时续               | 缺乏统一的管道/中间件         |
| 状态污染或并发Bug              | 共享可变状态 + 请求级隔离缺失 |
| 输出格式各异                   | 缺乏统一输出契约              |

### 1.3 实战原则
- **不要相信文档，相信调用链**：用 `grep` 或 IDE 的 Find Usages 追踪实际依赖。
- **检查 DI 容器注册**：确认接口实现和生命周期是否符合设计意图。
- **审计关键横切点**：安全检测、日志、审计是否在所有入口都存在。

## 二、领域驱动防御：让行业规范成为代码铁律

### 2.1 核心思想
**把业务法规翻译为技术约束，让系统自动执行合规检查，而不是靠人工事后审计。**

### 2.2 化工 → 架构映射表
| 行业规范要求         | 技术架构约束                                   |
| -------------------- | ---------------------------------------------- |
| 每次检查需记录依据   | 所有合规判定输出必须携带 `RegulationRef`       |
| 整改需跟踪验证       | `Ticket` 有状态机，闭环到 `Verified` 状态      |
| 操作不可篡改         | 事件溯源 + 只追加存储                          |
| 应急方案需科学依据   | `EmergencyResponseModule` 输出必须标注参考标准 |
| 危险化学品清单需实时 | `ChemicalAsset` 台账 + 定期自动合规扫描        |

### 2.3 实施路径
1. 列出行业强制规范的每条“必须/应”条款。
2. 为每条条款设计对应的架构约束或自动化测试。
3. 将这些约束纳入 CI 卡口，**让法规成为不可绕过的门禁**。

## 三、技术决策的权衡哲学

### 3.1 核心原则
**“不要因为技术学习而去剥夺工程价值”**  
- 新技术用于解决已验证的业务痛点，而不是用于“练手”。
- 稳定性 > 先进性，除非旧方案已证明确实妨碍核心需求。

### 3.2 决策四象限
```
                业务价值高
                    │
      ┌─────────────┼─────────────┐
      │  必须做      │  谨慎投入    │
      │  (安全)      │  (新框架)    │
      │              │             │
技术 ──┼──────────────┼──────────────→ 业务
成熟   │              │             │
      │  低优先级    │  果断拒绝    │
      │  (过度重构)  │  (玩具技术)  │
      │              │             │
      └─────────────┼─────────────┘
                    │
                业务价值低
```
- 左上角（安全加固、架构收敛）：**立即投入**。
- 右上角（新技术栈）：**评估风险，小范围试点，不绑死核心链路**。
- 左下角（纯粹重构）：**等有明确业务驱动力再做**。
- 右下角：**坚决拒绝**。

### 3.3 名言实战化
- “It depends.” → 说明理由，列出权衡维度（性能/安全/可维护性/成本）。
- “Premature optimization is the root of all evil.” → 先保证正确与安全，再测量瓶颈，最后定点优化。
- “Keep it simple, stupid.” → 能用现有模式解决就不引入新抽象，直到重复三次以上再重构。

## 四、工程成长路径：从“写代码的人”到“建造系统的人”

### 4.1 四个阶段
1. **功能实现者**：能完成需求，代码可运行。
2. **质量守护者**：主动发现 Bug，写单元测试，关注边界情况。
3. **架构定义者**：制定模块边界、接口契约、技术选型，让团队写不出烂代码。
4. **体系建造者**：设计 CI/CD、质量门禁、混沌工程、可观测性，让系统自保。

### 4.2 关键跃迁行为
- **从修 Bug 到写防止 Bug 的测试**：每修一个 Bug，就加一个对应的架构测试。
- **从手动检查到自动化卡口**：任何“我以后会记得检查”的事，都变成 CI 脚本。
- **从依赖记忆到依赖数据**：重要决策必须有监控数据支撑，而不是“我感觉”。
- **从做功能到做能力**：不再只交付“菜单项”，而是交付“业务闭环 + 防御体系”。

### 4.3 认知升级清单
- [ ] 我能不能在 5 分钟内画出系统的数据流和关键状态机？
- [ ] 我的架构约束是否已编码为自动化测试？
- [ ] 关键的外部依赖宕机时，系统是优雅降级还是崩溃？
- [ ] 新同事入职第一天，会不会因为架构约束而无法提交危险代码？
- [ ] 一年后我回来看这段代码，能看懂当初的设计意图吗？

## 五、项目文档与知识管理规范

### 5.1 必要文档结构
```
docs/
├── architecture/          # 架构决策记录(ADR) + 系统边界图
├── deploy/                # 环境配置 + 启动/回滚步骤
├── testing/               # 测试策略 + 关键用例说明
├── troubleshooting/       # 常见故障 + 排查步骤
└── learning-notes/        # 技术调研 + 踩坑记录
```

### 5.2 架构决策记录 (ADR) 模板
```
# ADR-001: 标题

## 状态
提议 / 已接受 / 已废弃

## 背景
为什么需要做这个决策？

## 决策
我们选了什么方案？

## 后果
- 正面：获得什么好处？
- 负面：引入什么代价？
- 风险：什么情况下需要重新审视？
```

### 5.3 知识复利原则
- 每解决一个难题，输出一份文档或 Skill，降低自己（和团队）下次的思考成本。
- 文档不是写给现在的自己，而是写给三个月后已经失忆的自己。

---

**最后总结**：你现在拥有的不仅仅是编码能力，而是一整套**从领域分析到架构收敛，从质量防御到业务编排的工程体系**。将这些框架内化为本能，下次遇到任何新项目，你都能在三天内搭建起安全、可观测、可验证的骨架，剩下的只是填充业务血肉。这套体系，就是你从普通程序员晋升为技术负责人的通行证。
