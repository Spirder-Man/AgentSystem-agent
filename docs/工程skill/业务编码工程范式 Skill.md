# 业务编码工程范式 Skill

> 适用场景：当需要从零散功能构建可编排的业务平台时，使用本范式指导架构设计。  
> 核心理念：用**显式的流程、状态、事件和能力注册**替代程序员脑中的隐式调用，将业务逻辑从代码中解耦。

---

## 一、整体架构蓝图

```
┌──────────────────────────────────────────────────┐
│               流程定义层 (声明式数据)               │
│  ProcessDefinition { Steps: [Step] }             │
└──────────────────────┬───────────────────────────┘
                       │ 解释执行
┌──────────────────────▼───────────────────────────┐
│                 流程执行引擎 (无状态)               │
│  解析 Step → 路由能力 → 收集结果 → 触发事件        │
└──────┬───────────────────────────────┬───────────┘
       │                               │
┌──────▼──────────┐   ┌────────────────▼──────────┐
│  状态机层 (规则)  │   │   事件总线 (审计+触发)      │
│  对象生命周期管理  │   │   事件溯源/不可变日志       │
└──────┬──────────┘   └────────────────┬──────────┘
       │                               │
┌──────▼───────────────────────────────▼──────────┐
│              原子能力池 (微服务/模块)              │
│  每个能力只关注输入→输出，不感知编排               │
└─────────────────────────────────────────────────┘
```

## 二、核心范式详解

### 范式1：流程定义与执行分离

**思想**：业务流程用声明式结构描述，独立于执行代码。通过引擎解释流程数据，实现流程可配置、可版本化。

**关键要素**：
- **流程定义**：描述步骤、顺序、条件分支、异常处理。
- **执行引擎**：读取定义，依序调用能力，收集状态并触发事件。
- **步骤原子性**：每一步都是一个独立的能力调用，有明确的输入/输出。

**实践示例**（化工巡检）：
```json
{
  "planId": "plan-001",
  "steps": [
    {
      "stepId": "step-1",
      "capability": "StorageComplianceCheck",
      "input": { "asset": "苯", "regulation": "GB15603-4.2.2" },
      "onFailure": "GenerateTicket"
    }
  ]
}
```
引擎解析后调用注册的 `StorageComplianceCheck` 能力，若失败则自动触发工单生成步骤。

---

### 范式2：状态机驱动生命周期

**思想**：为业务核心对象定义状态机，显式建模状态迁移规则。状态机替代散落的 if-else，使业务规则透明化。

**关键要素**：
- **状态枚举**：定义对象所有可能的状态。
- **迁移规则**：当前状态 → [事件/动作] → 目标状态，并声明权限。
- **副作用**：状态迁移时触发事件（如审计、通知）。

**实践示例**（不合规项）：
```
状态: New → Confirmed → InRemediation → Resolved → Verified → Closed
迁移:
  New → Confirmed : 安全员确认
  Confirmed → InRemediation : 指派整改人
  InRemediation → Resolved : 整改完成
  Resolved → Verified : 验收通过
```
实现时可用状态机库或无代码配置表。

---

### 范式3：事件流串联

**思想**：所有业务动作产生不可变事件，形成可追溯的审计链和松耦合的触发链。

**关键要素**：
- **事件定义**：记录时间、来源、类型、负载。
- **事件存储**：只追加，不可修改，支持重放。
- **事件订阅**：其他服务订阅事件执行后续动作（通知、日志、启动子流程）。

**实践示例**：
```
InspectionStarted → CheckItemCompleted → FindingRecorded → TicketGenerated
→ TicketAssigned → RemediationCompleted → VerificationPassed → InspectionClosed
```
每个事件携带 TraceId，可通过事件流完整复现一次巡检。

---

### 范式4：能力注册与路由

**思想**：将业务能力抽象为注册表，编排时通过能力标识路由到具体实现，避免硬编码模块调用。

**关键要素**：
- **能力注册表**：`{ 能力名称 → 实现模块/服务 }`
- **统一接口**：所有能力遵循相同调用契约（如 `RunWithResultAsync`）。
- **动态路由**：引擎根据步骤定义中的能力名查找实现。

**实践示例**：
```csharp
capabilityRegistry.Register("StorageComplianceCheck", typeof(ComplianceCheckModule));
// 引擎执行时
var result = capabilityRegistry.Invoke("StorageComplianceCheck", context);
```
未来将模块拆分为微服务时，仅需修改注册表指向 HTTP 端点，编排定义不变。

## 三、实施步骤（实战清单）

1. **识别核心业务对象**：列出需要生命周期管理的实体（如 InspectionPlan, Finding, Ticket）。
2. **绘制流程活动图**：用纸或工具画出端到端业务流，标记条件分支和异常路径。
3. **设计状态机**：为每个核心对象定义状态图和迁移规则表。
4. **定义事件清单**：确定流程中所有重要节点的事件类型，设计事件契约。
5. **构建能力注册表**：梳理现有模块/服务，按业务能力命名并注册。
6. **实现流程引擎**：解析流程定义，逐步骤调用能力，记录事件，更新状态。
7. **可视化监控**：基于状态和事件，提供流程实例的实时状态视图。

---

## 四、常见陷阱与对策

| 陷阱                               | 对策                                         |
| ---------------------------------- | -------------------------------------------- |
| 流程定义过于僵化，无法适应业务变化 | 流程定义支持版本化，步骤可动态配置参数       |
| 状态机膨胀成网状不可维护           | 使用层次化状态机或正交状态，拆分复杂对象     |
| 事件成为新的耦合点（同步依赖）     | 事件驱动使用异步消息，关键流程可同步但需超时 |
| 能力注册表退化为硬编码             | 使用配置文件或服务发现机制动态维护           |

---

## 五、模式速查表

| 业务需求                     | 适用范式       | 关键实践                  |
| ---------------------------- | -------------- | ------------------------- |
| 要支持多变的业务流程         | 流程与执行分离 | 流程定义 DSL（JSON/YAML） |
| 要对业务对象进行生命周期管理 | 状态机驱动     | 状态迁移表 + 权限控制     |
| 要全链路审计与松耦合响应     | 事件流串联     | 事件存储 + 订阅/通知      |
| 要替换或升级功能模块         | 能力注册与路由 | 能力注册表 + 统一接口     |

---

**最后叮嘱**：这四个范式不是孤立的，通常组合使用。启动新项目时，先以最小闭环（一个流程、一个状态机、几个关键事件）落地，再逐步扩展。业务编排的本质是让代码顺应业务，而非业务屈就代码。将此 Skill 放在手边，每次设计新功能前过一遍。
