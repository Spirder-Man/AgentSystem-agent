# MVP 启动与业务聚焦工程范式 Skill

> **适用场景**：以新技术（如 AI Agent）改造专业领域老系统时，避免技术猎奇、快速交付业务价值。  
> **核心理念**：业务闭环先于技术堆砌，质量门禁第一天就建，技术探索在独立分支进行。

---

## 一、核心原则

1. **业务闭环先于技术展示**  
   MVP 必须是解决一个人的一个真实问题，而不是展示技术能力。

2. **真实数据先于 Mock**  
   哪怕只有一条法规、一种化学品，也要用真实数据走通业务价值。

3. **质量门禁与业务代码同步搭建**  
   架构约束、CI、结构化日志在第一天就建立，不让系统“裸奔”。

4. **技术探索走独立分支，合并需业务验收**  
   新技术先在独立分支/脚本中实验，只有通过业务指标验证后才并入主干。

---

## 二、启动五步法

### 第 1 步：定义业务验收标准（先写这句话，再写代码）
**要求**：用一句话描述三个月后系统的最小可用状态，必须包含**用户、场景、结果**。

```
示例：安全员输入一种化学品名，系统能自动查出它属于哪类危险品，对照 GB 15603 判定储存条件是否合规，并给出“合规/不合规+依据”的结论。
```

**落地**：把这句话写在 README 最上方，每天审视是否在推进它。

---

### 第 2 步：只画“黄金路径”，砍掉其他一切
**做法**：用流程图或伪代码画出唯一一条能产生业务价值的端到端路径，其余功能全部注释或砍掉。

```
化工系统黄金路径示例：
CLI 输入 → 意图路由(合规查询) → 安全检测(输入) → 合规检查模块(RAG+LLM) → 安全检测(输出) → 结构化输出
```

**铁律**：第一版只交付一件事，但要交付完整——从输入到输出到审计，一个环节不能少。

---

### 第 3 步：第一天就建好质量门禁骨架
在业务代码尚未成型时，先建三个文件：

1. **`ArchitectureTests` 项目**：放一条架构约束测试（如“所有业务入口必须有安全检测”）。
2. **`.github/workflows/ci.yml`**：配置 `dotnet build` + `dotnet test`。
3. **`PipelineMetrics.cs`**：结构化日志模型，即使刚开始只记录“请求开始/结束”。

**目的**：从一开始就在培养一个“带自动防御的系统胚胎”，后期不会被技术债淹没。

---

### 第 4 步：用真实数据驱动，拒绝 Mock 幻觉
- 哪怕只有一个法规文件，也让它能被真正检索。
- 哪怕只有一种化学品，也让它的属性被真实查询到。

**原因**：Mock 数据会让你在“假快乐”中开发三个月，业务验收时彻底暴露。真实数据会倒逼你解决解析、清洗、索引等真正困难的问题。

---

### 第 5 步：第一版上线后立即做三件事
1. **录一个 2 分钟演示视频**：发给业务方（或假想用户）看，你自己会发现大量体验问题。
2. **写一份“已知问题清单”**：记录第一版被迫妥协的地方，作为第二版的设计输入。
3. **补一个混沌实验**：故意停掉 LLM 服务，看系统怎么死——死的姿势会告诉你架构最脆弱的地方。

---

## 三、技术选型决策树

每次遇到新技术冲动时，自问：

```
新技术出现
├─ 它能解决当前业务哪个具体痛点？ 
│  ├─ 明确痛点 → 下一步
│  └─ 找不出 → 记录笔记，搁置
├─ 解决后，业务指标能提升多少？（时间、准确率、成本）
│  ├─ 显著 → 下一步
│  └─ 微弱或不明确 → 搁置
├─ 集成成本多高？会破坏现有架构吗？
│  ├─ 可控 → 小范围试点
│  └─ 过高 → 等待更成熟版本
└─ 试点结果是否达到预期？
   ├─ 是 → 合并进主干
   └─ 否 → 回滚，记录原因
```

**适用场景**：在项目任何阶段，当你想引入一个新的范式、框架或工具时，强制自己按此树执行。

---

## 四、时间盒与双螺旋并行模型

每天固定时间分配，避免技术探索挤占业务交付：

- **70% 时间**：推进业务主线（按黄金路径打增量）
- **30% 时间**：技术预研（在独立分支或独立控制台脚本中实验）

技术预研结束必须回答一个问题：  
**“这个新东西能让我的业务主线的哪个环节更快/更准/更可解释？”**  
如果回答不了，记录结论后搁置。

---

## 五、禁止事项清单（血泪教训）

- ❌ 业务主线尚未跑通时，引入多个 AI 范式或框架。
- ❌ 用 Mock 数据演示业务价值。
- ❌ 将技术探索分支直接合并到主干，除非通过业务验收测试。
- ❌ 为了“技术学习”而给系统增加不需要的复杂度。
- ❌ 把架构测试、CI、日志放在项目后期补——越晚成本越高。

---

## 六、成熟度自评清单（启动前 & 每月复盘）

- [ ] 我能否在 3 分钟内讲清这个 MVP 为谁解决什么问题？
- [ ] 黄金路径是否已画出来，并且每个环节都有验收标准？
- [ ] CI 是否已配置，并在每次提交时自动跑架构测试？
- [ ] 所有关键业务操作是否有结构化日志和 TraceId？
- [ ] 外部依赖宕机时，系统是优雅降级还是崩溃？（至少做过一次故障注入）

---

**最后提醒**：MVP 不是技术 Demo 的简化版，而是**业务价值的完整切片**。你的目标从来不是“写一个能跑的 Agent”，而是“让一个化工安全员愿意每天打开这个系统”。下次启动新项目时，把这篇 Skill 放在手边，按步骤执行，你会发现自己少走 80% 的弯路。
