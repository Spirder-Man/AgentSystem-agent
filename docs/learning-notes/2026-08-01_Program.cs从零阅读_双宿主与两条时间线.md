## 一、开篇定心：两个 Program.cs 是两套人马（双宿主架构）

当时打开两个 Program.cs 差点混了——它们各自都有一份注册表：

| | `Agent1\Program.cs` | `Agent1.Api\Program.cs` |
|---|---|---|
| 身份 | **核心引擎·控制台宿主** | **Web API 宿主** |
| 注册表 | 34 个 AddSingleton（L105-319） | 精简版 ~14 个（L105-141） |
| 特有 | 无 | `AddHostedService<SessionCleanupHostedService>`（L156）、`AddControllers`（L315） |
| 服务对象 | CLI 控制台交互（6步流水线） | HTTP 请求（15 个 Controller） |
| 对应血谱 | L42「CLI 6步流水线」 | L38-41「API 快速通道」 |
| 启动命令 | `dotnet run --project Agent1` | `dotnet run --project Agent1.Api` |

一个 .NET 进程只能有一个 Program.cs——本项目刻意做成**双宿主**。两个进程 = 两套容器 = **两套互不相干的单例**：

```
Agent1.Api（Web 进程）                    Agent1（控制台进程）
├─ 自己的容器（~14个单例）                ├─ 自己的容器（34个单例）
├─ 15 个 Controller                      ├─ CLI 交互
└─ SessionCleanupHostedService           └─ 无 Web 层
```

⚠️ 推论：`Agent1.Api` 的 `SemaphoreSlim(2,2)` 和 `Agent1` 的是**两把不同的锁**——各自限 2 并发，合起来可能 4。这就是"进程级边界"的活案例（详见 DI 笔记 2.3）。

## 四、L275-293 注释三要点（DI 容器段）

### 4.1 "控制台应用不存在 Web 请求级别的隔离需求" —— 全单例的环境视角

| | Web 应用（Agent1.Api） | 控制台应用（Agent1） |
|---|---|---|
| "请求"概念 | 每次 HTTP 请求 = 独立作用域 | 只有一个主循环（while(true)） |
| 隔离需求 | 请求之间要隔离 | **没有**——所有人共享同一循环 |
| 生命周期 | Scoped 有意义 | Scoped 无意义 → **全单例是环境逼出来的合理选择** |

### 4.2 "注入 Mock<ILlmService> 即可隔离外部 AI 服务依赖" —— 替身测试

项目实据：`Agent1.Tests/Stubs/` 五个手写替身：

```
StubLlmService.cs        ← 假的 LLM（不连 llama-server！）
StubDatabaseService.cs   ← 假的数据库
StubKnowledgeBaseService.cs / StubChemicalKnowledgeGraph.cs / StubReflectionVerifier.cs
```

**Mock vs Stub**：都是"替身"，区别在生成方式——Mock 是 Moq 库运行时动态生成（`mock.Setup(...).Returns(...)`），Stub 是手写假实现类。目的相同：让被测代码只依赖"长得像真的"的假货。

替身三大好处：
1. **确定性**：真实 LLM 输出是概率的；假服务返回固定值 → 可断言、可重复
2. **速度**：毫秒级 vs 真实推理数秒~数十秒，且不烧 GPU
3. **环境解耦**：没 GPU / 没 llama-server / 没数据库也能跑测试（CI 可跑）

呼应测试分层：单元测试（替身，只测业务）→ 集成测试（部分替身，测协作）→ E2E（全真实，验链路）。

金句：**替身挡住真实世界，让业务逻辑裸奔接受检验——"无 AI 测 AI 逻辑"。**

## 五、三大基础设施验证（L306-310 预测-验证法实战）

### 5.1 预测 vs 真相

| 注册 | 我的猜测 | 验证结果 |
|---|---|---|
| `IDatabaseService/DatabaseService` | 连接数据库 | ✅ 对但升级认识：**全系统数据库唯一门面**（1817 行），连接只是第 1 个能力（接口 88 行 25 个方法） |
| `ISessionService/SessionService` | 存储临时会话 | ✅ 对：40 行**薄壳门面**，7 个方法全转发给 `SessionManager` 静态类 |
| `IMemoryService/MemoryService` | 持久化记忆 | ⚠️ 半对：**短期内存记忆**（`ConcurrentDictionary`，进程重启即失）；持久化的另有其人 `LongTermMemoryService`（调 DatabaseService 落库） |

短期/长期分工：`MemoryService（内存，记得快会忘）→ 筛选 → LongTermMemoryService（落库，记得牢）`

### 5.2 三个设计妙点

1. **门面模式（Facade）**：SessionService 40 行全转发——接口稳定，实现自由换
2. **单例下的伪作用域**：控制台没有 Scoped → 用 `ConcurrentDictionary<sessionId, 数据>` 模拟按会话隔离（类头 L13 注释"解决单例模式下用户数据泄漏问题"）
3. **质量门**：`IsFallbackContent` 先过滤降级内容才存记忆——垃圾不污染记忆

### 5.3 数据库门面前台五方法（DatabaseService.cs L21-101）

| 方法 | 人话 | 设计点 |
|---|---|---|
| `GetConnectionAsync` | 连接工厂：每次给一个新连接 | 三板斧骨架：CreateConnection → OpenAsync → SQL → 返回 |
| `TestConnectionAsync` | 健康检查：活着返回 true，死了打印原因返回 false | **catch 不抛 = 入口原则三活例**（预期分支用 return） |
| `GetDatabaseInfoAsync` | 诊断报告：一次 SQL 问库名/版本/当前用户 | SELECT current_database(), version(), current_user |
| `GetTableNamesAsync` | 查表清单：问元数据字典库里有哪些表 | information_schema 查询 |
| `InitializeDatabaseAsync` | 建库仪式：9 张表全家桶（vector 扩展→会话→审计→搜索日志→化学文档→知识文档→知识分块→长期记忆→RefreshToken） | 幂等，见 5.5 |

### 5.4 IO 100% 异步化（Task + Async 后缀）

接口 25 个方法全部 `Task` 返回。原因：**数据库是慢 IO，await 等待时不吃线程**——接口声明必须匹配底层异步实现（Npgsql 只有异步 API）。同步 = 线程堵在店门口等外卖；异步 = 外卖到了状态机续体被唤醒。

### 5.5 幂等三连（生产初始化黄金组合）

**幂等**：重复执行 N 次 = 执行 1 次。`CREATE TABLE IF NOT EXISTS`：第 1 次真建，第 2~10 次检查到已存在 → 跳过（no-op）。

**可重入**：中断后重新进入不炸。建到第 4 张表崩溃 → 重启 → 前 4 张跳过，后 5 张接着建。幂等是可重入的地基。

**分步失败隔离**：测连接 → 初始化两步分离（Program.cs L472-489）。连接失败跳过初始化避免异常连锁，运维可区分"网络问题"还是"表结构问题"（注释原文 L474）。

关键区分（表 vs 行）：

```
CREATE TABLE（表名）：天然唯一 → 重复执行 = 报错 relation already exists（数据库替你挡）
INSERT（行）：天然不唯一 → 重复执行 = 累积 → 需唯一约束 + ON CONFLICT DO NOTHING 手动幂等
→ 建表幂等很便宜（一个关键字），数据写入幂等很贵（要设计约束）
```

### 5.6 循环依赖破解 — Lazy<T>（L312-331）

**问题**：LlmService ↔ HybridKnowledgeBaseService 互相依赖——不是设计坏味道，是**同一个 llama-server 的两种能力分别被两个服务需要**：
- LlmService → KnowledgeBase：大模型问答时需要调"查资料"工具（ChemicalComplianceTools 做 RAG 检索）
- KnowledgeBase → LlmService：语义搜索前需要把查询文本转向量（embedding），只有 LLM 服务器有这能力

类比：餐厅里**厨师（LlmService）**需要冰箱拿食材，**冰箱（KnowledgeBase）**需要厨师预处理食材——同一厨房两个岗位的天然协作关系。

**解法**：Lazy<T> = 先发"欠条"，用时才兑现

```csharp
// L328-329：注册时只给配方，不执行
services.AddSingleton<LlmService>(sp => new LlmService(
    new Lazy<IKnowledgeBaseService>(() => sp.GetRequiredService<IKnowledgeBaseService>())));
```

时间线（三阶段解开死循环）：

```
① 构建 LlmService → 收到 Lazy 盒子（欠条，不碰 .Value）
② 构建 HybridKnowledgeBaseService → 需要 ILlmService → 容器返回第①步的单例 ✅
③ LlmService 首次 RAG 检索 → 访问 .Value → 兑现欠条 → 拿到已出生的 KnowledgeBase ✅
```

**vs 老方案**（注释 L324-326）：`new LlmService(null!)` 后补 Set = 运行时风险（忘记调用 → NullRef）；Lazy 编译期安全，凭条必兑。

### 5.7 ToolService 聚合门面 + 工厂注册 vs 自动注册（L333-345）

```csharp
services.AddSingleton<IToolService>(sp =>      // 工厂注册：亲手写构造过程
{
    var llm = sp.GetRequiredService<ILlmService>();             // sp = 容器本人，用它拿
    var kb = sp.GetRequiredService<IKnowledgeBaseService>();
    return new ToolService(llm, kb, AppConfig.Instance.ChemicalTool?.Tools);
    //                    ───  ──  ───────────────────────────────────────
    //                  容器拿  容器拿             自己口袋里拿
});
services.AddSingleton<AgentDialog>();           // 裸注册，无接口
```

**ToolService = 聚合门面**（与 SessionService 的薄壳门面不同）：把 ILlmService + IKnowledgeBaseService + Tools 配置三个独立东西捏成一个新服务。

**为什么是工厂注册（sp => ...）而不是自动注册？**

判据：构造器的**每一个**参数类型，在登记表里有 `AddSingleton<该类型>()` 吗？

| 参数 | 类型 | 登记表有？ | 传法 |
|---|---|---|---|
| llm | `ILlmService` | ✅ L330 | 自动（sp.GetRequiredService） |
| kb | `IKnowledgeBaseService` | ✅ | 自动 |
| Tools | `List<ToolDefinition>` | ❌ | **手动**（从 AppConfig 取） |

**为什么 List<ToolDefinition> 不注册进容器？**

技术上完全可以，但不该：

1. **类型太泛无身份**：`ILlmService` 自带语义"我是大模型服务"，`List<ToolDefinition>` 只是"一个工具列表"——万一将来另一个服务也要 `List<ToolDefinition>`（如命令注册表），容器分不清该给哪个（唯一性锁定冲突）
2. **配置数据不是服务**：Tools 来自 appsettings.json，没有行为、没有生命周期管理需求——它的家是 AppConfig，不需要住进容器

金句：**服务的归容器，配置的归 AppConfig。** 自动传 = 参数有强语义身份（容器知道填什么）；手动传 = 参数来自配置或类型太泛（你亲手选"走这条，不是那条"）。

**类比（方式二·自动挡 vs 手动挡）**：
- 标准路况（构造参数全有明确身份）→ 自动挡：`AddSingleton<I, C>()`，容器自己换挡
- 特殊路况（有配置数据或泛类型）→ 手动挡：`sp => new(...)`，你亲手控挡
- 判据：参数类型有没有强语义身份——有则自动，泛则手动

**AgentDialog 裸注册（L345）**：`AddSingleton<AgentDialog>()` 无接口——它是编排核心，是被测对象本身（不是外部依赖），不需要被 Mock 替换（接口判据详见 4.2 的"Mock/Stub 替身"配套逻辑）。

### 5.8 DI 注册表三层架构全景（L306-394+）

注册表的 34 个服务不是平铺的——它们分布在三层，自下而上支撑：

```
第三层 编排与规则引擎（L378-394）    ← "怎么干活"——把原子能力串成工作流
  InspectionOrchestrator  DeterministRuleEngine  ComplianceRuleEngine
  InspectionRepository    ScheduledScanService   CapabilityRegistry
        │ 调用
        ▼
第二层 核心业务能力（L328-366）      ← "能干什么"——每一项原子能力
  AgentDialog  ToolService  AuditService  IntegrationService
  ModuleDispatcher  ResponseCacheService  HybridKnowledgeBaseService
        │ 依赖
        ▼
第一层 基础设施（L306-320）           ← "凭什么能"——存数据、管状态
  DatabaseService  SessionService  MemoryService
```

**层间关系**：

| 层 | 职责 | 有没有业务思维？ | 类比 |
|---|---|---|---|
| 基础设施 | 连数据库、记会话、缓存记忆 | ❌ 纯能力，无思维 | 砖头、水泥 |
| 核心业务 | 调大模型、查知识库、记审计、接外部系统 | ✅ 单项思维 | 发动机、变速箱 |
| 编排规则 | 把查库存+查工单+合规判断+大模型分析串成巡检报告 | ✅ 组合思维 | 总装线：把零件装成整车 |

**为什么读到 L378 突然觉得"这又是什么"——因为你下意识在分"能干什么"和"怎么干"**：L362 之前都是"单项能力"（能调 LLM、能查数据库），L378 开始是"把这些能力编排成工作流"（巡检流程、定时扫描、规则匹配）。前者是零件，后者是装配图。

**三种注册方式的层分布**：
- 自动注册（`AddSingleton<I, C>()`）：三层都有——参数全在容器里，信任容器
- 工厂注册（`sp => new(...)`）：二三层为主——有配置数据或想控制构造过程
- 裸注册（`AddSingleton<C>()`）：二三层编排类——被测对象不需要接口

### 5.9 EventActionDispatcher 事件订阅机制 + 委托 vs 接口判据（L395-409）

**核心机制**：Publish（喊"发生了"）→ Subscribe（说"我干这个"）→ 中间靠事件类型标签匹配。

```
启动时（一次）：Subscribe("FindingCreated", 委托) → 存进 _subscriptions 字典
运行时（每次）：Publish("FindingCreated", evt)   → 字典取出委托 → 执行
```

**为什么用委托而不是接口？**

两种方式都能解耦——让 ScheduledScanService 不知道谁在听。区别不在"能不能"，在"值不值"：

| | 接口方式 | 委托方式 |
|---|---|---|
| 三行逻辑的代价 | 必须先写一个类（10行模板） | lambda 当场写（3行） |
| 适合场景 | 处理逻辑很重（几百行） | 处理逻辑极轻（几行） |
| 当前场景 | ❌ 每个订阅者当前只 3 行日志 | ✅ 选委托——最轻工具做最轻活 |

**解耦的具体方式**（对照权限系统同一张图纸）：

```
没有解耦：ScheduledScanService 肚子里写死"扫完了→记日志→发邮件→生工单"
         → 加新动作 = 改老代码 = 重新部署

有了解耦：
  ScheduledScanService: 只写 Publish("ScheduledScanCompleted")  ← 一行！
  Program.cs 启动时:    Subscribe("ScheduledScanCompleted", 记日志)
                        Subscribe("ScheduledScanCompleted", 发邮件)  ← 新增不改老代码
                        Subscribe("ScheduledScanCompleted", 生工单)  ← 新增不改老代码
```

**与权限系统的模式对照**：委托在这里的角色跟权限过滤完全一致——把"标签"和"行为"绑在一起存进注册表，等匹配时取出执行。标签=事件类型（"FindingCreated"）或权限名（"Article.View"），委托=行为规则，注册表=_subscriptions 字典或 PermissionRegistry。解耦=让"谁发生"和"发生之后做什么"互不认识，靠标签对接。

当前两条订阅只是占位（记日志），注释已标注未来扩展方向："FindingCreated→通知安全员"、"InspectionCompleted→生成巡检报告"——加一行 Subscribe 即生效，不改任何老代码。

**委托 = C# 里"把一段行为打包成数据"的原子类型**。字符串存的是"名字"不是"行为"，接口对行为的封装太重（三行逻辑不配一个独立类），委托是唯一"行为数据化"的轻量手段——就像 SqlConnection 是 DatabaseService 的唯一轻量选择一样，不是"选了委托"，是"要写 Subscribe 这种机制除了委托没别的轻量选项"。

### 5.10 DI容器注册机制全链路总结 —— 从字典本质到五条撰写规则

> 这是今天横跨 L298-425 全部注册分析后，对"容器到底是什么"和"怎么往容器里写东西"的系统性收官。

#### 5.10.1 容器的本质 = 一本 Dictionary<类型, 配方>

去掉所有术语，容器就是一本字典：

```
容器内部登记表（L298 注册之后开始填）：
┌─────────────────────────────────────────────────────┐
│ 类型（key）                  │ 值（value）           │
├─────────────────────────────────────────────────────┤
│ AppConfig                   │ AppConfig.Instance    │  ← L298 塞进去的
│ ILogger<>                   │ → 配方：new Logger<T>()  │  ← L304 开放泛型
│ IDatabaseService            │ → 配方：new DatabaseService(...) │
│ ISessionService             │ → 配方：new SessionService()     │
│ ILlmService                 │ → 配方：new LlmService(...)      │
│ ...（共 ~34 条记录）         │ ...                   │
└─────────────────────────────────────────────────────┘

容器的唯一工作：有人问类型 X → 翻字典找 key=X → 找到了就按配方 new 给 → 找不到就报错。
```

**关键认知：字典的 key 是"类型"，不是"属性名"。** AppConfig 作为类型登记了一次，它里面几十个属性（Llm、Database、ChemicalTool 等）对容器来说不可见。容器只认识 `AppConfig`，不认识 `AppConfig.ChemicalTool.Tools`。

#### 5.10.2 三要素认知框架

查看 Program.cs 任何一行注册，都可以用三个独立维度理解：

| 要素 | 含义 | SessionService 例 | ToolService 例 |
|---|---|---|---|
| **登记的** | 字典里多了什么 key→value | key=`ISessionService`，value=`配方：new SessionService()` | key=`IToolService`，value=`配方：执行这段 lambda` |
| **容器构造的** | 容器怎么 new 出对象 | `new SessionService()`——零参数，容器闭眼 new | **容器不负责 new**——只执行你写的 lambda，lambda 里你亲手 new |
| **方向盘参数** | 必须你亲手填的缺口 | 无 | `List<ToolDefinition>`（字典里没有这个 key） |

三要素的核心关系：**登记决定字典里有什么 → 字典内容决定容器能不能自动构造 → 容器不能自动构造的缺口就是方向盘参数 → 必须你亲手补上。**

#### 5.10.3 自动注册 vs 工厂注册 —— 一条判据走到底

**判据一句话：构造器所有参数的类型，都作为 key 在容器字典里存在吗？**

全有 → 自动注册。缺一个 → 工厂注册。构造完还需要调方法装配（如 `Register`）→ 工厂注册。

| 对比维度 | 自动注册 | 工厂注册 |
|---|---|---|
| 写法 | `AddSingleton<I, C>()` | `AddSingleton<I>(sp => { ... return new C(...); })` |
| 谁 new | 容器自动 new | 你亲手 new |
| 参数来源 | 容器翻字典自己找 | 你用 `sp.GetRequiredService` 拿一部分 + 自己从 AppConfig/别处搞一部分 |
| 适用条件 | 构造器所有参数类型都在字典里 | 至少一个参数类型不在字典里 |
| 控制力 | 零——容器说了算 | 完全——你说了算 |
| 在 Program.cs 的占比 | ~70% | ~30%（LlmService、ToolService、HybridKnowledgeBaseService、AlertDispatcher 等） |

**为什么有些类型字典里没有？** 两种原因：

1. **泛型基础类型不登记** —— `List<T>`, `string`, `int` 没有"唯一身份"。如果登记了 `List<ToolDefinition>`，全系统只能有一个工具列表 → 另一个要用 `List<ToolDefinition>` 的服务拿错东西 → 灾难。

2. **装配不止构造器** —— AlertDispatcher 构造完空壳后还要 `d.Register(通道)`。容器只会调构造器，不会"构造之后再调方法"。

**自动挡 vs 手动挡终极类比：** 不是"哪个更好"，是"不同的路况用不同的挡位"。直线（参数全在字典里）→ 自动挡。弯道（参数缺了/装配不走构造器）→ 必须手动挡。

#### 5.10.4 容器字典撰写五条规则

> 这五条规则从 Program.cs 全部 34 行注册反推得出，每一条都对应"如果不遵守会怎样"的灾难场景。

**规则一：强语义身份 —— 进字典的类型必须能唯一标识系统中那个东西**

```
✅ AppConfig           → "我是全局配置"——任何人一听就知道是哪个
✅ ILlmService         → "我是大模型服务"——系统中唯一
✅ InspectionOrchestrator → "我是巡检编排器"——唯一

❌ List<ToolDefinition> → "我是...一个列表？哪个列表？"
❌ string              → "我是...一段文字？谁的？"
❌ int                 → "我是...一个数字？什么的？"
```

自检语：**这个类型名说出去，任何一个同事能立刻知道它代表系统中哪个唯一的东西吗？**

**规则二：配置走 AppConfig 通道，不拆开登记**

```csharp
services.AddSingleton(AppConfig.Instance);   // ← 只登记这一个

// ❌ 绝对不写（违反则配置碎片化，到处是孤立的 key-value）：
services.AddSingleton(AppConfig.Instance.Database);
services.AddSingleton(AppConfig.Instance.ChemicalTool);
```

原因：子属性的类型没有"唯一身份"——`DatabaseConfig` 只是配置数据的一块，不是独立服务。谁需要配置就注入 `AppConfig` 整体，自己在构造器里取 `config.Database`。

**规则三：一个类一个身份 —— 绝不以多个 key 登记同一个实现类**

```csharp
// ✅ 正确
services.AddSingleton<IDatabaseService, DatabaseService>();

// ❌ 绝对不同时写（违反则同一类有两个独立单例 → 数据不同步 → 灾难）
services.AddSingleton<DatabaseService>();
```

**规则四：接口 vs 裸类 —— 被依赖者用接口，编排终点用自身**

```
用接口登记（AddSingleton<I, C>()）：    裸类登记（AddSingleton<C>()）：
  IDatabaseService     ← 被所有人依赖       AgentDialog           ← 编排核心，被测对象
  ISessionService      ← 被所有人依赖       ModuleDispatcher      ← 编排核心
  ILlmService          ← 被 ToolService 依赖  InspectionOrchestrator ← 编排核心
  IToolService         ← 被 AgentDialog 依赖  DeterministicRuleEngine ← 被测对象
```

判据：**这个服务会被其他服务当依赖注入吗？** 是 → 接口。否（编排终点/内部不暴露）→ 裸类。

**规则五：自动 vs 工厂 —— 构造参数字典命中率决定**

```
构造器所有参数类型 都在字典里       → 自动注册（写法和实例都在 5.10.3）
构造器任一参数类型 不在字典里       → 工厂注册
构造完还需要调方法装配（如 Register）→ 工厂注册
```

**五条规则互为约束，共同防止"参数混乱"。** 每一行 `AddSingleton` 都是五条规则同时审过的结果。

#### 5.10.5 全案例对照表 —— Program.cs 真实代码一表收束

| 服务 | 注册方式 | 判据（为什么） | 规则命中了哪条 |
|---|---|---|---|
| SessionService | 自动 | 零参数——零个缺零个 | 规则五（全命中） |
| DatabaseService | 自动 | 参数 AppConfig——字典里有 | 规则五（全命中）、规则二（走 AppConfig 通道） |
| AuditService | 自动 | 参数 IDatabaseService——字典里有 | 规则五、规则四（接口登记） |
| **ToolService** | **工厂** | `List<ToolDefinition>` 字典里没有 | 规则五（缺一个）、规则一（泛型不强语义） |
| **HybridKnowledgeBaseService** | **工厂** | 能自动但手动——构造器内 new 子对象（不走容器） | 规则五（装配不止构造器） |
| **LlmService** | **工厂** | `Lazy<T>` 延迟解析——打破循环依赖 | 规则五（特殊装配） |
| **AlertDispatcher** | **工厂** | new 完还要调 Register 装配通道 | 规则五（装配不止构造器） |
| AgentDialog | 自动 | 构造参数全在字典里（7个都有） | 规则五、规则四（编排终点裸类） |
| IntegrationService | 自动 | 构造参数 IDatabaseService + AppConfig——全在 | 规则五、规则四（接口登记） |

**工厂注册不是容器的失败——是容器刻意把控制权还给你。** 凡是需要"你亲手决策"的地方（选哪个列表、开不开邮件通道、子对象怎么造），容器都退后一步，让你写 lambda。

## 六、入口设计（L72-79，详见 async 笔记 6.1）

- 原则一：组装（一次）vs 常驻循环（反复）——判据"做一次还是反复做"
- 原则二：启动失败 = 进循环前不可恢复的错误，Fail-Fast
- 原则三：预期失败用 return，意外错误用 throw（return 是正常下班，throw 是报警器）
- 原则四：堆栈的读者是开发者不是用户——人的错误静悄悄，程序的错误响当当
