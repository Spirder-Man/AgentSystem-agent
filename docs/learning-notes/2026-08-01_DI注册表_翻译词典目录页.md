### 2.1 三个生命周期：容器的"对象分配策略"

一句话定位：**生命周期 = 这个对象"活多久、给谁用、大家拿到的是不是同一个"**。它和并发锁笔记的"对象身份"是同一件事——锁是手工管身份，生命周期是容器管身份。

**Singleton（单例）—— 全进程一个**

原理：容器内部有一张"已创建实例缓存表"。第一次解析时按构造器递归装配出一个实例存入缓存，之后所有请求、所有线程都直接返回缓存里的同一引用。

```
第一次解析：new AgentDialog(依赖们...) → 存入容器缓存 ┐
第二次解析：从缓存直接返回同一实例 ←──────────────────┤
第三次解析：从缓存直接返回同一实例 ←──────────────────┘
```

项目实例：`SemaphoreSlim(2,2)` 必须单例——若每个请求各拿一把新锁，互斥直接失效（Bug-038 教训）；`AgentDialog` 单例是因为 `_lastToolResults` 私有状态要跨调用透出（静脉4 #9）。

**Scoped（作用域）—— 每个请求一个**

原理：容器把解析作用域划成块，**一个 HTTP 请求 = 一个作用域**（`IServiceScope`）。同一请求内多次解析拿到同一实例；不同请求 = 不同作用域 = 不同实例；请求结束作用域销毁，容器对其中创建的 `IDisposable` 实例自动 `Dispose()`。

```
请求1 → 作用域1 → 实例A ─┐
请求2 → 作用域2 → 实例B ─┤ 互不相干，请求结束各自释放
请求3 → 作用域3 → 实例C ─┘
```

典型场景：EF Core `DbContext`——每个请求一个数据库上下文，防连接泄漏、防并发冲突。

**Transient（瞬时）—— 每次解析一个**

原理：容器**不做任何缓存**，每次解析都走完整构造流程 new 一个全新的。最纯净但也最浪费（构造昂贵的东西反复 new）。典型场景：轻量无状态对象。

| 维度 | Singleton | Scoped | Transient |
|---|---|---|---|
| 存活范围 | 进程级 | 请求级 | 一次解析级 |
| 实例数量 | 1 | 1/请求 | N 次解析 |
| 跨请求共享 | ✅ 共享 | ❌ 隔离 | ❌ 隔离 |
| 释放时机 | 进程停止 | 请求结束 | 由容器跟踪 |
| 你负责 | **线程安全** | 请求内安全 | 无共享 |
| 本项目使用 | 34/34 | 0 | 0 |

### 2.2 容器解析三层流程（注册→解析→释放）

```
① 注册期（Program.cs）：AddSingleton<T> 只是登记一条"生产说明书"（ServiceDescriptor），此刻不创建任何对象
② 解析期（请求进来）：容器查说明书 → 按生命周期策略决定"新建 or 取缓存"
   → 递归解析构造器参数（参数也是注册过的服务，继续同样流程）→ 装配完成
③ 释放期（请求结束/进程停止）：对 IDisposable 实例按各自生命周期调用 Dispose
```

关键认知：**Controller 每次请求都是新实例（瞬时默认），但它注入的单例服务是同一个**——所以 Controller 里存不了跨请求状态，状态都在单例服务里。ComplianceController 矩阵里 10 个字段全是"容器给的引用"，不是 Controller 自己的东西。

### 2.3 进程级边界（重要纠正：Singleton ≠ 跨服务器）

⚠️ **Singleton 是"进程级"共享，不是"服务器级"**——容器管共享到进程为止。

```
解析级(Transient) < 请求级(Scoped) < 进程级(Singleton) < 跨进程/服务器级（❌ 容器管不了）
```

两台服务器 = 两个进程 = 两套容器 = 两个独立单例：

```
服务器A 进程 → 自己的容器 → 自己的 SemaphoreSlim(2,2) ┐
                                                       ├─ 互不相干！
服务器B 进程 → 自己的容器 → 自己的 SemaphoreSlim(2,2) ┘
```

- 后果：A/B 各自限 2 并发，实际总并发可能 4——"限 2 并发"约束被击穿
- 本项目单机部署，进程级≈服务器级，但**水平扩展时第一个出问题的就是这里**
- 跨进程互斥需要**分布式锁**（Redis 锁/数据库锁）——这正是并发锁笔记六大坑之"跨进程"坑的架构级版本
- 哈希链审计为什么不怕：审计是追加写库，不依赖进程内共享——机制选择要同时看它的适用边界

### 2.4 IHostedService：不是"服务"，是"后台员工"

它和上面 34 个注入服务**不是一类东西**——不供 Controller 注入，而是应用启动后常驻后台干活的进程内任务：

```
应用启动 → Host 调用所有 IHostedService.StartAsync() → 后台任务开跑
应用停止（Ctrl+C / SIGTERM）→ Host 调 StopAsync() → 传取消令牌 → 任务优雅收手
```

SessionCleanupHostedService（Agent1/Services/Orchestration/SessionCleanupHostedService.cs，46 行）就是标准模板，逐行拆：

| 代码 | 作用 |
|---|---|
| `: BackgroundService` | 微软便捷基类，只需实现 ExecuteAsync 一个方法 |
| `ExecuteAsync(stoppingToken)` | 后台主循环体；应用停止时框架把令牌置为已取消 = "关门信号" |
| `while (!stoppingToken.IsCancellationRequested)` | 只要没人喊停就一直跑 |
| `await Task.Delay(10min, stoppingToken)` | 可中断睡眠，醒来清理 |
| `SessionManager.CleanupExpiredSessions(30min)` | **实际业务**：清掉超过 30 分钟未活动的会话 |
| `catch (OperationCanceledException) when(...)` | 被打断时优雅退出（break），不抛异常 |
| `catch (Exception)` | 单次清理出错只记日志，**不影响下一轮**——服务永不因一次失败死亡 |

它翻译的业务约束："API 长期运行，会话越积越多，内存会涨爆" → "每 10 分钟扫一遍，清掉 30 分钟没动的会话"（与 CreateSession 内联自清洁双保险）。

后台模式对比（两种血管，勿混）：

| 模式 | 生命周期 | 本项目例子 |
|---|---|---|
| 请求侧异步 | 跟请求走（Task.Run + 202 轮询） | Dashboard /scan（静脉5） |
| 进程侧常驻 | 跟进程走（IHostedService） | SessionCleanupHostedService |

### 2.5 容器本质：一本 Dictionary<类型, 配方>

> 这是理解"自动注册 vs 工厂注册"的底层地基——跳过本节就永远不知道为什么有些服务要手写 lambda。

去掉所有术语，`ServiceCollection` 就是一本字典：

```
容器内部登记表（每行 AddSingleton 往里写一条）：
┌─────────────────────────────────────────────────────┐
│ 类型（key）                  │ 值（value）           │
├─────────────────────────────────────────────────────┤
│ AppConfig                   │ AppConfig.Instance    │  ← AddSingleton(obj)
│ IDatabaseService            │ → 配方：new DatabaseService(...) │
│ ISessionService             │ → 配方：new SessionService()     │
│ ILlmService                 │ → 配方：执行 lambda → new LlmService(...) │
│ ...（共 ~34 条记录）         │ ...                   │
└─────────────────────────────────────────────────────┘

容器的唯一工作：有人问类型 X → 翻字典找 key=X → 找到就按配方 new → 找不到就报错。
```

**关键认知：字典的 key 是"类型"，不是"属性名"。** `AppConfig` 作为类型登记了一次（L105），它里面几十个属性（Llm、Database、ChemicalTool 等）对容器来说**不可见**。容器只认识 `AppConfig`，不认识 `AppConfig.ChemicalTool.Tools`。

### 2.6 三要素认知框架：理解任何注册行的统一视角

查看 Program.cs 任何一行 `AddSingleton`，都可以用三个独立维度拆解：

| 要素 | 含义 | SessionService 例 | ToolService 例 |
|---|---|---|---|
| **登记的** | 字典里多了什么 key→value | key=`ISessionService`，value=`配方：new SessionService()` | key=`IToolService`，value=`配方：执行这段 lambda` |
| **容器构造的** | 容器怎么 new 出对象 | `new SessionService()`——零参数，容器闭眼 new | **容器不负责 new**——只执行你写的 lambda，lambda 里你亲手 new |
| **方向盘参数** | 必须你亲手填的缺口 | 无 | `List<ToolDefinition>`（字典里没有这个 key） |

三要素的核心关系：**登记决定字典里有什么 → 字典内容决定容器能不能自动构造 → 容器不能自动构造的缺口就是方向盘参数 → 必须你亲手补上。**

### 2.7 自动注册 vs 工厂注册 —— 一条判据走到底

**判据一句话：构造器所有参数的类型，都作为 key 在容器字典里存在吗？**

全有 → 自动注册。缺一个 → 工厂注册。构造完还需要调方法装配（如 `Register`）→ 工厂注册。

| 对比维度 | 自动注册 | 工厂注册 |
|---|---|---|
| 写法 | `AddSingleton<I, C>()` | `AddSingleton<I>(sp => { ... return new C(...); })` |
| 谁 new | 容器自动 new | 你亲手 new |
| 参数来源 | 容器翻字典自己找 | 你用 `sp.GetRequiredService` 拿一部分 + 自己从 AppConfig 搞一部分 |
| 适用条件 | 构造器所有参数类型都在字典里 | 至少一个参数类型不在字典里 |
| 控制力 | 零——容器说了算 | 完全——你说了算 |
| 在本项目占比 | ~70%（DatabaseService, SessionService, AuditService...） | ~30%（LlmService, ToolService, HybridKnowledgeBaseService, AlertDispatcher...） |

**为什么有些类型字典里没有？** 两种原因：

1. **泛型基础类型不登记** —— `List<T>`、`string`、`int` 没有"唯一身份"。如果登记了 `List<ToolDefinition>`，全系统只能有一个工具列表 → 另一个服务（命令注册表）也是 `List<ToolDefinition>` 类型，容器分不清该给哪个 → 灾难。

2. **装配不止构造器** —— AlertDispatcher 构造完空壳后还要 `d.Register(通道)`；EventActionDispatcher new 完还要 `Subscribe(事件, 委托)`。容器只会调构造器，不会"构造之后再调方法"。

**自动挡 vs 手动挡类比：** 不是"哪个更好"，是"不同路况用不同挡位"。直线（参数全在字典里）→ 自动挡。弯道（参数缺了/装配不走构造器）→ 必须手动挡。工厂注册不是容器的失败——是容器刻意把控制权还给你。

### 2.8 容器字典撰写五条规则 — 反推 Program.cs 全部注册的设计约束

> 这五条规则从 Program.cs 全部 34 行注册反推得出，每一条都对应"如果不遵守会怎样"的灾难场景。

**规则一·强语义身份：进字典的类型必须能唯一标识系统中那个东西**

```
✅ AppConfig           → "我是全局配置"——任何人一听就知道是哪个
✅ ILlmService         → "我是大模型服务"——系统中唯一
✅ InspectionOrchestrator → "我是巡检编排器"——唯一

❌ List<ToolDefinition> → "我是...一个列表？哪个列表？"
❌ string              → "我是...一段文字？谁的？"
❌ int                 → "我是...一个数字？什么的？"
```

自检语：**这个类型名说出去，任何一个同事能立刻知道它代表系统中哪个唯一的东西吗？**

**规则二·配置走 AppConfig：只登记 AppConfig 整体，子属性不拆开登记**

```csharp
services.AddSingleton(AppConfig.Instance);   // ← 只登记这一个

// ❌ 绝对不写（违反则配置碎片化，到处是孤立的 key-value）：
services.AddSingleton(AppConfig.Instance.Database);
services.AddSingleton(AppConfig.Instance.ChemicalTool);
```

谁需要配置就注入 `AppConfig` 整体，自己在构造器里取 `config.Database`。

**规则三·一个类一个身份：绝不以多个 key 登记同一个实现类**

```csharp
// ✅ 正确
services.AddSingleton<IDatabaseService, DatabaseService>();

// ❌ 绝对不同时写（违反则同一类有两个独立单例 → 数据不同步 → 灾难）
services.AddSingleton<DatabaseService>();
```

例外：`LlmService/ILlmService` 的"双登记"是**别名转发**——`ILlmService` 的配方是 `sp.GetRequiredService<LlmService>()`，返回的是同一个实例，不是两个独立单例。

**规则四·接口 vs 裸类：被依赖者用接口，编排终点用自身**

```
用接口登记（AddSingleton<I, C>()）：    裸类登记（AddSingleton<C>()）：
  IDatabaseService     ← 被所有人依赖       AgentDialog           ← 编排核心，被测对象
  ISessionService      ← 被所有人依赖       ModuleDispatcher      ← 编排核心
  ILlmService          ← 被 ToolService 依赖  InspectionOrchestrator ← 编排核心
  IToolService         ← 被 AgentDialog 依赖  DeterministicRuleEngine ← 被测对象
```

判据：**这个服务会被其他服务当依赖注入吗？** 是 → 接口。否（编排终点/内部不暴露）→ 裸类。

**规则五·自动 vs 工厂：构造参数字典命中率决定**

```
构造器所有参数类型 都在字典里       → 自动注册
构造器任一参数类型 不在字典里       → 工厂注册
构造完还需要调方法装配（如 Register）→ 工厂注册
```

**五条规则互为约束，共同防止"参数混乱"。** 每一行 `AddSingleton` 都是五条规则同时审过的结果。

## 四、四种注册形态归纳（写代码时的选择依据）

| 形态 | 用法 | 何时选它 | 本项目例子 |
|---|---|---|---|
| 类型注册 | `AddSingleton<T>()` | 构造器依赖都能被容器自动解析，无特殊逻辑 | AgentDialog / ResponseCacheService / 规则引擎×2 |
| 接口映射 | `AddSingleton<I,T>()` | 需要面向接口编程、可替换实现、可测试 | IDatabaseService / IAuditService / IKnowledgeBaseService |
| 工厂委托 | `AddSingleton<T>(sp => ...)` | **判据见 2.7**：① 构造参数不在字典里 ② 需 Lazy 延迟解析 ③ new 完还要调方法装配（Register/Subscribe）④ 能自动但选了手动 | LlmService(Lazy) / ToolService(List<T>缺key) / AlertDispatcher(装配不止构造器) / EventActionDispatcher(Subscribe) |
| 实例注册 | `AddSingleton(new ...)` | 对象需预先构建（含配置判断） | SemaphoreSlim / AppConfig.Instance / AlertDispatcher |
| 后台服务 | `AddHostedService<T>()` | 常驻后台任务 | SessionCleanupHostedService |
| 条件注册 | `if(...) Add...` | 按配置决定启用与否 | EmailAlertService（邮件开关） |

> **核心判据**（详见 2.7）：构造器所有参数的类型都在容器字典里吗？全有→自动注册，缺一个→工厂注册。
> **五条撰写规则**（详见 2.8）：强语义身份 / 配置走AppConfig / 一个类一个身份 / 接口vs裸类 / 自动vs工厂。

## 五、本表最值得记住的三个点

1. **循环依赖破解（L117-119）**：`LlmService ⇄ HybridKnowledgeBaseService` 互相依赖，用 `Lazy<IKnowledgeBaseService>` 延迟解析——"欠条模式"。教科书级写法，真实系统少见。
2. **全单例架构**：34 个注册 100% 单例。所有并发风险集中在共享状态上，每一把锁（`_llmGate`/`_incrementalGate`）都有明确约束出处。读任何服务时问："它如果被并发调用，状态安全吗？"
3. **约束→机制映射密度**：本表 34 行 = 34 条约束翻译记录。它就是你翻译汽车厂需求的"词典"——排产限流抄 L107、追溯抄 L135、质检标准抄 L146、图像识别抄 L198-203（OCR 工厂）、看板抄 L297。
