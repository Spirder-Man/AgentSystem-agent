## 一、并发控制（SemaphoreSlim）

### 1.1 `_llmGate` — 全进程单例并发闸门

**技术锚点**：`Agent1/Program.cs#L107` + `Agent1.Api/Controllers/ComplianceController.cs#L129-209`

```csharp
services.AddSingleton(new SemaphoreSlim(2, 2));  // 全进程唯一锁
// ComplianceController 注入同一个引用 → 真互斥
```

> **"锁不是一个行为，而是一个对象。判断两段代码是否互斥，只看一条：它们拿到的引用是不是同一个对象。"**
> — 项目并发锁笔记 §0.2

**匹配精度**：这句话直接来源于 `SemaphoreSlim(2,2)` 单例注册的实际设计决策——若 Controller 是 Transient（默认瞬时态），每请求 new 一个 Controller 就意味着每请求一把新锁，2 并发限制彻底失效。DI 单例 = 全进程共享同一引用 = 真互斥。这不是泛泛的"锁要小心"，而是点出了 `AddSingleton` 生命周期与并发控制之间的精确因果关系。

### 1.2 `_incrementalGate` — 增量加载的"一毫秒都不等"

**技术锚点**：`Agent1/Services/Knowledge/ChemicalRAG.cs#L210-226`

```csharp
private static readonly SemaphoreSlim _incrementalGate = new(1, 1);
if (!await _incrementalGate.WaitAsync(0))  // 0 = 一毫秒都不等
    throw new IncrementalAlreadyRunningException();
```

> **"WaitAsync(0) 一毫秒都不等，拿不到立刻失败——增量闸机用此实现'已在跑→409'；WaitAsync(5s) 最多排队 5 秒，超时返回 false——`_llmGate` 用此实现'服务繁忙→503'。同一把刀，两样用法。"**
> — 项目并发锁笔记 §0.1

**匹配精度**：这句话精确对比了项目中两处 SemaphoreSlim 的用法差异。同一 API，参数不同，语义截然不同。`WaitAsync(0)` 是"绝不排队"（幂等保护），`WaitAsync(5s)` 是"可以排队但有限度"（资源保护）。Bug-038 的竞态交错（两个增量请求同时跑→duplicate key→死循环）就是用 `WaitAsync(0)` 修复的。

### 1.3 `finally { Release() }` — 饿死是最危险的锁陷阱

**技术锚点**：`Agent1.Api/Controllers/ComplianceController.cs#L134-210`

```csharp
try { /* LLM 推理业务 */ }
finally { _llmGate.Release(); }  // 无论成败必还证
```

> **"Release 漏一处，服务假死一片。100 个请求里 3 个走提前 return 路径 → 计数永久减少 → 后续全部拿不到锁 → 503 海啸。饿死不是锁坏了，是锁的看守人跑了。"**
> — 项目并发锁笔记 §三·坑1

**匹配精度**：这句话精确命中 `finally` 块的必要性——ComplianceController 的 3 个 LLM 端点（check/hazard/storage）内部有多个 `return 503` / `return 500` 的分支，如果 `Release` 不在 `finally` 里，任何一条提前退出的路径都会永久消耗一张通行证。3 条路径 × 2 个并发 = 6 次非正常退出即可让 `SemaphoreSlim(2,2)` 的计数归零，全站 503。

## 二、依赖注入（DI 容器）

### 2.1 容器本质 = Dictionary<类型, 配方>

**技术锚点**：`Agent1/Program.cs#L275-430`（全部 34 行 AddSingleton）

```csharp
// 容器内部登记表：类型（key）→ 配方（value）
services.AddSingleton<IDatabaseService, DatabaseService>();          // key=IDatabaseService
services.AddSingleton<IToolService>(sp => {                          // key=IToolService
    return new ToolService(llm, kb, AppConfig.Instance.ChemicalTool?.Tools);
});
```

> **"ServiceCollection 就是一本 Dictionary<类型, 配方>。容器的唯一工作：有人问类型 X → 翻字典找 key=X → 找到了就按配方 new 给 → 找不到就报错。字典的 key 是'类型'，不是'属性名'——AppConfig 作为类型登记了一次，它里面几十个属性对容器来说不可见。"**
> — 项目 DI 注册表笔记 §2.5

**匹配精度**：这句话是理解"自动注册 vs 工厂注册"的地基。ToolService 为什么必须是工厂注册（`sp => new(...)`）？因为 `List<ToolDefinition>` 没有登记在字典里——容器翻字典找不到这个 key。LlmService 为什么也是工厂注册？因为它需要 `Lazy<T>` 延迟解析打破循环依赖。判据只有一条："构造器所有参数的类型，都作为 key 在容器字典里存在吗？"

### 2.2 自动注册 vs 工厂注册的判据

**技术锚点**：`Agent1/Program.cs#L121-126`（ToolService 工厂注册） vs `Agent1/Program.cs#L108`（DatabaseService 自动注册）

| 对比维度 | ToolService（工厂） | DatabaseService（自动） |
|---|---|---|
| 构造参数 | `ILlmService`✅ + `IKnowledgeBaseService`✅ + `List<ToolDefinition>`❌ | `AppConfig`✅ |
| 判据 | 字典里缺 `List<ToolDefinition>` → 必须手动 | 参数全在字典里 → 容器自动 new |

> **"自动挡 vs 手动挡：不是'哪个更好'，是'不同的路况用不同的挡位'。直线（参数全在字典里）→ 自动挡。弯道（参数缺了/装配不走构造器）→ 必须手动挡。工厂注册不是容器的失败——是容器刻意把控制权还给你。"**
> — 项目 DI 注册表笔记 §2.7

**匹配精度**：这句话精准区分了两种注册方式的本质——很多人以为工厂注册是"容器的缺陷"，实际上容器在说"这个参数我翻遍字典也找不到，你来决定"。项目中 ~70% 是自动注册，~30% 是工厂注册（LlmService、ToolService、HybridKnowledgeBaseService、AlertDispatcher、MemoryCoordinator、ChemicalRAG），每一处工厂注册都有明确的"字典缺 key"原因。

### 2.3 五条 DI 字典撰写规则

**技术锚点**：`Agent1/Program.cs#L105-430`（34 行注册全部反推得出）

```csharp
// 规则一·强语义身份：进字典的类型必须能唯一标识系统中那个东西
AddSingleton<AppConfig>(AppConfig.Instance);   // ✅ "我是全局配置"
// ❌ AddSingleton(AppConfig.Instance.Database); ← 子属性没有唯一身份

// 规则三·一个类一个身份：绝不以多个 key 登记同一个实现类
AddSingleton<IDatabaseService, DatabaseService>();  // ✅
// ❌ 同时写 AddSingleton<DatabaseService>(); → 两个独立单例 → 数据不同步
```

> **"这个类型名说出去，任何一个同事能立刻知道它代表系统中哪个唯一的东西吗？——是，就登记。不是（如 `List<ToolDefinition>`、`string`、`int`），就从 AppConfig 取。"**
> — 项目 DI 注册表笔记 §2.8·规则一

**匹配精度**：这句话是"Services 的归容器，配置的归 AppConfig"这一设计原则的精确表述。`List<ToolDefinition>` 不登记进容器不是因为"技术上不行"，而是因为万一将来另一个服务（如命令注册表）也需要 `List<ToolDefinition>` 类型，容器分不清该给哪个——唯一性锁定冲突。这是"强语义身份"原则的直接约束。

## 三、异步编程（async/await 底层）

### 3.1 状态机三件套：发动机-信封-接线员

**技术锚点**：`Agent1/Program.cs#L67-L79`（13 行注释链条）

```csharp
// L67: async Main → 编译器生成 <Main>d__0 状态机（MoveNext 逐段执行）
// L70: 异常会被包装进 Task，不会导致进程静默崩溃
// L77: 【生产维度】async Main 的异常会被写入 Task 返回值
```

> **"async 关键字本身不干任何异步的事——它只是对编译器说'把下面的方法改造成状态机'；状态机跑完一段歇一段，最终把结果装进 Task 信封递给你；你写的 await 就是'拆信封看结果'。"**
> — 项目 async 状态机笔记 §一

**匹配精度**：这个三件套类比（状态机=发动机、Task=信封、AsyncTaskMethodBuilder=接线员）直接来源于 Program.cs L67-79 的 13 行注释链条的完整拆解。L67 说编译器造发动机（`<Main>d__0`），L70 说异常进信封（Task），L77 说 CLR 亲自拆信封验收——三行注释恰好对应三件套的三个角色。

### 3.2 三种等待方式的错误与正确

**技术锚点**：`Agent1.Api/Controllers/ComplianceController.cs`（全链路 await） vs 理论反例

```csharp
// ✅ 正确：await + try/catch（项目全用此模式）
await _llmGate.WaitAsync(TimeSpan.FromSeconds(5));

// ❌ 错误1：调用 async 方法但不 await → 异常静默丢失
// ❌ 错误2：用 .Result/.Wait() 等 → 堵死门等外卖 → 死锁/线程池饿死
```

> **"等的人不写对，就像堵着门等外卖——不是外卖不来，是你自己堵死了唯一能送到的路，平白让自己心堵。"**
> — 项目 async 状态机笔记 §四（用户原创比喻，AI 精修版）

**匹配精度**：这个类比精确对应 `.Result` 死等的底层机制：调用线程堵在 `.Result` 上，而异步续体需要回到该线程才能完成（SynchronizationContext 约束）——线程等 Task，Task 等线程，死锁。这不仅是"等的方式错了"，而是"等的人堵住了救自己的人的路"。项目用 `await` 全程避免了此坑，但 `_llmGate.WaitAsync(5s)` 的超时保险丝正是为了防止排队线程永久阻塞。

### 3.3 异常的四级影响地图

**技术锚点**：`Agent1/Program.cs#L67-L79` + `Agent1.Api/Program.cs` 异常中间件

```
对象级 < 任务(Task)级 < 线程级 < 进程级
```

> **"级别越高，爆炸半径越大。对象级坏影响一条链路，任务级坏影响一个信封，线程级坏了可能崩整个进程——而注释 L70 说的是：async Main 的异常进 Task 信封而不是直接砸到 CLR，所以进程不崩。但如果你不 await 那个信封，异常就永远静默——不是不崩，是崩了你不知道。"**
> — 项目 async 状态机笔记 §五

**匹配精度**：这个四级地图精确关联了 Program.cs L70 的注释——"不会导致进程静默崩溃"的真正含义是异常被 Task 信封接住了（任务级），而非"异常消失了"。如果不 await 那个 Task，异常就留在了无人查看的信封里（UnobservedTaskException，默认只警告）。"静默"的精髓是"没有交代后事"，而不是"没有崩溃"。

## 四、评测系统（EvalEngine）

### 4.1 FC 就绪性前置检查——"先验枪，再上战场"

**技术锚点**：`Agent1/Services/Eval/EvalEngine.cs#L71-87`

```csharp
// Layer 1: FC 就绪性检查
var (passed, trigCnt, totalCnt, detail) = await llmSvcLayer1.RunFcReadinessCheckAsync();
if (!fcReady) {
    // 跳过 63 条全量，避免无效跑测
    return blockedReport;
}
```

> **"在化工安全评测中，FC 就绪性检查不是可选项——它是'枪还没校准就别上战场'。5 条诊断用例，4/5 触发才放行；若 0/5 触发就跳过 63 条全量评测，因为 63 × 0 = 0——在哑火的管线上跑评测，不是在验证模型，是在浪费 GPU。"**
> — 项目评测系统分析 §三·3.1

**匹配精度**：这句话精准命中 `RunFcReadinessCheckAsync` 的设计意图——不是"可选的验证步骤"，而是"阻断门卫"。63 条用例全部依赖 Function Calling，如果 FC 管线本身不工作（模型不支持/工具未注册/Prompt 未引导），63 条全量跑测将全部返回 false，产生的数据毫无价值。前置检查让"无意义的 GPU 小时消耗"归零。

### 4.2 CheckRegulation 笔误——"一个字符的代价"

**技术锚点**：`Agent1/Services/Eval/EvalEngine.cs#L174` + 系统血谱病灶表

```csharp
// compliance_judgment 白名单：
: new[] { "CheckStorageCompatibility", "CheckHazardCategory",
          "GetSafetyDistance", "CheckRegulation", "GetCurrentTime" };
//                                   ^^^^^^^^^^^^^^
// 插件真实函数名：           "CheckRegulationVersion" ← 差 7 个字符
// 临时 Kernel 过滤后实际注册：4/9 工具
```

> **"白名单里差一个 Version，合规判断评测中法规版本查询工具永远不可用。不是模型能力缺陷，不是架构设计失误——是七个字符的 Typo。在化工安全系统里，一个字符的错误就足以让整个评测维度的数据归零。"**
> — 系统血谱 §七·病灶登记表

**匹配精度**：这是项目自己发现的候选 Bug——EvalEngine.cs#L174 的 `"CheckRegulation"` 与 LlmService.cs 中 Semantic Kernel 注册的 `"CheckRegulationVersion"` 不匹配，导致临时 Kernel 过滤后该工具被剔除。后果是：所有合规判断类（compliance_judgment）评测用例中，法规版本查询工具永远不可用——而评测报告中的 `conclusion_match` 不会告诉你"是因为工具没注册所以结论错了"。

### 4.3 评测结论的三级优先级——"标签优先于正则，正则优先于关键词"

**技术锚点**：`Agent1/Services/Eval/EvalEngine.cs#L1088-1230`（CheckConclusion 方法）

```csharp
// Level 1：结构化标签 [判定:is_compliant=依据原文]
// Level 2：法规编号正则匹配 GB\s*/?T?\s*\d{4,}[.\-]?\d*
// Level 3：关键词回退（合规/不合规/允许/禁止/严禁）
```

> **"三级优先级的本质是信任层级：结构化标签是程序写的，信任最高；正则匹配是规则写的，信任中等；关键词匹配是 heuristic，信任最低。当'标签说合规'但'正文说不合规'时——信标签，因为那是 Agent 在格式化输出时做的最终裁定。"**
> — 项目 EvalEngine.cs#L1082-1086 注释

**匹配精度**：这句话对应 CheckConclusion 方法的已知边界风险（代码注释 L1082-1086 明确自陈）——标签与关键词结论冲突时标签优先，但"可以"在条件句中的多义性（如"若不采取隔离则不合规"中同时出现"可以"和"不合规"）可能被关键词逻辑误判。这是一个"信任层级"问题而非"精度"问题。

## 五、循环依赖破解（Lazy\<T\>）

### 5.1 LlmService ⇄ KnowledgeBase 的"欠条模式"

**技术锚点**：`Agent1/Program.cs#L312-331`

```csharp
// 构建 LlmService → 收到 Lazy 盒子（欠条，不碰 .Value）
services.AddSingleton<LlmService>(sp => new LlmService(
    new Lazy<IKnowledgeBaseService>(() => sp.GetRequiredService<IKnowledgeBaseService>())));
// 构建 HybridKnowledgeBaseService → 需要 ILlmService → 容器返回第①步的单例 ✅
// LlmService 首次 RAG 检索 → 访问 .Value → 兑现欠条 → 拿到已出生的 KnowledgeBase ✅
```

> **"循环依赖不是设计坏味道——是同一个 llama-server 的 chat 和 embedding 两种能力天然绑定同一台服务器带来的架构事实。Lazy<T> 只是让这个事实在代码里不变成死循环：先发欠条入职，再按顺序兑现。厨师需要冰箱，冰箱需要厨师预处理食材——这不是管理混乱，是同一个厨房里两个岗位的天然协作关系。"**
> — 项目 Program.cs 阅读笔记 §5.6

**匹配精度**：这段话精确解释了为什么 LlmService 和 KnowledgeBase "互相依赖"不是 Bug——chat 能力需要查资料（RAG 检索），embedding 能力需要 LLM 服务器（文本转向量）。同一个 llama-server 提供两种能力，两个服务必然互相需要。Lazy<T> 不是"修复循环依赖"，而是"让天然的互相需要不变成代码上的死循环"——三阶段时间线（欠条出生 → 对方出生 → 兑现欠条）是精确到代码行的机制拆解。

## 六、入口设计原则

### 6.1 return vs throw — "正常下班"与"报警器"

**技术锚点**：`Agent1/Program.cs#L158-167`

```csharp
if (configErrors.Count > 0) {
    foreach (var err in configErrors) Console.WriteLine($"❌ {err}");
    return;  // 注意：这里用 return 而非 Environment.Exit()，让 finally 块正常执行
}
```

> **"return 是正常下班（悄悄走，不产生噪音），throw 是报警器（响得刺耳，带着堆栈证据）。配置校验失败是'用户写错了'，不是'程序坏了'——对预期路径用 throw，等于把'下班'当'报警'，是反模式。堆栈的读者是开发者，不是用户。"**
> — 项目 async 状态机笔记 §6.1·原则三

**匹配精度**：这句话精确关联到 Program.cs L166 的选择——为什么用 `return` 而非 `throw`？因为配置校验失败是"预期中的、设计好的退出路径"，不是事故。如果用 throw，用户会看到一屏幕 Unhandled Exception 堆栈（`System.IO.FileNotFoundException at Program.<Main>d__0.MoveNext()...`），而代码 L161-164 已经给了人类语言的友好提示。同时，注释强调"让 finally 块正常执行"——return 保证 finally 执行（清理资源），而 throw 虽然也执行 finally 但之后继续冒泡，可能打断清理链。

### 6.2 组装 vs 常驻循环的判据

**技术锚点**：`Agent1/Program.cs#L158-167`（启动段） vs `Agent1/Program.cs#L581-690`（while(true)）

```
L158-167（启动段·一次性）          L581-690（常驻段·循环）
配置校验 → 失败则打印错误+return    while(true) { 打印菜单→读输入→分发命令 }
```

> **"这件事是'做一次'还是'反复做'？配置加载是开店前备货摆摊（一次），while(true) 是开店后的营业循环（反复接待客人，直到打烊）。你不会把'摆货架'写进'接待客人'的循环里，也不会只接待一个客人就关店。判据一句话：这个能力是'持续提供、直到显式停止'吗？"**
> — 项目 async 状态机笔记 §6.1·原则一

**匹配精度**：这句话来源于对 Program.cs L158 和 L581 两段代码的对照——组装和循环泾渭分明。项目中已有三个活例子验证了这个判据：CLI 菜单循环（`while(true)` 直到用户选"0.退出"）、SessionCleanup（`while(!stoppingToken)` 直到进程停止）、命令分发（`switch(input)` 每次迭代处理一个输入）。判断标准不是"有几行代码"，而是"这个能力是否持续提供直到显式停止"。

## 七、幂等性

### 7.1 建表幂等 vs 插入幂等

**技术锚点**：`Agent1/Services/Infrastructure/DatabaseService.cs#L85-101`（InitializeDatabaseAsync）

```csharp
// 9 张表全部 CREATE TABLE IF NOT EXISTS
await CreateVectorExtensionAsync(...);    // 1. pgvector 扩展
await CreateSessionTableAsync(...);       // 2. 会话表
// ... 共 9 张表
```

> **"CREATE TABLE（表名天然唯一）→ 重复执行 = 数据库替你挡（relation already exists）。INSERT（行天然不唯一）→ 重复执行 = 累积 → 需唯一约束 + ON CONFLICT DO NOTHING 手动幂等。建表幂等很便宜（一个关键字），数据写入幂等很贵（要设计约束）。"**
> — 项目 Program.cs 阅读笔记 §5.5

**匹配精度**：这句话精确区分了"表级别幂等"和"行级别幂等"的成本差异。`CREATE TABLE IF NOT EXISTS` 是 SQL 标准内置的幂等保护——第 1 次真建，第 2~N 次检查到已存在 → 跳过（no-op）。但 INSERT 没有这种内置保护——重复插入同一行数据会累积，必须通过 UNIQUE 约束 + ON CONFLICT 手动实现幂等。这个区分直接对应 Bug-038（增量加载竞态 → duplicate key）的根因。

### 7.2 可重入：中断后重新进入不炸

**技术锚点**：`Agent1/Program.cs#L472-489`（分步失败隔离）

```csharp
// 测连接 → 初始化两步分离
// 连接失败跳过初始化避免异常连锁，运维可区分"网络问题"还是"表结构问题"
```

> **"幂等是可重入的地基。建到第 4 张表崩溃 → 重启 → 前 4 张跳过（IF NOT EXISTS），后 5 张接着建——因为每一步都不累积，所以每一步都不怕重来。"**
> — 项目 Program.cs 阅读笔记 §5.5

**匹配精度**：这句话将"幂等"和"可重入"的关系精确化为地基与建筑的关系。`InitializeDatabaseAsync` 的 9 步建表全部是 `IF NOT EXISTS`，这保证了"崩溃 → 重启 → 接着建"不会产生任何副作用。而 Program.cs L474 的"连接失败跳过初始化"是分步失败隔离——测连接失败直接退出，不进入初始化，运维可以区分"网络问题"（连不上）和"表结构问题"（初始化失败）。

## 八、事件驱动（EventActionDispatcher）

### 8.1 Publish/Subscribe 解耦

**技术锚点**：`Agent1/Program.cs#L395-409`

```csharp
var eventDispatcher = new EventActionDispatcher();
eventDispatcher.Subscribe("FindingCreated", async evt => {
    Serilog.Log.Information("[EventAction] 新合规发现: {Desc}", evt.Description);
    await Task.CompletedTask;
});
eventDispatcher.Subscribe("ScheduledScanCompleted", async evt => { ... });
```

> **"Publish 只管喊'发生了'，Subscribe 只管说'我干这个'——生产者不知道有几个消费者，消费者不知道谁在生产。没有这层解耦：ScheduledScanService 肚子里得写死'扫完了 → 记日志 → 发邮件 → 生工单'——加一个新动作 = 改老代码 = 重新部署。有了它：加一行 Subscribe 就完事，不改任何老代码。"**
> — 项目 Program.cs 阅读笔记 §5.9

**匹配精度**：这句话精确对应 EventActionDispatcher 的核心机制——`_subscriptions` 字典存事件类型→委托列表的映射，Publish 时遍历执行。当前两条订阅只是占位（记日志），注释已标注未来扩展方向（"FindingCreated→通知安全员"、"InspectionCompleted→生成巡检报告"）。解耦的具体收益是：未来加 10 个下游动作，只需 10 行 Subscribe，零改动生产者代码。

### 8.2 委托 vs 接口 — "三行逻辑不配一个独立类"

**技术锚点**：`Agent1/Program.cs#L400-408`（lambda 订阅） vs `Agent1/Services/Infrastructure/IDatabaseService.cs`（接口）

```csharp
// 委托方式：三行 lambda
eventDispatcher.Subscribe("FindingCreated", async evt => {
    Serilog.Log.Information("..."); await Task.CompletedTask;
});

// 接口方式（如果要的话）：先写一个类
public class FindingCreatedHandler : IEventHandler { ... }  // 10 行模板
```

> **"字符串存的是'名字'不是'行为'，接口对行为的封装太重（三行逻辑不配一个独立类），委托是唯一'行为数据化'的轻量手段——就像 SqlConnection 是 DatabaseService 的唯一轻量选择一样，不是'选了委托'，是'要写 Subscribe 这种机制除了委托没别的轻量选项'。"**
> — 项目 Program.cs 阅读笔记 §5.9

**匹配精度**：这句话精确解释了为什么 EventActionDispatcher 用 `Func<PipelineEvent, Task>` 委托而非 `IEventHandler` 接口。每个订阅者当前只有 3 行日志逻辑——为一个 3 行的行为创建一个类（10 行模板 + 接口实现）是过度设计。委托把"行为"当"数据"存进 `_subscriptions` 字典，这是唯一能在注册阶段（Program.cs 启动时）灵活定义行为、在运行时按标签匹配执行的轻量机制。

## 九、确定性规则 vs LLM

### 9.1 两级判断体系

**技术锚点**：`Agent1/Program.cs#L381-385`

```csharp

services.AddSingleton<ComplianceRuleEngine>();       // 合规规则引擎
```

> **"DeterministicRuleEngine 存在的理由只有一个：化工安全的最终裁定不能依赖概率。LLM 可能产生幻觉——把'易燃'说成'不燃'，把'甲类'说成'乙类'。但规则引擎说'苯存储温度 ≤ 40°C'——这句话没有温度参数、没有随机种子、没有置信度，只有 true/false。在安全关键系统里，确定性不是偏好，是底线。"**

## 十一、Token 预算管理

### 11.1 "超预算就跳过，不硬撑"

**技术锚点**：`Agent1/Services/Eval/EvalEngine.cs#L177-195`

```csharp
var estimatedTokens = budgetManager.EstimateTokens(systemRole)
    + budgetManager.EstimateTokens(promptWithoutQuery)
    + budgetManager.EstimateTokens(tc.Query)
    + toolNames.Sum(n => budgetManager.EstimateToolTokens(n, "", 1));

    result.error = $"Token 预算超限: {estimatedTokens + 500} > {budgetManager.EffectiveBudget}";
```

> **"Token 预算不是'能跑就跑'，是'跑不动就诚实跳过'。在 8K 上下文的 Qwen3 上做 7 工具全量评测，一条用例的 prompt + 工具定义就可能吃掉 2000+ tokens——如果不做预算检查，硬撑的结果不是'慢'，是'输出截断'或'工具定义被吃掉'，评测数据直接作废。"**
> — 项目 EvalEngine.cs#L177-195

**匹配精度**：这句话精确对应 TokenBudgetManager 的两步工作流：Step 1 按 intent 裁剪工具集（info_query 6 工具 ~500 tokens vs compliance_judgment 5 工具 ~800 tokens），Step 2 预估总消耗。如果超预算，`continue` 跳过而非硬跑——因为硬跑的代价不是"慢一点"，而是输出截断导致评测结果完全不可靠。这是 T13 无状态架构的核心优化之一。

## 十二、哈希链审计

### 12.1 每条日志 = SHA256(上一条哈希 + 本条内容)

**技术锚点**：`Agent1/Services/Infrastructure/DatabaseService.cs#AddAuditLogAsync`

```csharp
// 审计日志不是孤立记录，是哈希链：
// chainHash = SHA256(previousChainHash + currentContent)
// → 任何一条日志被篡改，后续所有哈希全部失效
```

> **"审计日志的可信度不来自'存了'，来自'改了就能被发现'。哈希链让每一条日志都依赖于所有前序日志——改中间一条，后面所有哈希全部断裂。这是'不可篡改'的数学保证，不是运维纪律。"**
> — 项目 DI 注册表 §A·L135-139

**匹配精度**：这句话精准区分了"存库"和"可审计"的本质差异。普通审计日志只保证"存了"，哈希链保证"存了且不能改"。SHA256 的单向性和雪崩效应（`previousChainHash` 变一个字符，`chainHash` 面目全非）是数学级别的防篡改——不是靠运维纪律（"不要改日志"），而是靠密码学设计（"改了必被发现"）。
