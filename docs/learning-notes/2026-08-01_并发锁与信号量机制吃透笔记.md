## 零、认知基准：锁的正常工作原理

### 0.1 信号量是什么（以 SemaphoreSlim 为例）

`SemaphoreSlim(2, 2)` = 一个有 **2 张通行证**的计数器（初始 2，上限 2）：

```
请求进来 → WaitAsync(超时)
  有通行证(计数>0)  → 计数 -1，立即进入业务
  无通行证(计数=0)  → 排队等待；期间有人 Release 则被唤醒；超时未获证 → 返回 false
业务结束 → finally { Release() } → 计数 +1，唤醒一个排队者
```

关键 API 契约：
- `WaitAsync(0)`：一毫秒都不等，拿不到立刻失败（增量闸机用此实现"已在跑→409"）
- `WaitAsync(5s)`：最多排队 5 秒，超时返回 false（`_llmGate` 用此实现"服务繁忙→503"）
- **返回值必须检查**：false = 没拿到证，绝不能继续走业务

### 0.2 互斥的唯一前提：对象身份

**"锁"不是一个行为，而是一个对象**。判断两段代码是否互斥，只看一条：**它们拿到的引用是不是同一个对象**。

```
一份锁对象（全进程共享）→ 真互斥
N 份锁对象（各自 new）  → 各管各的 = 等于没锁
```

两个 `new SemaphoreSlim(2,2)` 对象，即使代码一模一样，也是两把完全独立的锁。

### 0.3 生命周期决定锁的共享范围（本项目实锤）

ASP.NET Core 默认 **Controller 是瞬时态（Transient）**——每个 HTTP 请求都 `new` 一个全新 Controller（`Program.cs#L315` 只有 `AddControllers()`，无自定义激活器）。

| 生命周期 | 创建时机 | 共享范围 | 锁放这里的后果 |
|---|---|---|---|
| Transient 瞬时 | 每次解析都 new | 谁也不共享 | ❌ 锁只锁自己一个请求 |
| Scoped 作用域 | 每请求一个 | 请求内共享 | ❌ 锁只锁同一次请求 |
| Singleton 单例 | 进程启动一次 | **全进程共享** | ✅ 真互斥 |

项目现状（`Program.cs#L107`）：`AddSingleton(new SemaphoreSlim(2,2))` —— 全进程只有一把锁，所有请求注入同一引用。

## 一、真互斥的代价：它"限制"了什么

锁的本质 = **用并发能力换数据安全**。真互斥生效后的代价：

| 代价 | 说明 | 项目里的样子 |
|---|---|---|
| 吞吐量封顶 | 并发数被压到锁容量上限，多出来的请求只能排队 | `_llmGate` 限 2 并发 → 第 3 个请求必须等，等不到就 503 |
| 延迟增加 | 每个请求多了一段排队时间 | 用户体感：高峰期审核变慢 |
| 排队风暴 | 排队者超时后立刻重试，重试又排队，恶性循环 | 前端拿到 503 + `retryAfter:10` 就是为此设计——强制客户端冷却 |
| 瓶颈转移 | 锁本身成为热点：竞争开销可能反超业务 | 若锁粒度太大，无关请求互相拖累 |

一句话：**真互斥 = 用"最多 2 个并行"换"绝不超过 2 个并行"**。对 CPU 推理这种硬资源（llama.cpp 单机），这个代价必须付——超并发不是"慢"而是"崩"。

## 二、没锁的后果：项目真实案例（Bug-038 增量闸机）

### 2.1 修复前的时间线（竞态交错）

```
管理员 09:00:01 点增量更新 → 请求A 开始扫描
管理员 09:00:02 又点一次   → 请求B 也进来，两个任务同时跑
请求A: 对文件 X 执行 DELETE（删旧）
请求B: 对文件 X 执行 DELETE（删旧）→ 删 0 行
请求A: 执行 INSERT → ✅ 成功
请求B: 执行 INSERT → ❌ 23505 duplicate key（source_path UNIQUE 约束）
请求B 失败不记账 → 下轮又当"新增" → 又撞 → 死循环 🔁
```

### 2.2 没锁的典型后果清单

- **竞态交错**：两个请求的"先删后插"交错执行，中间态互相踩踏
- **重复写/唯一约束爆炸**：INSERT 撞 UNIQUE（项目实锤）
- **半写状态**：一个任务删了旧数据，另一个任务没写完就失败，DB 处于"既没旧也没新"的中间态
- **资源超载**：锁失效 → 并发无上限 → CPU/显存被打爆（`_llmGate` 若失效，3 个 CPU 推理同时跑，llama.cpp 直接卡死，类似 Bug-040 服务假死模式）

### 2.3 修复后（有锁）的对照

```
第二个请求 WaitAsync(0) 一毫秒都等不到 → 立刻抛 IncrementalAlreadyRunningException
→ 两个调用方 catch → HTTP 409「已有任务运行中」
```

互斥铁证：07-30 远程实测 3 个并发 curl → **1×200 + 2×409**。

## 三、六大坑（反直觉知识库 · 四要素格式）

### 坑 1：锁饿死（Starvation）⭐ 最危险

- **现象**：永远有请求拿不到锁，服务 CPU 空闲但全部请求被拒（假死）
- **根因底层机制**：通行证被持续占用或丢失，计数只减不增最终归零。与死锁的区别：死锁是"互相等、谁都动不了"（僵局）；饿死是"别人一直能进、你永远等不到"（单方挨饿）
- **错误示例（成因A：Release 丢失）**：

```csharp
// ❌ Release 不在 finally，中途 return/抛异常就漏还
if (!await _llmGate.WaitAsync(TimeSpan.FromSeconds(5))) return 503;
try {
    if (某些条件) return Ok("提前返回");   // 这里 return → 下面的 Release 永远不执行
    await DoLlmInference();
} catch { return 500; }                     // 异常一样漏还
_llmGate.Release();                         // ❌ 永远到不了
```

- **标准规避模板（成因A）**：

```csharp
// ✅ finally 保证"无论成败必还证"——项目现状 ComplianceController.cs#L134-210
try { ...业务... } finally { _llmGate.Release(); }
```

- **成因B：持锁时间失控**——持锁者业务跑 10 分钟，排队者 5 秒超时全部 503。不是锁坏了，是"锁容量(2) × 单次时长"算不过业务流量（本质是容量规划问题）
- **推演饿死后果**：100 个请求里 3 个走提前 return 路径 → 计数永久减少 → 后续全部拿不到锁 → 503 海啸 → 服务假死

### 坑 2：死锁（互相等钥匙）

- **现象**：相关请求全部永久卡死
- **根因**：两个任务各持一把锁、互相等对方的那把

```
线程1: 持有 锁A → 等待 锁B
线程2: 持有 锁B → 等待 锁A     → 永远卡死
```

- **项目对照**：`Program.cs#L116` 有 `Lazy<T>` 破解循环依赖的注释——"互相引用"一旦发生在锁上就是死锁
- **规避模板**：多把锁必须全局固定获取顺序（永远先 A 后 B）；所有 `WaitAsync` 加超时（本项目统一 5 秒超时 = 防死锁保险丝，等不到就放弃，不让僵局无限持续）

### 坑 3：SemaphoreSlim 不可重入（自锁）

- **现象**：同一逻辑链里第二次 WaitAsync 把自己堵死
- **根因**：`Monitor`/`lock` 可重入（同一线程重复进入没问题），`SemaphoreSlim` **不可重入**

```csharp
await _llmGate.WaitAsync();   // 计数 2→1 ✅
await _llmGate.WaitAsync();   // 计数 1→0 ✅（还能拿到）
await _llmGate.WaitAsync();   // 计数 0 → ❌ 自己等自己 → 死锁/超时
```

- **触发场景**：A 方法拿锁，B 方法（被 A 调用）又拿同一把锁
- **规避模板**：一个信号量只在一个层级的入口拿一次；需要重入语义用 `AsyncLock` 包装或 `lock`

### 坑 4：异步代码里用阻塞等待

- **现象**：async 链路整体卡死（配合 SynchronizationContext 时）
- **根因**：在 async 方法里同步阻塞等待异步锁，阻塞了上下文线程，而锁的释放又依赖该上下文
- **错误示例**：`_llmGate.Wait();` 或 `.Result` / `.Wait()`
- **规避模板**：全程 `await _llmGate.WaitAsync(TimeSpan.FromSeconds(5))`（本项目全用 await，未踩此坑）

### 坑 5：跨进程/多实例部署 → "N 份锁"问题复现

- **现象**：限流上限按副本数翻倍
- **根因**：`SemaphoreSlim` 是**进程内**锁。2 个 API 副本 = 2 把独立锁 = 实际并发 4

```
进程1 的锁 Ω₁（2 张证）  进程2 的锁 Ω₂（2 张证）
→ 全系统实际并发 = 4，2 并发限制失效
```

- **规避模板**：多实例部署换**分布式锁**（Redis SETNX / PostgreSQL advisory lock）；单实例部署（项目现状：远程一台 AutoDL）进程内锁够用——这是"进程内锁"成立的前提边界

### 坑 6：锁粒度与重试风暴

- **粒度太大**：把不需要互斥的读操作也锁了 → 无关请求排队 → 吞吐雪崩
- **重试风暴**：503 后客户端立刻重试（不等 retryAfter）→ 排队者越来越多 → 锁队列恶性膨胀
- **规避模板**：锁只包最小临界区；超时响应带 `retryAfter` 冷却指令（项目 `retryAfter = 10` 字段）

## 四、自检清单（拿到任何锁代码先过一遍）

```
□ WaitAsync 返回值检查了吗？超时/取消后有没有误入业务？（拿不到必须 return，不能继续走）
□ Release 在 finally 里吗？所有 return/异常路径都覆盖吗？
□ 同一把锁会被重入（重复 WaitAsync）吗？
□ 多把锁时获取顺序全局一致吗？都有超时保险丝吗？
□ async 环境里用的是 await 而不是 .Wait()/.Result 吗？
□ 部署是单实例吗？（多实例 → 需要分布式锁）
□ 锁的容量 × 单次持锁时间 > 业务峰值流量吗？（防饿死）
□ 超时响应给了 retryAfter 冷却吗？（防重试风暴）
```

## 六、可复用结论（一句话版）

1. 锁的互斥范围由**对象身份**决定：全进程一份 = 真互斥；N 份 = 没锁
2. 共享状态（锁/计数器/缓存）必须 Singleton（或 static）；请求级数据绝不能放 Singleton（反着错会全局串数据）
3. 锁的正确写法三件套：**WaitAsync 查返回值 + finally Release + 超时保险丝**
4. 最危险的坑是"饿死"：Release 漏一处，服务假死一片；最隐蔽的坑是"不可重入"与"跨进程"
