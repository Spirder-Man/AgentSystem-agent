# 代码阅读顺序与 DI 从零设计方法论

> 归档日期：2026-08-01
> 背景：用户在熟悉 ASP.NET Core DI（曾写过 WMS 系统）基础上，面临两个问题：① 阅读本项目代码的最佳顺序；② 如何从零把业务规则设计进 DI 容器。
> 遵循：第一宪法（正常基准先行、人脑认知规律）、第二宪法（底层疑惑自研吃透）

---

## 一、核心认知：阅读与设计是两个相反方向

| 维度 | 阅读（理解已有系统） | 设计（从零构建新系统） |
|------|---------------------|----------------------|
| 方向 | **自顶向下**：入口 → 依赖树 → 数据 | **自底向上**：业务规则 → 服务边界 → 注册 |
| 起点 | Program.cs（DI 注册全景 = 系统地图） | 业务用例（要解决什么问题） |
| 主线 | 请求链路（血管） | 依赖关系（谁依赖谁） |
| 终点 | 存储层/工具层 | Program.cs 注册表 + Controller |
| 产出 | 认知地图（血谱回写） | 可运行的系统 |

**关键**：不能用阅读的顺序去设计，也不能用设计的顺序去阅读。两者在 Program.cs 交汇——阅读是"逆着注册表找实现"，设计是"顺着业务往注册表填"。

## 二、阅读顺序方法论（自顶向下五步）

### Step 0：先读血谱（导航图前置，不是后置）

```
docs/architecture/系统血谱.md
```

- 血谱 = 已经存在的导航图，**第一步就读它**，用它定位要读的血管，而不是读完代码再"结合理顺"
- 血谱告诉你：4 条 L0 大动脉（数据从哪来到哪去）、5 条 L1 静脉（关键机制）、病灶表（阅读陷阱预警）
- 带着血谱的血管视角读代码：每读一个文件，问自己"这属于哪条动脉/静脉？血谱说的和代码一致吗？"

### Step 1：Program.cs（DI 注册全景 + 中间件全序）

```
Agent1.Api/Program.cs（661 行）
```

Program.cs 是整个系统的"地图"，一次读完获得四张表：

| 要提取的信息 | 具体内容 | 本项目的证据 |
|---|---|---|
| ① 服务注册表 | 每个服务注册了哪个生命周期 | L107 `AddSingleton(new SemaphoreSlim(2,2))`；AgentDialog/ResponseCacheService 等单例；Controller 瞬时 |
| ② 中间件全序 | 10 个中间件顺序 | L366-394：异常兜底→RequestId→限流→指标→Swagger→CORS→认证→Token黑名单→授权 |
| ③ 配置绑定 | .env + appsettings.json → AppConfig | Config/AppConfig.cs |
| ④ 入口端点 | 健康检查/特殊路由 | /health、/knowledgebase/incremental-update |

### Step 2：挑主干链路（不贪多，按业务线分优先级）

**不要**平铺 15 个 Controller 全读——按血谱 4 条业务线走，优先级排序：

| 优先级 | 业务线 | 链路（文件路径） | 覆盖机制 |
|---|---|---|---|
| P0 | 合规审核（主业务） | ComplianceController → AgentDialog → LlmService → ChemicalComplianceTools → 三级降级瀑布 | FC 策略、双通道管线、核验、缓存、并发闸门、审计 |
| P1 | 知识库查询 | KnowledgeBaseController → ChemicalRAG → HybridKnowledgeBaseService → PG+向量 | 双加载管道、BM25/向量、RRF 融合 |
| P2 | 应急响应 | EmergencyController → EmergencyResponseService → 工具层 | 确定性流程、降级路径 |
| P3 | 审计追踪 | AuditController → AuditService（哈希链） | 数据完整性、只追加 |

读完 P0 就覆盖了系统 60% 的机制；其余 Controller 按需再看，不必求全。

### Step 3：逐层下钻（沿字段引用走，一条链路一口气到底）

以 P0 合规审核为例的阅读顺序：

```
① ComplianceController（入口：三端点 + summary）
   → 每个字段追问：谁注册的？什么生命周期？谁在用？（见字段×端点矩阵法）
② AgentDialog（编排核心）
   → ExecuteEvalFastAsync（API快速通道）→ ExecuteEvalInternalAsync → ApplyDecoupledPipeline
   → 另一条支线 ExecuteAsync（CLI 6步流水线）——对比双路径差异
③ LlmService（LLM 门面）
   → FC 策略声明、流式+死循环检测、熔断器、重试
   → InvokeEvalWithToolsAsync（评测裁剪：临时 Kernel）
④ ChemicalComplianceTools（工具层）
   → 三级降级瀑布 Level 1 SQLite → Level 2 PG门面 → Level 3 硬编码字典
⑤ 存储层
   → ChemicalDatabaseService（SQLite）/ ChemicalKnowledgeGraph（PG 内存图）
```

**每层阅读时带"三问清单"**：
1. 这个依赖是谁在 Program.cs 注册的？什么生命周期？
2. 它有没有内部状态？（有状态 → 为什么能跨请求安全？）
3. 血谱说它属于哪条血管？与代码是否一致？（不一致 → 登记病灶）

### Step 4：交叉验证 + 回写血谱

- 发现图码不符 → 以代码为准，登记病灶（血谱第七节）
- 发现新机制/新血管 → 回写血谱（维护纪律：改变数据源/消费者/降级顺序必须同批次更新）

## 三、从零设计方法论（自底向上六步）

> 用户真正的问题：已有 WMS 的 DI 使用经验，但缺"从业务规则反推注册设计"的流程。

### Step 1：先写业务规则（不碰 DI）

把业务逻辑写成**纯 C# 类**，不依赖任何框架——用本项目例子：

```csharp
// 合规规则引擎：输入巡检数据 → 输出合规态势（纯计算，无 IO）
public class ComplianceRuleEngine
{
    public ComplianceOverview BuildOverview(assets, findings, lastScan) { ... }
}
```

判断标准：这个类**能不能不启动 Web 项目就跑单元测试**？能 → 规则层合格。

### Step 2：识别服务边界（三类服务）

| 类型 | 特征 | 本项目例子 | DI 决策 |
|---|---|---|---|
| 领域服务 | 承载业务规则，可无状态 | ComplianceRuleEngine、AgentDialog（有状态） | 注入给 Controller |
| 基础设施服务 | 封装外部资源（DB/LLM/缓存/HTTP） | LlmService、ChemicalDatabaseService、ResponseCacheService | 注入给领域服务 |
| 工具类 | 无状态纯函数 | ConclusionVerifier、SensitiveDataMasker、OutputSanitizer | **不注入，静态调用** |

### Step 3：画依赖图（依赖抽象，不依赖实现）

```
Controller → 领域服务 → 基础设施服务 → 存储/外部
```

- 上层依赖**接口**（ILlmService），不依赖具体类（LlmService）——本项目的 `_llmService as LlmService` 强转是反例
- 工具类不进入依赖图（静态调用）

### Step 4：生命周期决策（三问速查表）

对每个要注册的服务问三个问题：

| 问题 | 答"是" → | 答"否" → |
|---|---|---|
| ① 它有内部状态且需要跨请求共享吗？ | **单例**（缓存、并发闸门、有状态编排器） | 继续问 ② |
| ② 它内部状态与请求绑定吗（会话/连接）？ | **作用域**（DbContext 模式） | 继续问 ③ |
| ③ 它完全无状态、创建廉价吗？ | **瞬时**（纯计算服务） | 单例（避免重复创建） |

本项目实战对照（与并发锁笔记互证）：

| 服务 | 状态 | 生命周期 | 原因 |
|---|---|---|---|
| SemaphoreSlim `_llmGate` | 有（信号量计数） | **单例** | 非单例则并发请求各拿各锁，互斥失效（Bug-038 教训） |
| ResponseCacheService | 有（缓存字典） | **单例** | 缓存必须跨请求共享才有意义 |
| AgentDialog | 有（_lastToolResults 等） | **单例** | 私有状态跨调用透出（静脉4 #9），且创建开销大 |
| ComplianceRuleEngine | 无 | 单例即可 | 无状态但创建廉价，单例省构造 |
| ComplianceController | 无 | **瞬时**（默认） | 每请求新建，字段只是容器给的引用 |

### Step 5：注册到容器

```csharp
// Program.cs
builder.Services.AddSingleton(new SemaphoreSlim(2, 2));          // 有状态共享 → 单例
builder.Services.AddSingleton<AgentDialog>();                     // 有状态编排器 → 单例
builder.Services.AddScoped<ILlmService, LlmService>();            // 接口→实现，作用域
builder.Services.AddControllers();                                // Controller 默认瞬时
```

### Step 6：验证

- `dotnet run --project Agent1.Api` 独立启动（不依赖脚本）
- 三个生命周期是否正确：写测试验证单例引用同一实例（`ReferenceEquals` 断言）
- 规则层单元测试先行（Agent1.Tests/ 内 xUnit，不写 scripts/）

## 四、阅读时的"字段 × 端点矩阵法"（本项目的实践工具）

读 Controller 时，不要逐行读，先画矩阵再读：

```
| 字段 | 端点A | 端点B | 端点C | 用途 |
|------|-------|-------|-------|------|
| _cache | ✅L128 | ✅L241 | ✅L316 | 缓存先查后写 |
| _inspectionRepo | ✅L78 | — | — | 仅 summary 用 |
```

方法：Grep 字段名 → 记录行号 → 填矩阵。**矩阵即认知**——一眼看出"哪个依赖被哪个端点独占"，这是理解 Controller 为什么注入这 10 个依赖的最快路径（已实践于 ComplianceController，发现 hazard/storage 端点不核验的盲区）。

## 附：方法论一句话

- **阅读**：Program.cs 开地图 → 跟 4 条血管走到底 → 边读边对血谱 → 差异回写
- **设计**：业务规则先落地（不碰框架）→ 分服务边界 → 画依赖图 → 三问定生命周期 → 注册 → 测试验证
- **共同铁律**：有状态共享 → 单例；无状态工具 → 静态；依赖抽象不依赖实现；血谱前置不后置
