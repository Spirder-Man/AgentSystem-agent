## 1. 合规结论完整数据流

```
用户输入
  │
  ▼
IntentRouter.Route()                         ← static 纯逻辑
  │
  ▼
AgentDialog.ExecuteChemicalComplianceAsync()  ← AgentDialog private
  │
  ├─ SK Auto FC (LLM 选择工具)
  │    └─ ILlmService.InvokeStreamWithRetryAsync()
  │
  ├─ 工具执行 (DB / RAG)
  │    └─ ChemicalComplianceTools (无接口具体类)
  │
  ├─ ApplyDecoupledPipeline()                 ← AgentDialog private
  │    ├─ ComplianceFactExtractor.Extract()   ← static 纯逻辑
  │    ├─ OutputSanitizer.Sanitize()          ← static 纯逻辑（硬拦截）
  │    ├─ FactAssembler.Build()               ← static 纯逻辑（确定性渲染）
  │    └─ ResponseMerger.Merge()              ← static 纯逻辑
  │
  └─ 返回: (answer, toolCalls, warnings)

评测时 (EvalEngine):
  │
  ├─ CheckConclusion()                        ← static 纯逻辑（三级判定）
  │    ├─ Level 1: [判定:is_compliant=...] 标签匹配
  │    ├─ Level 2: 法规编号匹配
  │    └─ Level 3: 关键词回退
  │
  ├─ ConclusionVerifier.VerifyAsync()         ← static, 需要 IKnowledgeBaseService
  │    └─ KB 反向检索验证（仅 compliance_judgment 路径）
  │
  └─ ValidateGbNumberHallucinations()         ← static 纯逻辑
       └─ GB 编号格式/映射交叉验证
          （仅在 EvaluateFaithfulnessAsync 降级路径中调用！）
```

## 2. 关键耦合点分析

### 2.1 EvalEngine ↔ AgentDialog（高耦合，无接口）

```
EvalEngine (1290行)
  ├─ 依赖 AgentDialog（具体类，无接口）
  │    └─ ExecuteEvalPerCaseAsync(userInput, toolNames, isInfoQuery) → string
  ├─ 依赖 ILlmService（有接口 ✓）
  ├─ 依赖 IKnowledgeBaseService（有接口 ✓）
  └─ 依赖 ReflectionVerifier?（具体类，nullable）
```

**影响**: EvalEngine 无法脱离 AgentDialog 独立测试。**但这不是当前准确率瓶颈** — CheckConclusion 是 static 纯逻辑，不受此耦合影响。

### 2.2 CheckConclusion — 纯后置判定（无预防能力）

```
位置: EvalEngine.CheckConclusion() [static, 1082-1209行]
输入: LLM 输出文本 + 预期结论
输出: bool (匹配/不匹配)

问题: 它只判断"LLM说对了没有"，不阻止 LLM 说错。
```

**已知边界风险**（来自代码注释）:
1. 标签与关键词结论冲突时的优先级（当前：标签优先）
2. "可以"在条件句中的多义性
3. "不合规"出现在免责声明中而非结论句中

### 2.3 ValidateGbNumberHallucinations — 存在但未在主流中调用

```
调用链:
  EvaluateFaithfulnessAsync
    └─ if (_reflectionVerifier == null)         ← 仅在降级路径
         └─ ValidateGbNumberHallucinations()    ← P0 FIX Bug3

  BuildCorrectedPrompt                           ← 仅在 Reflection 修正用
    └─ ValidateGbNumberHallucinations()
```

**问题**: 这个方法是"纠正 GB 编号幻觉"的核心工具，但它：
- **不在主流 CheckConclusion 中被调用**
- 不在 ApplyDecoupledPipeline 中被调用
- 只在没有 ReflectionVerifier 时才运行（即测试/降级场景）

### 2.4 OutputSanitizer — 硬拦截防线（已工作，但不完美）

```
位置: OutputSanitizer.Sanitize() [static, 46-103行]
机制: 白名单过滤 — 不在工具返回的法规列表中的 GB 编号被硬删除
```

**优点**: 确定性，不依赖 LLM，已是最后防线
**局限**: 
- 白名单来自 `ComplianceFactExtractor.Extract()` 提取的工具返回结果
- 如果工具返回的法规本身就缺少某些编号（如 DB 只返回了 GB 30000.7 但 LLM 需要引用 GB 30000.14），Sanitizer 不会补充
- Sanitizer 只"删除"，不"纠正"

### 2.5 ConclusionVerifier — KB 反向验证（后置，仅部分路径）

```
调用位置: EvalEngine.RunComplianceEvalAsync [line 332-337]
  └─ if (tc.Intent == "compliance_judgment")
       └─ ConclusionVerifier.VerifyAsync()
            └─ KB 反向检索每个法规编号

特点:
  - 仅在 compliance_judgment 意图下调用
  - info_query 意图不调用
  - kbService 为 null 时跳过
  - GetDocumentCount() == 0 时跳过
```

## 3. 准确率瓶颈推断

基于评测集结构和代码分析，当前 65% 结论准确率的主要瓶颈：

| 瓶颈 | 影响的 case 类型 | 根因 | 占比估计 |
|------|------------------|------|----------|
| GB 编号幻觉 | C001-C015（危险类别查询）| LLM 发明或混淆 GB 编号；ValidateGbNumberHallucinations 未在主流调用 | ~40% |
| 合规判断关键词误判 | D001-D020, F001-F007 | "不可以/不合规"在条件句/免责声明中被误判 | ~20% |
| 安全距离数值丢失 | E001-E008 | LLM 回答丢失工具返回的具体距离数值 | ~10% |
| 多法规编号只返回部分 | C003-C005 等 | LLM 只提第一个法规编号，忽略其余 | ~15% |
| 工具未触发/Error | 全部 | SK Auto FC 未调用工具；降级路径兜底 | ~10% |
| 其他 | - | - | ~5% |

## 4. 三条改进路径

### 路径 A: 预防性 — 强化 Prompt 注入工具结果（风险低，效果中）

**原理**: 在 `ExecuteEvalPerCaseAsync` / `ExecuteEvalInternalAsync` 构造 prompt 时，将工具返回的 GB 编号列表显式注入 `{UserInput}` 尾部。

**代码改动**:
- AgentDialog.cs: `ExecuteEvalPerCaseAsync` 方法 (~660行附近)，在调用 LLM 前将工具返回的法规编号追加到 userInput
- 或更彻底: 在 `ExecuteChemicalComplianceAsync` 构造 prompt 时注入

**改动范围**: ~10 行
**风险**: 低 — prompt 格式变更，需回归测试
**预期收益**: 减少 GB 编号幻觉 ~50%

### 路径 B: 后置强化 — CheckConclusion 中调用 ValidateGbNumberHallucinations（风险低，效果中）

**原理**: 在 `CheckConclusion` 判定前，先调用 `ValidateGbNumberHallucinations` 对 LLM 输出做 GB 编号交叉验证，发现幻觉直接 return false。

**代码改动**:
- EvalEngine.cs `CheckConclusion` 方法 (~1082行)
- 在 info_query 路径中，在法规编号匹配前调用 `ValidateGbNumberHallucinations`
- 如果检测到格式错误或幻觉，直接返回 false

**改动范围**: ~15 行
**风险**: 低 — 仅影响判定逻辑，不影响输出
**预期收益**: 减少 GB 编号幻觉 ~60%

### 路径 C: 管线级 — 在 OutputSanitizer 后增加 GB 纠正层（风险中，效果高）

**原理**: 创建 `GbNumberCorrector` 组件，在 `ApplyDecoupledPipeline` 的 OutputSanitizer 之后、ResponseMerger 之前，对输出做 GB 编号修正（格式修正 + 映射修正）。

**代码改动**:
- 新建 `Agent1/Services/Compliance/GbNumberCorrector.cs` (~60行)
- AgentDialog.cs `ApplyDecoupledPipeline` (~810行): 插入新步骤
- 需处理 `ChemicalSubstanceDatabase` 的 DB 查找

**改动范围**: ~80 行新代码 + ~5 行现有代码
**风险**: 中 — 新增管线步骤，可能改变输出格式
**预期收益**: 减少 GB 编号幻觉 ~80%

## 5. 推荐实施顺序

```
第一轮: 路径 A + 路径 B（低风险快速见效）
  预期: 65% → 72-75%

第二轮: 路径 C（中等风险，补齐剩余缺口）
  预期: 72-75% → 78-82%
```

**理由**: 路径 A 和 B 改动范围小、风险低、不涉及新组件，可以快速验证效果。路径 C 作为补充，在第一轮效果不足时启用。
