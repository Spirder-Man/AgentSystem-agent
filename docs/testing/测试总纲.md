### 2.4 Mock 测试模式说明

项目中使用了两种 Mock 模式，各司其职：

#### 2.4.1 后端 Moq Mock（xUnit 单元测试）

已有 13 个测试类中，以下使用了 Moq 框架 Mock 外部依赖：

| 测试类 | Mock 了什么 | Mock 原因 |
|--------|-----------|----------|
| `LlmServiceTests` | `ILlmService` + `HttpClient` | 不依赖真实 llama.cpp，快速验证 LLM 调用逻辑 |
| `CircuitBreakerTests` | 熔断器状态机 | 纯逻辑验证（熔断/半开/恢复），不需真实故障 |
| `KnowledgeBaseServiceTests` | `IDatabaseService` | 验证检索逻辑，不依赖 PostgreSQL |
| `ErrorPathTests` | 异常场景注入 | 验证降级策略，不需要真实 I/O 崩溃 |
| `ToolServiceTests` | `IToolService` | 工具注册/调用逻辑隔离测试 |
| `MetricsCollectorTests` | 指标采集管道 | 独立验证采集逻辑 |
| `IntentRouterTests` | 路由依赖 | 意图路由纯逻辑 |
| `SensitiveDataMaskerTests` | 数据源 | 脱敏规则纯函数验证 |

> **Mock 原则**：测逻辑时不调真实外部服务（LLM/DB/HTTP），保证测试 <30s 跑完。Mock 行为必须与真实行为一致（行为契约）。

#### 2.4.2 前端 MSW Mock（开发用，非测试）

`agent1-web/src/mocks/` 目录使用 **MSW (Mock Service Worker)** 在浏览器端拦截请求：

```
agent1-web/src/mocks/
├── server.ts          ← MSW 服务启动（浏览器/Node 双端）
├── handlers.ts        ← 请求拦截规则（365 行）
└── data/
    ├── compliance.ts  ← 合规审核假数据
    ├── inspection.ts  ← 巡检假数据
    └── tickets.ts     ← 工单假数据
```

- **用途**：前端独立开发时不依赖后端 API，浏览器拦截 `fetch`/`axios` 返回假 JSON
- **状态**：生产代码（非测试代码），但**当前 0 测试覆盖**
- **风险**：handler 返回数据结构可能与 `types/api.ts` 不一致、拦截规则路由匹配错误

### 9.2 组件清单

#### 远程端 (AutoDL RTX 3090 / Ubuntu 22.04)

| 脚本 | 路径 | 触发方式 | 产出 |
|------|------|---------|------|
| **post-deploy-eval.sh** | `scripts/post-deploy-eval.sh` | cron 每日 3:00 | `eval_reports/YYYYMMDD_HHMM/summary.json` |
| **post-deploy-analyze.sh** | `scripts/post-deploy-analyze.sh` | cron 紧随 eval 后 | `eval_reports/YYYYMMDD_HHMM/analysis.md` + `log_slices/` |

**Cron 配置内容**：
```bash
# 每日凌晨3点：评测 → 分析
0 3 * * * ADMIN_PWD=xxx bash post-deploy-eval.sh >> cron_logs/post-deploy-$(date +\%Y\%m\%d).log 2>&1 && ADMIN_PWD=xxx bash post-deploy-analyze.sh >> cron_logs/analyze-$(date +\%Y\%m\%d).log 2>&1

# 每小时：API 心跳
0 * * * * curl -sf http://localhost:5000/health/live -o /dev/null || echo "$(date): FAIL" >> cron_logs/heartbeat.log
```

> 注意：AutoDL 容器重启后需手动执行 `service cron start` 恢复 cron 服务。

**Windows 计划任务配置**：
