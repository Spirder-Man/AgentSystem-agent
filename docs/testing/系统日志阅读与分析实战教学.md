## 第一课：日志结构解析

### 1.1 解剖一条日志的每个字段

以 **日志①** 第 7 行为教材：

```
[2026-06-23 00:23:04.689 INF] LAPTOP-40G212RC RunId=0509e705 [Pipeline] 开始 | TraceId=ce1bc382 | 输入长度=10 | 输入=苯和丙酮能一起储存吗
```

让我们逐字段拆解：

```
┌────────────────────────────────── 时间戳（精确到毫秒） ──────────────────────────────────┐
│                                                                                          │
│  [2026-06-23 00:23:04.689 INF] LAPTOP-40G212RC RunId=0509e705 [Pipeline] 开始 | ...
│          ↑              ↑            ↑              ↑             ↑           ↑
│          │              │            │              │             │           │
│        日期         日志级别      机器名        运行实例ID    模块标签     消息体开始
│                                                                                          │
│  ...TraceId=ce1bc382 | 输入长度=10 | 输入=苯和丙酮能一起储存吗                            │
│         ↑                      ↑                  ↑                                      │
│   请求追踪ID             结构化键值对           结构化键值对                               │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

**逐个字段详解**：

| # | 字段 | 示例值 | 含义 | 为什么这样设计 |
|---|------|--------|------|---------------|
| 1 | **时间戳** | `2026-06-23 00:23:04.689` | 精确到毫秒的事件时间 | 毫秒级精度让你能计算任两步之间的耗时差（如：`00:23:14.198 - 00:23:04.689 = 9.509秒`） |
| 2 | **日志级别** | `INF` | Information（正常流程） | 五种级别：`VRB`(详细) → `DBG`(调试) → `INF`(信息) → `WRN`(警告) → `ERR`(错误) → `FATAL`(致命)。生产环境只输出 INF 及以上 |
| 3 | **机器名** | `LAPTOP-40G212RC` | 运行程序的计算机名 | 多机部署时区分日志来源。在 Docker 里会是容器 ID |
| 4 | **RunId** | `0509e705` | 程序本次启动的唯一标识 | 程序每启动一次生成一个新 RunId。同一次运行的所有日志共享同一个 RunId，用于区分"上次启动"和"这次启动"的日志 |
| 5 | **模块标签** | `[Pipeline]` | 产生日志的代码模块 | 约定用 `[模块名]` 格式，如 `[IntentRouter]`、`[Memory]`。让你不用看代码就知道日志来自哪个模块 |
| 6 | **TraceId** | `ce1bc382` | 单次请求的唯一追踪 ID | 8 位十六进制（GUID 前 8 位）。同一次请求的所有日志用同一个 TraceId。这是全链路追踪的金线 |
| 7 | **结构化字段** | `输入长度=10`, `输入=苯和丙酮...` | 键值对形式的上下文数据 | 不用解析自由文本，直接 `grep "输入长度=10"` 就能精确过滤。支持后续接入 ELK/Splunk 等日志分析平台的结构化查询 |

### 1.2 两种日志格式对比

本项目有两种日志输出格式，对应不同的使用场景：

**格式 A：Serilog 结构化日志**（日志①）
```
[2026-06-23 00:23:04.689 INF] LAPTOP-40G212RC RunId=0509e705 [Pipeline] 开始 | TraceId=ce1bc382 | 输入长度=10 | 输入=苯和丙酮能一起储存吗
```
- 特点：包含时间戳、级别、机器名、RunId、模块标签
- 用途：生产环境日志、ELK 分析、结构化查询
- 来源：`Serilog.Log.Information(...)` 调用

**格式 B：诊断双写日志**（日志②）
```
📦 正在测试数据库连接...
[15:06:03 INF] 📦 正在测试数据库连接...
```
- 特点：每条同时输出纯文本版 + Serilog 版（因此叫"双写"）
- 用途：开发调试、快速肉眼扫描
- 来源：`Console.WriteLine(...)` + `Serilog.Log.Information(...)` 并行调用

> **设计考虑**：双写的原因是在开发阶段，纯文本日志可以直接 `tail -f` 查看，不需要解析 Serilog 格式；同时保留结构化版本供自动化分析。生产部署时可以关闭 Console 输出，只保留 Serilog 文件输出。

### 1.3 符号前缀语义系统

从 **日志②** 中可以观察到一套完整的符号前缀系统：

```
✅  向量嵌入成功 (维度: 768)     ← 成功，一切正常
⚠️  中文配置不可用，使用simple配置  ← 警告，降级但不影响核心功能
❌  失败:   0                     ← 错误，功能受损
🚫  脏数据拦截: 来源=...          ← 主动拒绝（安全/质量策略触发）
⏭️  跳过:  1100 (空表单/模板)     ← 跳过，策略性忽略
📦  正在测试数据库连接...          ← 信息标记，提示当前阶段
🔗  RAG 知识库已注入               ← 信息标记，依赖就绪
📝  诊断日志双写已启用             ← 信息标记，配置确认
```

**判断规则**：

| 符号 | 是否需要处理 | 说明 |
|:----:|:---:|------|
| ✅ | 否 | 正常流程，无需关注 |
| ⚠️ | 关注 | 降级行为，理解影响后决定是否修复 |
| ❌ | **是** | 必须排查 |
| 🚫 | 视情况 | 如果拦截了该拦截的（如注入攻击），是好事；如果拦截了正常请求，是误报需修复 |
| ⏭️ | 否 | 策略性跳过，无需处理 |

## 第二课：链路追踪方法

### 2.1 TraceId 金线原则

**日志①** 中的 9 行日志记录了程序一次启动后的两件事情：

```
行号  RunId      TraceId     模块              动作
───   ────────   ────────    ──────────        ──────
1-3   0509e705   (无)        (系统启动)         程序启动 Banner
4-5   0509e705   (无)        (数据库初始化)     数据库连接成功
6     0509e705   0c68ec2f    [Pipeline]         安全拦截 ← 请求A
7     0509e705   ce1bc382    [Pipeline]         开始     ← 请求B
8     0509e705   ce1bc382    [IntentRouter]     意图归类 ← 请求B
9     0509e705   ce1bc382    [Pipeline]         完成     ← 请求B
```

**关键发现**：
- 行 1-5 没有 TraceId → 属于系统启动阶段，不是用户请求
- 行 6 的 TraceId=`0c68ec2f` → 一次被安全拦截的请求（只有开始+拦截，没有完成）
- **行 7-9 的 TraceId=`ce1bc382`** → 这就是我们要追踪的完整请求链路！

> **核心心法**：`grep "ce1bc382"` 就能看到这次请求的一切。

### 2.2 逐步追踪一条完整请求

以 `TraceId=ce1bc382` 为例，逐步还原发生了什么：

**第 1 步：请求开始**（行 7）
```

```
- **时间**: `00:23:04.689` — 记下这个起点时间
- **动作**: Pipeline 启动，生成 TraceId
- **输入**: `苯和丙酮能一起储存吗`（10 个字符）
- **对应代码**: [AgentDialog.cs:75-76](../../Agent1/Services/Dialog/AgentDialog.cs#L75-L76)

**第 2 步：意图路由**（行 8）
```

```
- **时间**: `00:23:04.787` — 距开始仅 `98ms`
- **动作**: 意图路由器分析输入，命中合规关键词 `"储存"`
- **决策**: 路由到 `ChemicalCompliance`（化工合规处理）
- **对应代码**: [IntentRouter.cs:66-67](../../Agent1/Services/Dialog/IntentRouter.cs#L66-L67)

> **验证方法**: 看关键词是否合理 → `"储存"` 确实匹配了用户问题中的 `能一起储存吗`，路由决策正确 ✅

**第 3 步：Pipeline 完成**（行 9）
```
[2026-06-23 00:23:14.198 INF] [Pipeline] 完成 | TraceId=ce1bc382 | 总耗时=9508ms | 意图=ChemicalCompliance | 工具调用=0 | 安全警告=0 | 路由=84ms | 上下文=2ms | 执行=9400ms | 输入安全=10ms | 输出安全=0ms
```

- **时间**: `00:23:14.198` — 距开始 `9508ms` (约 9.5 秒)
- **意图**: `ChemicalCompliance` — 确实走了合规处理流程
- **工具调用=0**: ⚠️ 异常信号！合规问题应该调用工具
- **耗时分解**: `执行=9400ms` 占 98.9%，是绝对瓶颈

> **异常发现**: `工具调用=0` 对于"苯和丙酮能一起储存吗"这类问题是不正常的。应该调用 `CheckStorageCompatibility` 工具。这说明工具调度的 Prompt 可能需要优化。

### 2.3 对比：一次异常请求的追踪

行 6 展示了一次被拦截的请求：
```
[2026-06-23 00:22:58.446 WRN] [Pipeline] 安全拦截 | TraceId=0c68ec2f | 原因=检测到潜在注入攻击: 匹配模式 "忽略之前的指令"
```

- **级别是 WRN 不是 ERR**：说明这是**预期的安全行为**，不是系统故障
- **TraceId 只有开始+拦截**：没有后续的"完成"日志，说明请求在安全检测阶段就被终止了
- **原因明确**：`匹配模式 "忽略之前的指令"` — 典型的 Prompt 注入攻击被正确拦截

> **判断方法**: 用 `grep "0c68ec2f" agent1-20260623.log` 验证，应该只有一条日志。一条开始+一条拦截 = 正常的安全阻断流程。

## 第四课：问题排查技巧

### 4.1 错误模式一：向量嵌入上下文超长

从 **日志②** 第 314-315 行：

```
⚠️ 向量请求失败 [InternalServerError]: {"error":"the input length exceeds the context length"}
⏭️ 向量生成失败，跳过向量库写入（BM25 已写入）
```

**排查五步法**：

```
Step 1 — 识别信号
  看见 ⚠️ + InternalServerError → 有异常但非致命

Step 2 — 读错误消息
  "the input length exceeds the context length"
  → 翻译：文本块超过了嵌入模型的上下文窗口限制
  → nomic-embed-text-v1.5 的默认上下文是 8192 tokens
  → 这个文本块超过了 8192 tokens

Step 3 — 看降级行为
  "跳过向量库写入（BM25 已写入）"
  → 系统有设计好的降级策略：
    ✅ BM25 索引仍然写入（全文检索不受影响）
    ❌ 向量库跳过（语义检索会遗漏这个文档块）
  → 影响范围：该文档块无法通过语义检索召回，但 BM25 关键词匹配仍可用

Step 4 — 统计影响范围
  grep "input length exceeds" full-20260605.log | wc -l
  → 全日志出现 15 次
  → 15/1241 = 1.2% 的块受影响，可接受

Step 5 — 确定修复方向
  选项 A: 减小 SemanticChunker 的 MaxChunkSize
  选项 B: 增大嵌入服务的 -c (context size) 参数
  选项 C: 当前影响小(1.2%)，暂不修复，记入技术债务
```

### 4.2 错误模式二：Pipeline 工具调用异常

回到 **日志①** 行 9 的 `工具调用=0`：

```
[Pipeline] 完成 | TraceId=ce1bc382 | 总耗时=9508ms | 意图=ChemicalCompliance | 工具调用=0
```

**诊断树**：

```
工具调用=0 但意图=ChemicalCompliance
│
├─ 可能原因 1: IntentRouter 误判
│   检查: 意图=ChemicalCompliance 是否正确？
│   验证: "苯和丙酮能一起储存吗" → 命中"储存"关键词 ✅ 路由正确
│   结论: 排除
│
├─ 可能原因 2: 工具调度 Prompt 未引导工具调用
│   检查: ComplianceCheckModule 的 Prompt 是否包含工具选择指引？
│   方法: 搜索代码中工具规划相关 Prompt
│   结论: 需要进一步审查 Prompt
│
├─ 可能原因 3: LLM 返回了不需要工具的结果
│   检查: 9508ms 的执行时间说明 LLM 推理确实执行了
│   但 LLM 可能直接回答了问题而不调用工具
│   结论: 最可能的原因
│
└─ 排查动作:
   1. 打开详细日志（设置 Serilog 级别为 Debug）

```

### 4.3 错误模式三：安全拦截误判排查

**日志①** 行 6：
```

```

**判断是否误报的三步法**：

```
Step 1 — 看输入内容
  需要找到这次请求的原始输入：
  grep "0c68ec2f" agent1-20260623.log
  → 如果有"开始"日志，看输入内容
  → 如果没有（本次情况），说明输入本身可能就是攻击

Step 2 — 看拦截模式
  "匹配模式 '忽略之前的指令'"
  → 这是经典 Prompt 注入模式（Prompt Injection）
  → 该模式在任何系统中都应该被拦截

Step 3 — 判断
  ✅ 这是正确的拦截，不是误报
  ✅ 不需要修改安全规则
  ✅ 如果同类拦截频繁，说明有人在尝试攻击，应告警
```

### 4.4 区分正常与异常速查表

### 6.1 单次请求性能画像

从 **日志①** 行 9 提取：

**分析**：
- 执行占 98.9%，说明系统开销极小（路由+上下文+安全 < 1.1%）
- 9400ms 在 GPU 模式下对应约 1-2 次 LLM 推理调用（Qwen3-8B 的典型推理延迟 ~5s/次）
- `输入安全=10ms` 说明安全检测是基于正则/关键词匹配，不是用 LLM 做检测（否则会是秒级）
