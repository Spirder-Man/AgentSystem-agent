## 一、日志体系全景

本项目采用 **三层日志架构**：

```
Serilog 结构化日志 ──→ *.log 文件 (JSON/纯文本)
       │
       ├── Console.WriteLine ──→ 控制台实时输出
       │
       └── PipelineEvent ──→ 内存事件流 (结构化指标)
```

**日志文件分布**：

| 目录 | 文件 | 内容 |
|------|------|------|
| `logs/` | `agent1-YYYYMMDD.log` | Serilog 结构化日志 (生产格式) |
| `logs/` | `full-YYYYMMDD.log` | 诊断双写日志 (Console + Serilog) |
| `logs/linux/` | `自动化脚本测试输出/` | Linux 自动化测试输出 |
| `Agent1.Api/logs/` | `agent1-api-*.log` | API 服务日志 |

## 二、如何阅读日志中的关键信息

### 2.1 日志格式解析

以 `agent1-20260623.log` 中的一条典型日志为例：

```
[2026-06-23 00:23:04.689 INF] LAPTOP-40G212RC RunId=0509e705 [Pipeline] 开始 | TraceId=ce1bc382 | 输入长度=10 | 输入=苯和丙酮能一起储存吗
```

拆解后的字段含义：

```
┌── 时间戳 (精确到毫秒)
│                          ┌── 日志级别 (INF/WRN/ERR/FATAL)
│                          │     ┌── 机器名
│                          │     │               ┌── 运行实例ID (每次启动唯一)
│                          │     │               │            ┌── 模块标签 ──┐
│                          │     │               │            │              │
[2026-06-23 00:23:04.689 INF] LAPTOP-40G212RC RunId=0509e705 [Pipeline] 开始 | TraceId=ce1bc382 | 输入长度=10 | 输入=苯和丙酮能一起储存吗
                                                                                        │                 │
                                                                              TraceId=ce1bc382      结构化字段
                                                                              (本次请求全程一致)
```

**关键识别技巧**：

| 你要找的 | 看什么 | 示例 |
|----------|--------|------|
| 某次请求的完整链路 | 相同的 `TraceId` | `ce1bc382` 从开始到完成的所有日志 |
| 某次运行的所有日志 | 相同的 `RunId` | `0509e705` |
| 某个模块的行为 | `[模块名]` 标签 | `[Pipeline]`, `[IntentRouter]`, `[Memory]` |
| 错误/异常 | 日志级别 `ERR`/`WRN` | `WRN` 安全拦截, `ERR` 服务异常 |

### 2.2 日志级别含义与应对策略

```
INF (Information)  → 正常业务流程，无需处理
WRN (Warning)      → 非致命问题，需关注但系统可继续
ERR (Error)        → 功能受损，需排查修复
FATAL (Fatal)      → 系统级崩溃，需立即处理
```

**实战案例**：从 `agent1-20260623.log` 第 6 行：

```
[2026-06-23 00:22:58.446 WRN] [Pipeline] 安全拦截 | TraceId=0c68ec2f | 原因=检测到潜在注入攻击: 匹配模式 "忽略之前的指令"
```

- **级别是 WRN 不是 ERR**：说明这是**预期行为**——安全模块正常工作了
- **不需要修复**：系统正确地拦截了注入攻击
- **需要关注**：如果有大量此类 WRN，说明有人在尝试攻击

### 2.3 测试结果日志格式

以 `summary.txt` 为例：

```
Agent1 自动化测试报告
══════════════════════
时间: 2026-06-24 00:26:20
通过: 22
失败: 0
跳过: 3
总计: 25
总耗时: 338s
LLM: 200     ← LLM 服务 HTTP 状态码 (200=正常)
Embed: 200   ← Embedding 服务 HTTP 状态码

各测试日志:
  T1_CoT标准推理: PASS
  T12_工具调用诊断: PASS
  T13_合规评测集: PASS
```

**快速判断**：
- `PASS` = 测试通过
- `FAIL` = 需要排查 (去找对应 `T*.log` 文件)
- `SKIP` = 前置条件不满足而跳过 (如 API 未启动)

## 三、通过日志排查系统运行问题

### 3.1 排查流程：从现象到根因

```
现象 → 定位时间窗口 → 找到 TraceId → 追踪完整链路 → 定位故障点
```

**实战案例 1：向量嵌入失败**

从 `full-20260605.log` 第 314-315 行：

```
⚠️ 向量请求失败 [InternalServerError]: {"error":"the input length exceeds the context length"}
⏭️ 向量生成失败，跳过向量库写入（BM25 已写入）
```

**排查步骤**：

| 步骤 | 操作 | 发现 |
|------|------|------|
| 1. 识别现象 | 看到 `⚠️` + `InternalServerError` | 向量服务返回 500 错误 |
| 2. 读错误详情 | `"the input length exceeds the context length"` | **根因**：文本块超过嵌入模型的上下文窗口 |
| 3. 看降级行为 | `⏭️ 跳过向量库写入（BM25 已写入）` | 系统有降级：向量跳过但 BM25 仍写入 |
| 4. 判断影响 | 搜索同类错误次数 | 全文出现 15 次同类错误 |
| 5. 修复方向 | 调整分块策略 | 减小 `SemanticChunker` 的 `MaxChunkSize`，或增加嵌入服务的 `-c` 参数 |

> 📖 关联记忆：`llama-server嵌入服务需同步调大-c和-b参数` — 嵌入服务上下文窗口需要与分块大小匹配

**实战案例 2：知识库质量问题**

从 `full-20260605.log` 第 2500-2558 行：

```
🚫 脏数据拦截: 来源=分析检验组班组长与员工责任书（分析）, 质量=未知, 内容长度=0
⚠️  部分:  2
❌ 失败:   0
⏭️  跳过:  1100 (空表单/模板)
```

**阅读技巧**：日志用符号前缀表示状态

| 符号 | 含义 | 是否需要处理 |
|------|------|:---:|
| ✅ | 操作成功 | 否 |
| ⚠️ | 警告/降级 | 关注 |
| ❌ | 错误/失败 | 是 |
| 🚫 | 主动拦截 | 看情况 |
| ⏭️ | 跳过 | 否 |
| 📦 / 🔗 / 📝 | 信息标记 | 否 |

这里 `🚫 脏数据拦截` + `内容长度=0` 说明**系统正确拦截了空文件**（企业制度模板的 DOCX 文件提取后无有效文本），这不是 Bug。

**质量报告解读**：

```
文件总数: 1158    ← 知识库目录下所有文件
✅ 成功:   56     ← 成功入库 56 个文档
⚠️  部分:  2     ← 2 个文档部分成功（向量失败但 BM25 成功）
❌ 失败:   0     ← 0 个完全失败
⏭️  跳过:  1100  ← 1100 个是空表单/模板，被脏数据拦截
总块数:    1241  ← 最终 1241 个语义块可用于检索
```

**判断标准**：如果 `❌ 失败 > 0`，需要排查；如果 `⏭️ 跳过` 占比高且都是空表单，属于正常现象。

### 3.3 TraceId 全链路追踪实战

在 `agent1-20260623.log` 中，同一个 `TraceId=ce1bc382` 贯穿了完整流程：

```
行7:  [Pipeline] 开始 | TraceId=ce1bc382 | 输入=苯和丙酮能一起储存吗
行8:  [IntentRouter] 关键词 "储存" 命中 → ChemicalCompliance
行9:  [Pipeline] 完成 | TraceId=ce1bc382 | 总耗时=9508ms | 意图=ChemicalCompliance | 工具调用=0
```

**从这里能读到什么？**

1. **用户输入**：`苯和丙酮能一起储存吗` (10 个字符)
2. **路由决策**：`"储存"` 命中合规关键词 → `ChemicalCompliance`
3. **总耗时**：9508ms（约 9.5 秒），`执行=9400ms` 占绝对主导
4. **工具调用=0**：⚠️ **这是一个异常信号！**——对于"储存兼容性"问题，应该调用 `CheckStorageCompatibility` 工具

> **排障线索**：如果 `工具调用=0` 但意图是 `ChemicalCompliance`，需要检查工具调度的 Prompt 是否正确引导了工具选择。

**完整链路查询技巧**：

```bash
# Linux 上提取某个 TraceId 的全部日志
grep "ce1bc382" agent1-20260623.log

# 统计某次运行中每种意图的数量
grep "意图=" agent1-20260623.log | sed 's/.*意图=//' | sed 's/ |.*//' | sort | uniq -c
```

### 4.3 评测集业务验证 (Part C)

从 Task 11 测试的 `C-eval-full.log` 中，每条用例的日志格式：

```
[C001] 查询: 丙酮属于危险化学品吗？哪一类？
  工具触发: CheckHazardCategory ✅
  参数: substanceName=丙酮 ✅
  结论: 丙酮属于易燃液体，类别2... ⚠️ 幻觉
  忠实度: 1/3 声明可验证
```

**逐条解读**：

| 字段 | 含义 | 判断标准 |
|------|------|:---:|
| `工具触发` | LLM 是否选择了正确的工具 | ✅/❌ |
| `参数` | 传递给工具的参数是否正确 | ✅/❌ |
| `结论` | 最终回答是否准确 | ✅/⚠️/❌ |
| `忠实度` | 结论中有多少声明可追溯到工具数据 | 越高越好 |

**典型异常模式诊断**：

```
模式 A: 工具触发=❌ → 问题在工具调度 Prompt 或意图路由
模式 B: 工具触发=✅, 参数=❌ → 问题在参数提取逻辑
模式 C: 工具触发=✅, 参数=✅, 结论=❌ → 问题在结论生成(幻觉/忠实度)
模式 D: 忠实度=0/3, 结论=✅ → 结论碰巧正确但不可信
```

```
  │   │   └─ ReflectionModule.Verify()           ← 反思验证

  │   ├─ SaveSessionAsync()                      ← [5/6] 会话保存
  │   └─ FormatOutput()                          ← [6/6] 格式化
  │
  └─ [9508ms] 返回 CliExecutionResult           ← Pipeline 完成
```

### 5.3 定位瓶颈：耗时分析

从 `[Pipeline] 完成` 日志中的耗时分解字段：

```
路由=84ms | 上下文=2ms | 执行=9400ms | 输入安全=10ms | 输出安全=0ms
```

```
总耗时 9508ms
├─ 路由: 84ms (0.9%)      ← 很快，不是瓶颈
├─ 上下文: 2ms (0.02%)    ← 非常快
├─ 执行: 9400ms (98.9%)   ← 🔴 绝对瓶颈！需要深入分析
├─ 输入安全: 10ms (0.1%)  ← 正常
└─ 输出安全: 0ms          ← 正常
```

**深入分析"执行"阶段**：9400ms 花在哪里？

- 如果 `工具调用=N`，则 LLM 推理时间 ≈ 执行时间
- 在 GPU 模式下，单次推理通常 3-5 秒
- 9400ms 约 2 次 LLM 调用（规划 + 执行 + 反思），属于正常范围
- 如果执行 > 30 秒，需检查：
  - 是否触发了多次工具调用（ReAct 循环）
  - LLM 服务是否有排队
  - Prompt 是否过长

## 七、常用排障命令

### Linux 服务器命令

```bash
# 查看最近的错误
grep -E "ERR|FATAL|❌" /root/autodl-tmp/agent-system/logs/agent1-*.log | tail -20

# 提取某个 TraceId 的完整链路
grep "ce1bc382" /root/autodl-tmp/agent-system/logs/agent1-*.log

# 统计 Pipeline 完成耗时分布
grep "\[Pipeline\] 完成" logs/agent1-*.log | grep -oP '总耗时=\K\d+'
```

## 八、总结：日志阅读心法

1. **先看级别再看内容**：`ERR`/`FATAL` 优先处理，`WRN` 判断是否误报，`INF` 用于追踪
2. **TraceId 是金线**：一个 TraceId 贯穿一次完整请求，grep 它就能看到全貌
3. **对照代码**：日志里的 `[模块名]` 对应源码中的 `Serilog.Log` 调用，找得到出处
4. **符号即状态**：`✅⚠️❌🚫⏭️` 是快速判断的信号灯
5. **数据说话**：不要猜，用 `grep -c` 统计频率，用 `awk` 计算分布
6. **先看最后再看最前**：排查故障时，先看崩溃前最后几行，再回溯到开头
