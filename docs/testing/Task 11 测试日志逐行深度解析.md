> 📁 **来源日志**：`logs/linux/手动测试控制台输出.txt`（Windows 手动测试环境，LLM 端点配置错误导致）

#### 维度 1：日志格式解析
| 字段     | 值                   | 含义                                    |
| -------- | -------------------- | --------------------------------------- |
| 符号前缀 | `⚠️`                  | **警告**（不是 `❌` 错误！）             |
| 错误类型 | `Connection refused` | TCP 连接被目标端口拒绝                  |
| 目标地址 | `localhost:11434`    | **关键线索**：这不是 llama.cpp 的端口！ |
| 诊断标记 | `[SK诊断]`           | Semantic Kernel 内置诊断                |

#### 维度 2：业务逻辑映射
- **根因分析**：`localhost:11434` 是 **Ollama 的默认端口**，但本系统使用的是 **llama.cpp**（端口 8080）！这说明 SK 框架的 HTTP 客户端配置错误，仍然指向 Ollama 地址
- **影响**：每次需要 LLM 推理时（工具规划、回答生成）都连接被拒 → `工具调用=0` 或极短耗时

#### 维度 3：数据链路追踪

这是一个**环境配置断层**异常。正常流程应该是：
```
Semantic Kernel → llama.cpp (localhost:8080) → Qwen3-8B 推理
```
实际流程是：
```
Semantic Kernel → Ollama (localhost:11434) → ❌ Connection Refused
                   └─ 降级: GenerateSimpleResponseAsync
                       └─ 再次 → localhost:11434 → ❌
                           └─ 返回空/兜底响应
```

#### 维度 4：设计意图说明
- **为什么这不是 ERR 而是 WRN**：系统设计有降级路径——LLM 不可用时返回兜底响应，不会崩溃。**优雅降级 > 硬失败**
- **为什么 SK 诊断单独输出 `本轮未调用任何工具`**：这是 SK 框架层面的诊断——"LLM 没有返回 Function Calling 指令"可能是 LLM 不支持 FC，也可能是连接失败导致根本没调用 LLM。诊断信息让你区分这两种情况

#### 维度 5：异常信号识别

按指南 §六 错误模式速查表：

| 分类         | 判断                                                         |
| ------------ | ------------------------------------------------------------ |
| **根因类别** | 类别 2：模型特性不兼容 / 配置错误                            |
| **严重程度** | 🔴 P0 —— 所有 LLM 推理全部失败                                |
| **影响范围** | 全局 —— 每个请求都受影响                                     |
| **修复方向** | 修正 SK 框架的 endpoint 配置从 `localhost:11434` → `localhost:8080` |

### 3.2 ⚠️ **熔断器激活**

> 📁 **来源日志**：`logs/linux/手动测试控制台输出.txt`（同上，连续 LLM 连接失败触发熔断器）

```
   ⚠️ [熔断器] 失败计数: 1/3
   ⚠️ [熔断器] 失败计数: 2/3
   🔴 [熔断器] 连续 3 次失败，熔断器打开 (30s 冷却)
   ⚠️ 异常: LLM 服务熔断中：连续 3 次失败，请在 29 秒后重试
```

#### 维度 1：日志格式解析
|                  符号                  | 级别     | 含义                             |
| :------------------------------------: | -------- | -------------------------------- |
|       `⚠️ [熔断器] 失败计数: 1/3`       | 警告     | 第 1 次失败，阈值 3，尚未熔断    |
| `🔴 [熔断器] 连续 3 次失败，熔断器打开` | **关键** | 阈值触发，熔断器打开             |
|        `⚠️ 异常: LLM 服务熔断中`        | 警告     | 后续请求被快速拒绝（不尝试连接） |

#### 维度 2：业务逻辑映射
- **代码位置**：`CircuitBreakerTests` 的被测代码 —— `CircuitBreakerService`
- **熔断逻辑**：连续 3 次失败 → 打开熔断器 → 30 秒冷却期 → 半开状态尝试 1 次 → 成功则关闭，失败则重新冷却
- **评测集前置检查中的触发**：FC 就绪性检查的 5 个诊断用例依次执行，前 3 个都 `Connection refused` → 第 3 次触发熔断 → 第 4、5 个直接返回"熔断中"

#### 维度 4：设计意图说明
- **为什么需要熔断器**：当 LLM 服务不可用时，没有熔断器会导致**每个请求都等待连接超时**（通常 30-60 秒），64 条评测集会耗时 > 30 分钟。熔断器让系统在检测到连续失败后**快速失败**（< 1ms），节省资源
- **为什么阈值是 3**：经验值。1 次可能是网络抖动，2 次可能是瞬时过载，3 次大概率是真故障
- **为什么冷却期 30s**：给服务恢复时间，避免"震荡"（刚恢复又被大量积压请求打死）

#### 维度 6：性能分析
- **熔断器节省的时间**：64 条评测 × 30s 连接超时 = 1920s（32 分钟）。熔断后直接返回，节省了大量无效等待
