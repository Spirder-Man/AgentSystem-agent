## 审查点 2: 工单状态流转状态机

### 发现：前后端使用了两套不同的状态枚举

这是本次审查发现的**最严重问题**，将导致工单列表页无法正确渲染、状态流转按钮全部失效。

### 后端实际使用的 `TicketStatus`

**来源**: `Modules/TicketFollowupModule.cs:244-252`（TicketsController 使用的工单类型）

```csharp
public enum TicketStatus
{
    New,         // 新建
    Accepted,    // 已受理（指派了责任人）     ← 注意
    InProgress,  // 整改中
    Completed,   // 已整改（待验收）            ← 注意
    Verified,    // 已验证通过                 ← 注意
    Closed,      // 已归档
    Rejected     // 驳回                       ← 注意
}
```

TicketsController 调用 `ticket.Status.ToString()` 返回的状态值是: `"New"`, `"Accepted"`, `"InProgress"`, `"Completed"`, `"Verified"`, `"Closed"`, `"Rejected"`

### 后端另有一套 `FindingStatus`

**来源**: `ComplianceModels.cs:217-226`（合规总览 `GET /api/Compliance/summary` 使用）

```csharp
public enum FindingStatus
{
    New,
    Confirmed,      // ← 与 TicketStatus.Accepted 不同!
    InProgress,
    Remediated,     // ← 与 TicketStatus.Completed 不同!
    VerifiedClosed, // ← 与 TicketStatus.Verified 不同!
    Closed,
    FalsePositive   // ← 与 TicketStatus.Rejected 不同!
}
```

### 前端使用的状态枚举

**来源**: `agent1-web/src/types/api.ts:208` + `agent1-web/src/mocks/data/tickets.ts:7-68`

```typescript
// types/api.ts
status: string;  // ← 宽松类型，允许任意字符串，不会编译报错但运行时错误

// tickets.ts Mock 数据
status: 'New' | 'Confirmed' | 'InProgress' | 'Remediated' | 'VerifiedClosed' | 'Closed' | 'FalsePositive'

// components/ticket/TicketStatusBadge.vue (设计)
status: 'New' | 'Confirmed' | 'InProgress' | 'Remediated' | 'VerifiedClosed' | 'Closed' | 'FalsePositive'
```

### 差异映射表

| 前端期望值 (基于 FindingStatus) | 后端实际返回值 (基于 TicketStatus) | 是否匹配 |
|-------------------------------|----------------------------------|----------|
| `New` | `New` | ✅ |
| `Confirmed` | `Accepted` | ❌ **不匹配** |
| `InProgress` | `InProgress` | ✅ |
| `Remediated` | `Completed` | ❌ **不匹配** |
| `VerifiedClosed` | `Verified` | ❌ **不匹配** |
| `Closed` | `Closed` | ✅ |
| `FalsePositive` | `Rejected` | ❌ **不匹配** |

### 影响范围

| 受影响组件/页面 | 故障表现 |
|---------------|---------|
| `TicketStatusBadge.vue` | 4 种状态显示为默认样式/颜色，无法正确渲染状态徽章 |
| `TicketActionButtons.vue` | `TICKET_ACTIONS_BY_STATUS` 使用错误的状态 key，所有操作按钮不显示 |
| `TicketListPage.vue` | 状态筛选下拉框与后端数据不匹配，筛选失效 |
| `TicketDetailPage.vue` | 状态流转可视化显示错误 |
| `tickets.ts` Mock | Mock 数据使用 FindingStatus 值，与后端不一致 |

### 修正建议

**方案 A（推荐）: 前端适配后端现状**

1. 更新 `types/api.ts` 中的 `TicketItem.status` 类型为精确联合类型:
   ```typescript
   type TicketStatus = 'New' | 'Accepted' | 'InProgress' | 'Completed' | 'Verified' | 'Closed' | 'Rejected';
   ```

2. 更新 `TICKET_ACTIONS_BY_STATUS` 状态 key:
   ```typescript
   New → Accepted    (action: 'accept')
   Accepted → InProgress (action: 'start'), Closed (action: 'close')
   InProgress → Completed (action: 'complete'), Closed (action: 'close')
   Completed → Verified (action: 'verify')
   Verified → (终态，无操作)
   New → Rejected (action: 'reject')
   ```

3. 同步更新 Mock 数据 `tickets.ts` 中的状态值。

4. 注意区分两套状态：仪表盘合规总览中的 `findingsByStatus` 使用 `FindingStatus`（Confirmed/Remediated/VerifiedClosed/FalsePositive），这是合规发现的状态，与工单（Ticket）状态是两套不同的东西。前端需要为 Finding 和 Ticket 分别维护状态常量。

**方案 B: 后端统一两套状态枚举**

将 `TicketStatus` 和 `FindingStatus` 统一为同一套枚举值（如都使用 FindingStatus 的命名），修改 `TicketFollowupModule.cs` 和 `TicketsController.cs`。这需要后续回归测试，风险较高，不推荐在 Sprint 0 前实施。

## 审查点 3: LLM 推理流式协议

### 后端现状

- `ModuleType.cs` 定义了 `CoTStream = 2` 和 `ReActStream = 4` 枚举值
- 但 **所有 API Controller 均返回 JSON 格式的完整响应**（`Ok(...)`），没有任何 SSE 端点
- `AgentDialog.ExecuteEvalFastAsync()` 返回 `Task<string>`，是完整的字符串响应
- 6 步流水线在服务端执行，`Console.WriteLine` 实时输出到服务端日志，**不向客户端推送**

### 前端现状

- 使用 `POST` + `useMutation` 等待完整 JSON 响应
- MSW Mock 中模拟 3-45s 延迟，前端显示进度条（基于预估时间，非真实进度）
- 前端设计文档中未提及 SSE/EventSource 支持

### 结论

**✅ 完全一致。** 当前后端没有 SSE 端点，前端基于 `POST` + 完整响应的设计是正确的。不需要引入 `useSSE` 或 `EventSource`。

### 未来演进建议

如果后续后端新增 SSE 流式端点（如 `POST /api/Compliance/check/stream`），前端需要：
1. 新增 composable `useSSE(url, body)` 封装 `fetch` + `ReadableStream` 解析
2. 合规自查页增加"流式模式"开关，切换 `useMutation` 和 `useSSE`
3. 进度条从"预估时间"改为"真实推理进度（token 级别）"

> 当前可记录为技术债，在 Sprint 2+ 处理。

## 审查点 4: 权限策略

### 后端策略定义

**来源**: `Program.cs:239-243`

```csharp
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("Admin",   policy => policy.RequireRole("admin"));
    options.AddPolicy("Auditor", policy => policy.RequireRole("admin", "auditor"));
    options.AddPolicy("Viewer",  policy => policy.RequireRole("admin", "auditor", "viewer"));
});
```

**Controller 级授权**:

| Controller | 授权策略 | 允许的角色 |
|-----------|---------|-----------|
| `AuthController` | `[AllowAnonymous]` (login/refresh) + `[Authorize]` (logout) | 所有已认证用户 |
| `ComplianceController` | `[Authorize(Policy = "Auditor")]` | admin, auditor |
| `InspectionController` | `[Authorize(Policy = "Auditor")]` | admin, auditor |
| `TicketsController` | `[Authorize(Policy = "Auditor")]` | admin, auditor |

### 前端权限矩阵（设计文档 2.1 节）

| 功能模块 | 前端赋予 viewer 的权限 | 后端实际允许 |
|---------|---------------------|-------------|
| 查看合规历史 | ✅ viewer 可访问 | ❌ `ComplianceController` 要求 Auditor |
| 查看巡检计划列表 | ✅ viewer 可访问 | ❌ `InspectionController` 要求 Auditor |
| 查看巡检结果 | ✅ viewer 可访问 | ❌ `InspectionController` 要求 Auditor |
| 查看工单列表 | ✅ viewer 可访问 | ❌ `TicketsController` 要求 Auditor |
| 查看资产台账 | ✅ viewer 可访问 | ❌ `InspectionController` 要求 Auditor |
| 查看仪表盘 | ✅ viewer 可访问 | ❌ 调用的 API 全部要求 Auditor |

### 结论

**⚠️ 发现差异 — viewer 角色在当前后端架构中无法访问任何业务功能。**

`Viewer` 策略（`RequireRole("admin", "auditor", "viewer")`）虽然已定义，但**没有任何 Controller 使用它**。所有业务 Controller 都使用 `Auditor` 策略。

这意味着:
- viewer 用户登录后，仪表盘数据请求全部返回 401/403
- viewer 用户看到的将是白屏或错误页面
- `viewer` 角色在当前系统中形同虚设

### 修正建议

**方案 A（推荐 — 最小改动）: 前端临时收缩 viewer 权限**

在 Sprint 0-1 阶段，将前端权限矩阵中的 viewer 角色限制为仅能访问登录页和 403 页。dashboard 页面仅对 admin + auditor 展示。待后端增加 Viewer 策略的 Controller 后，再恢复 viewer 的只读权限。

> ✅ **2026-07-10 已执行**: 方案 A 已实施，涉及文件:
> - `src/types/api.ts` — 新增 `UserRole` 类型
> - `src/stores/auth.ts` — `hasPermission()` viewer 返回 false
> - `src/router/index.ts` — 所有业务路由 `roles: ['admin', 'auditor']` + 全局守卫
> - `src/components/layout/AppSidebar.vue` — viewer 角色无菜单
> - `src/App.vue` — 侧边栏布局
> - `src/pages/ForbiddenPage.vue` — 403 页面
> - `docs/frontend/Agent1前端架构设计方案.md` — 2.1 节矩阵已更新

修改 `router/index.ts`:
```typescript
// viewer 可访问的路由: /login, /403
// admin/auditor 可访问的路由: 所有业务路由
{
  path: '/dashboard',
  meta: { requiresAuth: true, roles: ['admin', 'auditor'] },
}
```

**方案 B（长期正确）: 后端细粒度授权**

为每个 Controller 的 GET（读）端点使用 `Viewer` 策略，POST/PUT（写）端点使用 `Auditor` 策略:

```csharp
// ComplianceController.cs
[Authorize(Policy = "Viewer")]   // GET summary → viewer 可读
public IActionResult GetComplianceSummary() { ... }

[Authorize(Policy = "Auditor")]  // POST check → 仅 auditor 可写
public async Task<IActionResult> CheckCompliance(...) { ... }
```

或在 Controller 级别使用 `Viewer`，方法级别覆盖:
```csharp
[ApiController]
[Route("api/[controller]")]
[Authorize(Policy = "Viewer")]        // 默认所有端点 viewer 可访问
public class ComplianceController : ControllerBase
{
    [HttpGet("summary")]
    public IActionResult GetComplianceSummary() { ... }  // viewer ✅

    [HttpPost("check")]
    [Authorize(Policy = "Auditor")]    // 覆盖: 仅 auditor 可写
    public async Task<IActionResult> CheckCompliance(...) { ... }
}
```

### 额外发现: 缺少 `Admin` 策略的 Controller

审计日志页（`/audit`）在前端设计中被标记为 "admin only"，但后端没有 `AuditController` 暴露 API。这是已知差距（已在设计文档附录 C 中标注"需新增"），但如果在后续 Sprint 中实现，需要确保使用 `Admin` 策略。
