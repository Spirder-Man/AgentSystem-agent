## 五·补、PITR 恢复演练实录（2026-08-11，两轮全通过）

**方法**：不碰生产数据——生产库建临时表 `pitr_drill` 分 3 批写入（T1=16:52:24 5 行 → T2=16:52:30 8 行 → T3=16:55:06 11 行），每批后强制切 WAL 归档；复制 base 备份到独立目录、5433 端口离线起实例、PITR 到指定时间点验证行数。

| 演练 | 恢复目标 | WAL 证据 | 结果 |
|------|----------|----------|------|
| A：恢复到 T1~T2 之间 | 16:52:27 | `restored log file 000...00B/00C/00D from archive` + `recovery stopping before commit of transaction 16846, time 08:52:29` | pitr_drill = **5**（batch2 被截断）✅ audit_logs = 1189 ✅ |
| B：恢复到 batch3 前 | 16:55:06 | `restored log file 000...00E from archive` + `recovery stopping before commit of transaction 16847, time 08:55:06.97` | pitr_drill = **8**（batch3 被截断）✅ audit_logs = 1189 ✅ |

**学到的边界（重要）**：恢复目标不能超过归档 WAL 的最后一条事务——演练 B 首轮目标 16:52:35 晚于最后事务 16:52:29.83，报 `recovery ended before configured recovery target was reached`（预期行为，非故障）。真实事故中目标=误删前 1 秒，必然在 WAL 覆盖内。

**演练发现的 3 个环境坑**（已并入速查手册 6.3 落地实录）：
1. pg_basebackup 不备份 pg_hba.conf / postgresql.conf（Debian 配置在 /etc/postgresql/16/main/，数据目录没有）——独立恢复实例需手动复制
2. 恢复实例必须改端口（5433）避免与生产冲突
3. 恢复配置写数据目录内 postgresql.conf + `recovery.signal` 标记（PG 12+ 语法）

**清理**：演练实例已停、目录已删、pitr_drill 已删、生产库 1189/427 行完好、备份产物完好（base 60M / dump 4.3M / 归档 8 段）。

**结论**：**备份体系三件套经实战验证可用**——base + 归档 WAL 能精确恢复到任意时间点，PITR 从文档变成了已验证的能力。

## 六、一句话教训

> 数据库"数据没了"是最高危的指控之一——第一动作永远是 `SELECT count(*)`，不是翻日志讲故事。证据不足时，结论只能说"未确认"，不能说"被删除"。
