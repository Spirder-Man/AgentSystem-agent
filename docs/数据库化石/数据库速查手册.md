## 一、基本概念（零跳跃五步，先看懂这 5 个词）

| 概念 | 大白话 | 类比 |
|------|--------|------|
| **数据库** | 装数据的仓库 | 一个 Excel 文件 / 档案室 |
| **表** | 仓库里专门记一类东西的工作表 | Excel 里的一个 sheet / 档案柜 |
| **字段** | 工作表的表头列（姓名/年龄），规定每行能记什么 | 表格的表头 |
| **记录（行）** | 表头下面的一行具体数据（张三，25岁） | 表格的一行 |
| **主键** | 每一行的身份证号（唯一标识） | 工号 E001 |
| **外键** | 存别人家主键的"参见"列，把两张表串起来 | 员工表的部门编号 → 部门表 |

**关键关系**：
- 先有字段（表头）定义，才能填记录（行）
- 字段决定"记什么"，行决定"记了谁"
- 外键 = 一行数据指向另一张表某行的"参见"标注

| 维度 | 8 核心表 | 7 张 chemical_* 表 |

| 来源 | 代码 DatabaseService 自动建表 | 002 迁移 SQL 显式建表 |
| 主键 | int4 SERIAL 或 uuid | int4 SERIAL |

## 五、疑问与解答（持续追加区）

### 2026-08-11

**Q：CSV 文件 188 行太多，怎么看得动？**
A：不要整文件看。一次只看一张表（约 10~17 行），按"身份/内容/状态"分组读。字段数量多 ≠ 要一次看懂，分组后每组 2~6 个字段，逐个消化。

**Q：数据库、表、字段到底是什么？**
A：数据库 = 装数据的仓库（Excel 文件）；表 = 仓库里专门记一类东西的工作表（sheet）；字段 = 表头列（规定每行记什么）；记录 = 一行数据。详见"一、基本概念"。

**Q：数据库里哪些表是我们系统的？**
A：15 张 = 8 张核心表（sessions / refresh_tokens / audit_logs / search_logs / chemical_documents / knowledge_documents / knowledge_chunks / long_term_memories）+ 7 张 knowledge 图谱表（chemical_substances / chemical_aliases / chemical_hazard_categories / chemical_incompatibilities / chemical_incompatible_categories / chemical_regulation_versions / chemical_safety_distances，来自 002 迁移）。历史版本曾有 9 张 agent_* 外来空壳表（本地独有、0 数据），2026-08-11 整库替换后已消失。

**Q：什么叫"谁在乎被查，谁才上锁"？"锁"是 chain_hash 字段吗？**
A：分两部分：
① **"锁"是什么**：锁 = 防篡改机制（哈希链）。chain_hash 字段只是锁的"锁体"。完整一把锁 = chain_hash 字段（锁体）+ 哈希计算规则（锁芯）+ 验证比对逻辑（查账时开锁：重新算一遍哈希与存值比对，对不上 = 被改过）。光有字段不够，它只是一串字符。
② **"谁在乎被查"**：被查 = 有监管方/审计方来验证"账本没被人改过"。小店老板的流水本不上锁（没人查）；上市公司财务报表必须上锁（证监会审计）。合规系统（我们）面对监管，审计日志本身是被审查对象，必须能自证清白 → 上锁；外来表 agent_audit_log 是内部管理记录，没人查它 → 不上锁。本质：**需要向别人证明账本清白的人，才需要锁**。

**Q：为什么数据库全是 0 行？之前 E2E 评测的数据去哪了？（2026-08-11 数据丢失疑案，后经 L0 实测证实为误判）**
A：**结论更正：数据从未丢失——本次疑案是误判链（已入宪法第四条根本准则）。** 真相三层：
① **L0 直接查库（2026-08-11 实测）**：audit_logs 1189 行、long_term_memories 1157 行、refresh_tokens 427 行（最后一条 8-3 11:25:43）、knowledge_chunks 55 行——数据全部完好；
② **WAL 挖掘（L1 证据）**：8-3 只有 2 条登录 INSERT，无任何 DROP/TRUNCATE 记录；11:27 checkpoint 是正常活动，18KB WAL 非"DDL 量级"；
③ **误判起源**：sessions 表 0 行（僵尸表——代码 SessionManager 纯内存，从不写该表）被误读为"数据被清空"；checkpoint 日志、WAL 18KB、排除法推定"外部手动 SQL"构成完整但错误的叙事链。8-8 测试日志（用户提供）进一步证明 8-8 测试在另一实例运行（该实例 60 条分块，本实例 55 条）。
**教训（已入工程宪法）**：① 任何"数据丢失"怀疑，第一动作必须 L0 直接查库（count(*) + 时间范围），禁止先构建因果叙事；② 测试加"数据留存断言"（第六维度：跑完用独立连接查库）仍有价值——防真丢失；③ 破坏性数据库操作必须备份+审批；④ PG 在 AutoDL 系统盘，断电/实例重置存在丢失风险（实测断电后 crash recovery 数据完好，但需常态化备份）；⑤ 误判结论会污染文档——已同步修正本手册与宪法（详见第四条根本准则"污染修正"）。

**根因**：① 本地 agent_* = 历史导入外来空壳表（源码 0 引用）；② 远程 chemical_* = 知识图谱数据表（`db/migrations/002_chemical_knowledge_graph.sql` 建表 + 种子数据 35 物质/83 别名/116 危险类别/21 禁忌边），**本地从未执行该迁移** → 本地知识图谱以空图启动（模块有表检测机制）；③ 数据差异 = 本地是开发测试库（曾大量插入后删除，chemical_documents 序列到 5909 但实际 16 行），远程是生产库（8-8 E2E 后的真实残留）。

A：**结论：本地库已与远程生产库 100% 对齐（15 表行数/索引/序列全部一致），本地 knowledgebase/ 文件夹也同步为生产文件。**

四个动作依次执行（均按"备份 → 审批 → 执行 → 验证"规范）：
① **异地备份**：远程 `pg_dump -Fc` → 拉到本地 `db/backups/dump_20260811.dump`（4.5MB）留档。服务器挂了，本地 `pg_restore` 即可完整恢复（已实测）。

③ **知识库表数据替换**：pg_dump 导出远程 knowledge_documents(34)/knowledge_chunks(55) → 本地 DELETE 1160 条测试数据 → 导入生产数据 → SETVAL 对齐序列（1325/1299）。

**异地备份 → 恢复操作流程（复现手册）**：
1. 远程备份：`pg_dump -h localhost -U postgres -Fc -d chemical_park_ai_agent -f /tmp/dump_YYYYMMDD.dump`（远程 trust 认证）→ `base64 -w0` 输出 → SshRunner 拉回本地 `db/backups/`。
2. 本地恢复：`DROP/CREATE DATABASE`（**不能带 -C 恢复**：远程 locale 是 C.UTF-8，Windows 没有该 locale 会报 `invalid LC_COLLATE`；手动建库用本地默认 locale 再 `--no-owner` 恢复即可）→ `pg_restore --no-owner --no-privileges -d chemical_park_ai_agent dump.dump`。
3. 恢复后验证：count(*) 逐表对比 + 序列对比（`pg_sequences` 列名是 **sequencename** 不是 sequence_name）+ 索引清单对比。

**本次踩坑清单（复用时直接避开）**：① Windows tar/7z/Git tar/.NET System.Formats.Tar 全部解不开 GNU tar 中文文件名 → **用 Python tarfile**（原生支持）；② PowerShell 5.1 执行 UTF-8 无 BOM 脚本按 GBK 解析 → 含中文路径的 .ps1 必须全 ASCII + `$PSScriptRoot` 推导；③ psql `-o` 输出文件是 UTF-8 主体 + GBK 尾部混合编码（"(N 条记录)"行）→ 按行是否含 `/` 过滤最稳；④ SshRunner `--upload` 必须是**第一个参数**；⑤ pg_restore 读中文路径失败 → 用变量传路径；⑥ psql 交互会等密码 → 必须 `PGPASSWORD` 环境变量；⑦ 本地库 drop 前须 `pg_terminate_backend` 踢掉 pgAdmin 空闲连接。

**学习意义**：① 本地 = 远程生产镜像后，"设计不脱离数据"的后续学习（方法论文档第 2 组逐表精读）可直接以本地库为准，与远程一致；② 异地备份的价值已实测闭环：服务器挂了，一个 dump 文件 + 三条命令 = 完整生产数据；③ 动态表（audit_logs/refresh_tokens/ltm）会随远程运行继续增长——**本地是 08-11 快照，学静态结构用本地，看最新动态以远程为准**。

## 六、PG 事故标准恢复流程（PITR 实操 + 备份体系，2026-08-11 疑案沉淀）

### 6.0 先立 B：这套流程解决什么问题

**问题**：数据库被误操作（DROP 表 / TRUNCATE / 全表 DELETE / 清库）后，怎么把数据找回来？

**一句话答案**：靠**备份体系三件套**——全量基线（pg_basebackup）+ 连续 WAL 归档 + PITR 时间点恢复。三者缺一不可，且必须在事故**发生前**就搭好。

**类比**：MySQL 的 binlog 像**录像带**（记下每一笔操作），全量备份像**全家福照片**，恢复 = 拿最近的全家福 + 从那天到现在的录像带，重新剪出事故前一刻的画面。PG 的 WAL 归档 = 录像带，pg_basebackup = 全家福，PITR = 剪辑。

---

### 6.1 备份体系三件套（对标 MySQL）

| 能力 | MySQL | PostgreSQL | 本项目实测（2026-08-11） |
|------|-------|-----------|--------------------------|
| 实时变更日志 | binlog（**默认开**，row 格式） | WAL（**默认开**，物理日志） | ✅ WAL 在写，但段 8/9 循环覆盖 |
| 日志持久保留 | binlog 文件按策略保留 | **archive_mode=on + archive_command（默认关！）** | ❌ 关闭（archive_status 空） |
| 全量基线 | mysqldump / 物理备份 | **pg_basebackup 定期执行（需主动做！）** | ❌ 无 |
| 恢复到删除前一刻 | mysqlbinlog 重放 → PITR | **restore_command + recovery_target_time → PITR** | ❌ 无 |
| 逻辑兜底 | mysqldump 定期 | **pg_dump 定期** | ❌ 无 |

### 6.2 为什么 PG 不能像 MySQL 那样"删了立刻恢复"

- MySQL binlog 是**逻辑日志**（记录 SQL 语句 / 行级变更），row 模式下删除前的整行数据就写在 binlog 里，可以直接提取重放；
- PG 的 WAL 是**物理日志**（记录数据页的字节级变更），只能整体重放，不能"挑出某几行"——所以 PG 恢复没有捷径，标准姿势就是：**全量基线 + 归档 WAL 重放到时间点（PITR）**；
- 用户常说的"MySQL 删了能很快恢复"，本质是 binlog 默认开 + 有全备的习惯；PG 的 WAL 归档默认关，不主动配置就等于没有录像带。

**Step 4：恢复演练 ✅ 已完成（2026-08-11 两轮 PITR 全通过，实录见《闭环报告》五·补）**

方法：生产库建临时表分 3 批写入（T1 5 行 → T2 8 行 → T3 11 行），复制 base 到独立目录、5433 端口离线起实例，PITR 到 16:52:27 验证 5 行、到 16:55:06 验证 8 行——**时间点精确截断全部命中**。

**落地实录（2026-08-11 实操踩坑，下次直接抄）**：

| 坑 | 现象 | 解法 |
|----|------|------|
| 归档目录在 /root 下 | 归档一直失败 `Permission denied`（/root 是 700） | `apt install acl` + `setfacl -m u:postgres:x /root`、`setfacl -m u:postgres:rwx /root/autodl-tmp`（最小授权，不动全局权限） |

| 归档目录已有同名段 | archiver 无限重试失败（`test ! -f` 语义：文件存在=命令非零） | 删掉手动复制产物，让 archiver 自己归档；archive_status 看到 `.done` = 成功 |
| crontab 报 missing newline | 追加块结尾无换行 | 追加块末尾补 `\n` 再 `crontab` 安装 |

### 6.4 事故应急流程（误删发生后，按顺序执行）

**Step 0：冻结现场（最重要！误删后第一时间做，不是先查原因）**

```bash
# 有 base + 归档 WAL → 立即停库，防止新写入覆盖恢复窗口
pg_ctlcluster 16 main stop
# 同时把当前 pg_wal 目录整份复制留证（防 WAL 循环覆盖）
cp -a /var/lib/postgresql/16/main/pg_wal /root/autodl-tmp/pg_backup/wal_crash_$(date +%Y%m%d_%H%M%S)
# 无归档只有 pg_dump → 不用停库，直接 pg_dump 当前数据（已删除的部分只能手工补）
```

**Step 1：评估损失（L0 直接查库，宪法第四条）**

```bash
pg_isready
PGPASSWORD=xxx psql -U postgres -h localhost -d chemical_park_ai_agent -c "SELECT relname, reltuples FROM pg_class WHERE relkind='r' AND relnamespace='public'::regnamespace ORDER BY relname"
# 对照备份前的行数基线，确认到底丢了多少、哪些表
```

**Step 2：选择恢复路径**

| 手上有 | 恢复方式 | 能恢复到 |
|--------|----------|----------|
| base + 归档 WAL | PITR（6.4 Step 3） | 误删前一刻（精确到秒） |
| 只有 base | 整体还原 base | 最近一次备份时刻 |
| 只有 pg_dump | pg_restore | 最近一次 dump 时刻 |
| 什么都没有 | 文件系统级恢复（容器内基本不可行） | 基本不可恢复 |

**Step 3：PITR 实操（完整命令序列，PG 12+ 语法）**

```bash
# ① 停库
pg_ctlcluster 16 main stop

# ② 把损坏的数据目录移走留证（不要删！）
mv /var/lib/postgresql/16/main /var/lib/postgresql/16/main.corrupt

# ③ 把 base 备份复制为新的数据目录
cp -a /root/autodl-tmp/pg_backup/base_20260810 /var/lib/postgresql/16/main
chown -R postgres:postgres /var/lib/postgresql/16/main

# ④ 写恢复配置（PG 12+：参数进 postgresql.conf，另建 recovery.signal 标记）
# 在 /var/lib/postgresql/16/main/postgresql.conf 追加：
#   restore_command = 'cp /root/autodl-tmp/pg_backup/wal/%f %p'
#   recovery_target_time = '2026-08-11 14:59:59'   ← 误删前一刻
#   recovery_target_inclusive = false               ← 不含目标时刻之后的事务
#   recovery_target_action = pause                  ← 重放到目标后暂停，先验证

# ⑤ 创建恢复标记文件（PG 12+ 用 recovery.signal 代替 recovery.conf）
touch /var/lib/postgresql/16/main/recovery.signal

# ⑥ 启动，观察日志
pg_ctlcluster 16 main start
# 日志应出现：recovery stopping before commit of transaction ...
# 此时库处于只读（恢复中）状态

# ⑦ 验证数据（L0 行数 + 抽查关键表）
PGPASSWORD=xxx psql -U postgres -h localhost -d chemical_park_ai_agent -c "SELECT count(*) FROM audit_logs"

# ⑧ 确认无误 → 结束恢复，恢复可写
psql -c "SELECT pg_wal_replay_resume();"
rm /var/lib/postgresql/16/main/recovery.signal
# 重新启动一次即转为正常读写库
pg_ctlcluster 16 main restart
```

**Step 4：复盘闭环（宪法第四条四件套）**

## 七、逐表精读笔记（持续追加）

### 2026-08-11 · audit_logs（操作监控记录）——完整精读

**第 0 步：用途（先立 B）**

系统里每次**重要操作**都记一行账：**谁、在哪个功能、干了什么、从哪台电脑、什么时候**。

- 类比：**监控室的录像带**——平时没人看，出事（"谁删了数据？"）就回放对质
- 场景举例：用户登录、删除数据、导出文件、修改系统设置，都会写一行

**第 1 步：字段分组（8 字段 → 4 组）**

从 CSV 提取：

```
audit_logs  1  id           integer  NO  nextval(...)     ← 编号
audit_logs  2  user_id      varchar 100 YES               ← 谁干的
audit_logs  3  action       varchar 100 NO                ← 干了什么（必填！）
audit_logs  4  module       varchar 100 YES               ← 在哪个功能里干的
audit_logs  5  detail       text     YES                 ← 细节补充
audit_logs  6  ip_address   varchar 50  YES               ← 从哪台电脑干的
audit_logs  7  created_at   timestamptz YES 默认当前时间   ← 什么时候干的
audit_logs  8  chain_hash   text     YES                 ← 防篡改指纹（灵魂）
```

| 组 | 字段 | 回答的问题 |
|----|------|-----------|
| 身份组 | `id` | 这是第几条记录 |
| 人物组 | `user_id` + `ip_address` + `created_at` | **谁**、**从哪**、**何时** |
| 事件组 | `action` + `module` + `detail` | **干了什么**、**在哪个功能**、**细节** |
| 防篡改组 | `chain_hash` | **这条记录被改过吗** |

**第 2 步：每组讲故事**

**人物组 + 事件组 = 审计六要素**：Who / When / Where / What / Which module / Detail。任何一条记录都能回答：

> "2026-08-11 10:30，用户 admin 在知识库模块删除了文件 X（IP 192.168.1.5）"

两个细节：
- `action` 是 **NO（必填）**——可以不知道是谁（user_id 可空，匿名操作），但必须知道干了什么。**事件是账本的主干**
- `detail` 是 `text`（不限长）——细节可长可短，放补充信息（比如删除的文件名）

**chain_hash = 防篡改的"骑缝章"（灵魂）**

- **哈希是什么**：把任意内容变成一串固定长度的"指纹"。内容改一个字符，指纹完全不同
- **哈希链怎么工作**：

```
第 1 条：chain_hash₁ = 指纹(第1条内容)
第 2 条：chain_hash₂ = 指纹(第2条内容 + chain_hash₁)
第 3 条：chain_hash₃ = 指纹(第3条内容 + chain_hash₂)
...每条都咬住上一条的尾巴
```

- **效果**：有人偷偷改了第 5 条记录的内容 → 第 5 条的指纹变了 → 第 6、7、8 条的指纹全部对不上 → **篡改立刻暴露**
- **类比**：一摞发票，每张都盖着上一张的编号做骑缝章——撕掉、换掉任何一张，整摞就接不上了
- **为什么项目要这个**：这是**合规系统**——审计日志本身要能被审计（法规要求防篡改）

**"锁" = 防篡改机制（疑问补充）**

- `chain_hash` 字段是这把锁的"锁体"，但光有字段不够——它只是一串字符
- 完整一把锁：`chain_hash` 字段（锁体）+ 哈希计算规则（锁芯）+ 验证比对逻辑（查账时拿钥匙开锁：重新算一遍哈希，与存值比对，对不上 = 被改过）
- **谁在乎被查，谁才上锁**：

| 场景 | 要不要上锁 | 为什么 |
|------|-----------|--------|
| 小店老板自己的流水本 | 不上锁 | 没人来查，记错也无所谓 |
| 上市公司财务报表 | **必须上锁** | 证监会要审计——账本必须能证明"没被改过" |

  - 我们的系统（合规系统）：面对化工园区监管场景，**审计日志本身就是被审查对象**——监管方会问"你凭什么证明日志没被篡改？" → 主动上锁，被问时能拿出证据
  - `agent_audit_log`（外来表）：内部管理场景，**不需要向任何人证明日志完整性** → 设计者没上锁
- 一句话大白话：**要向别人证明"我的账本没被改过"的人，才会给账本上锁；不需要证明的人，账本随便记**

**第 3 步：一句话总结**

> **`audit_logs` 是"操作监控账本"：6 要素记录谁在何时何地干了什么，chain_hash 哈希链把每一行咬合成一串，让任何篡改都无处遁形——合规系统的最后一道防线。**

**对照**：外来表 `agent_audit_log` 没有 chain_hash——谁在乎被查，谁才上锁。

- **落差 2（ip_address 半实现）**：1140 行空、49 行有值（全是测试写的 127.0.0.1）→ 接口有参数、生产调用点从没传 → 审计的"从哪台电脑"能力空转
