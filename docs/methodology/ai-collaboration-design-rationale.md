# AI 协作中的"设计理据追问法"

> 从 Bug-033（E1 兜底未接入 T13 评测路径）的排查过程中提炼的通用方法论。

---

## 一、核心命题

**程序成功会骗你，但设计意图不会。**

在 AI 辅助编程中，最大的陷阱不是 AI 写出有 bug 的代码，而是 AI 修了症状、测试 PASS，但系统内部多了一条重叠的降级路径、一处僵尸代码、一个未来必然冲突的设计矛盾——三个月后才爆炸。

---

## 二、心理模型的三个问题

每做一个修改，**先问"为什么"，再动手。** 不是在问代码怎么写，是在问设计者当时怎么想的。

| # | 问题 | 含义 |
|---|------|------|
| 1 | **这个模块的设计意图是什么？** | 它为了解决什么场景而生？边界条件是什么？ |
| 2 | **为什么选了这种方案而不是另一种？** | 当时有哪些选项？被排除的方案是因为什么被排除的？ |
| 3 | **这个决策的边界条件是什么？** | 什么情况下这个模块会被触发？什么情况下它不该起作用？ |

如果三个问题答不上来 → 不要改，先搞清楚。

## 三、案例：Bug-033 完整诊断过程

### 3.1 现象

评测中 3 例 FC=Required 违约（LLM 零工具调用 → 输出被丢弃 → 返回拒绝模板）。

### 3.2 症状级修复（AI 的第一反应）

给正则加模式、接入 T13 路径 → 测试 PASS → 参数准确率 +3%、结论准确率 +1.6%。看起来是有效修复，但——

### 3.3 Git 时间线还原

追问"既然写了规则引擎为什么之前没有用"后，通过 git 历史还原了完整时间线。关键发现：**所有相关代码均为同一作者** (`2732232706@qq.com`)，不存在沟通断层。

```
6月23日  DeterministicRuleEngine 创建
         └─ 三个方法：TryHandleStorageQuery / TryHandleHazardQuery / TryHandleSafetyDistanceQuery
         └─ 从数据库匹配物质名、从关键词检测意图、查内置规则表
         └─ 设计定位："LLM 不可用时的降级路径"

7月3日   DecoupledPipeline 创建（"双通道解耦架构"）
         └─ LLM输出 → 事实提取 → 消毒 → 渲染 → 合并

7月11日  TryFallbackToRuleEngine 接入 AgentDialog
         └─ 触发条件：熔断器打开 / LLM返回"生成失败"
         └─ 即：只在 LLM 彻底挂掉时才走规则引擎

7月20日  Bug-032 v1 (11:26) → Bug-032 v2 (11:52)  ← 26分钟内连修两次
11:26    FC=Required违约时 toolCalls==0 → 丢弃LLM输出 → BuildNoResult()
         └─ 返回纯拒绝模板："无法处理此查询"
11:52    提升为最高优先级独立闸门（之前被 HasAnyToolResult 绕过）

7月25日  E1-E7（"工程侧6项缺陷修复"）
         └─ E1: 在 LlmService 里新写三个正则
         └─ 覆盖同库储存/安全距离/危险类别 ← 和规则引擎的三类场景完全重叠
         └─ 但没有调用已有的 TryFallbackToRuleEngine

7月27日  Bug-033（本轮修复）
         └─ E1 正则在 T13 路径上没接线 → 补接
```

### 3.4 根因分析

#### 为什么 Bug-032 没调规则引擎？

Bug-032 的思维模型：

> "LLM 没调工具 → LLM 输出不可信 → **必须丢弃**"

这是一个**排斥性思维**——重点是隔离 LLM 的污染，而不是获取答案。所以返回 `BuildNoResult()` 拒绝了事。规则引擎的设计定位是"LLM 彻底不可用"（基础设施级故障），而被开发者归类为不同的心理范畴。

#### 为什么 E1 没复用规则引擎，而是新写正则？

E1 的思维模型：

> "LLM 没调工具 → 但我们可以**绕过 LLM 自己调工具** → 写几个正则匹配用户问题"

这是同一个排斥性思维的延续——"既然是 LLM 的问题，那就在 LLM 附近修"。修在了 `LlmService.cs`（LLM 调用层），而不是往上看到 `AgentDialog.cs` 里已有的 `TryFallbackToRuleEngine`。

#### 核心问题：同一开发者拆出了两个心理边界

```
┌─ 规则引擎 ────────────────────────┐  ┌─ E1 正则 ──────────────────────┐
│ 触发条件：LLM 彻底挂掉             │  │ 触发条件：LLM 不调工具              │
│ （熔断器打开 / "生成失败"）        │  │ （toolCalls==0，但 LLM 还在线）    │
│ 心理模型："基础设施故障，降级"     │  │ 心理模型："LLM 不听话，补一刀"        │
│ 同一需求，被当成两类问题处理        │  │                                   │
└───────────────────────────────────┘  └───────────────────────────────────┘
```

两种"兜底"实际上解决的是同一个需求：**LLM 不能正常工作时，如何用确定性手段获取合规答案**。但开发者把"LLM 挂了"和"LLM 不调工具"当成了两类问题，各自设计了独立的降级路径。

### 3.5 如果不追问就修，会怎样？

如果把 FC=Required 违约路径直接指向规则引擎，但没理解这个心理边界是如何产生的：

1. **同样的分裂继续发生**：下一个开发者看到"LLM 响应变慢"又会写第三种兜底，因为在他的心理模型里这又是一类新问题
2. **规则引擎可能被误用**：它目前假设只在"LLM 不可用"时被调用，可能有状态假设不适用于高频 FC 违约场景
3. **降级路径永不收敛**：真正该做的是把所有"LLM 不能正常工作"的场景（挂了、不调工具、返回乱码、超时）统一到一条降级链上，而不是每发现一种异常就加一条新路径

**正确的修法不只是"把 FC 违约指向规则引擎"，而是在架构层面明确：LLM 所有异常状态 → 确定性降级的唯一入口。**

## 四、为什么传统"改了就跑测试"的工作流不够用

```
传统工作流：
  发现问题 → AI 给方案 → 改代码 → 测试 PASS → ✅

问题在哪：
  - AI 给的方案基于模式匹配，不是基于对系统架构的理解
  - AI 不会主动告诉你"这里已经有一个现成的设施了"
  - 测试只验证行为正确性，不验证设计一致性

插入追问后的工作流：
  发现问题 → 问 AI"为什么" → AI 被迫查 git 历史/代码关系
           → 暴露设计矛盾 → 重新定义问题 → 收敛方案 → 改代码 → 测试 PASS → ✅
```

## 五、追问的时机

以下信号出现时，**必须追问**，不能直接动手：

| 信号 | 示例 |
|------|------|
| 方案涉及新增一个和现有模块功能高度重叠的东西 | E1 正则 vs 规则引擎 |
| 方案是"在 X 情况下补一刀"这种补丁式描述 | "当 LLM 不调工具时，我们写个正则匹配" |
| 修改跨了多个文件但 AI 没说它们之间的关系 | LlmService + AgentDialog + DecoupledPipeline |
| AI 给的答案太"顺"——仿佛问题只有一个解 | "改成懒匹配就行" → 实际上懒匹配也解决不了 |

---

## 六、核心原则

> **你不是在审查 AI 的代码，你是在审查 AI 的思路。**

AI 的优势是快，劣势是不理解设计意图。追问"为什么"是在做 AI 做不到的事——而这件事恰好决定了修改是"修好了一个 bug"还是"埋下了一个未来的 bug"。
