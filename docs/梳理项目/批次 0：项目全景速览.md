**段 1：单例模式 + 懒加载校验（第 36-46 行）**

```csharp
private static AppConfig? _instance;

public static AppConfig Instance
{
    get
    {
        if (_instance == null)
            throw new InvalidOperationException("AppConfig 尚未加载。请先调用 AppConfig.Load(configuration)");
        return _instance;
    }
}
```

**【语法层】**
- `private static AppConfig? _instance`：nullable 引用类型（`?`），C# 8.0 可空引用类型特性。`_instance` 在 `Load()` 调用前为 `null`，调用后保证非空。
- `public static AppConfig Instance`：只读属性（只有 getter），外部不可赋值，强制通过 `Load()` 初始化。
- `throw new InvalidOperationException(...)`：fail-fast 模式，如果使用者在 `Load()` 之前访问，立刻崩溃而非返回 null 导致后续 NRE。

**【功能层】**
- 全局唯一入口：项目中任何代码都可以通过 `AppConfig.Instance.Llm.ModelId` 获取 LLM 模型名称。
- 线程安全：CLR 保证静态构造函数的线程安全，但这里使用的是显式 `Load()` 方法。单线程初始化（Main 启动时），初始化后只读，无需加锁。

**【设计意图层】**
- **为什么用静态单例而不是依赖注入？** 配置是全局性的，几乎所有服务都需要它。如果全部通过构造函数注入，每个服务的构造函数签名会非常冗长。静态单例让 `ChemicalComplianceTools` 等类可以直接 `AppConfig.Instance.VectorSearch.RerankerCandidateTopK` 而不需要额外的构造函数参数。
- **为什么加 fail-fast 校验？** 这是一个典型的 defensive programming 实践。如果忘记调用 `Load()`，在第一次访问时就崩溃，而不是在深层业务逻辑中出现神秘的 `NullReferenceException`。错误信息明确告诉开发者"配置未加载"。
- **为什么是 `static` 类成员而不是 `Singleton` 模式？** 两者语义等价，但 `static` 成员更轻量，对于配置这种进程级别、不可变的数据，`static` 是正确的选择。

**段 2：Load 方法 + 环境变量覆盖（第 48-71 行）**

```csharp
public static void Load(IConfiguration configuration)
{
    var config = new AppConfig();
    configuration.Bind(config);    // ← 核心：自动绑定 appsettings.json

    var dbPassword = Environment.GetEnvironmentVariable("DB_PASSWORD");
    if (!string.IsNullOrEmpty(dbPassword))
        config.Database.Password = dbPassword;

    // ... DB_USERNAME, DB_HOST, DB_NAME 同理

    _instance = config;
    ModelConfig.Initialize(config);
}
```

**【语法层】**
- `IConfiguration configuration`：Microsoft.Extensions.Configuration 的核心接口，支持 JSON/环境变量/命令行等多种配置源。
- `configuration.Bind(config)`：**反射绑定**。自动将 `appsettings.json` 的 JSON 键（如 `"Llm:ModelId"`）映射到 `AppConfig.Llm.ModelId` 属性上。这是 .NET Options 模式的核心。
- `Environment.GetEnvironmentVariable("DB_PASSWORD")`：读取操作系统环境变量。

**【功能层】**
- 第一步：从 `appsettings.json` 读取所有配置
- 第二步：用环境变量**选择性覆盖**敏感字段（数据库密码、用户名、主机、数据库名）
- 第三步：设置单例，同时初始化 `ModelConfig` 静态门面

**【设计意图层】**
- **为什么不在 appsettings.json 中直接写密码？** 安全要求。`appsettings.json` 会被提交到 Git，而环境变量是运行时注入的。这遵循了 **12-Factor App** 的"配置与代码分离"原则。
- **为什么先 Bind 再覆盖，而不是逐字段读取？** `Bind()` 一次性映射所有字段，代码量极小。对于 100+ 个配置字段，手动读取会极其冗长。环境变量覆盖只在少数敏感字段上进行。
- **`ModelConfig.Initialize(config)` 的作用？** 代理模式。让 `ModelConfig` 成为一个"快捷门面"，外部代码不需要写 `AppConfig.Instance.Llm.ModelId`，可以直接写 `ModelConfig.ModelId`。

**段 3：Validate 校验方法（第 77-111 行）**

```csharp
public List<string> Validate()
{
    var errors = new List<string>();
    if (string.IsNullOrWhiteSpace(Llm.ModelId))
        errors.Add("Llm.ModelId 未配置（模型名称不能为空）");
    if (!Llm.Endpoint.StartsWith("http", StringComparison.OrdinalIgnoreCase))
        errors.Add($"Llm.Endpoint 格式异常: {Llm.Endpoint}");
    // ...
    return errors;
}
```

**【语法层】**
- `string.IsNullOrWhiteSpace()`：比 `IsNullOrEmpty` 更严格，连纯空格也拒绝。
- `StringComparison.OrdinalIgnoreCase`：不区分大小写的字符串比较，Culture-invariant。
- 返回 `List<string>` 而非抛出异常：**错误收集模式**，让调用方一次性展示所有配置问题，而不是"修复一个→重新启动→发现下一个"。

**【功能层】**
- 启动时一次性检查所有关键配置项的有效性
- 返回错误列表，空列表表示全部通过

**【设计意图层】**
- **为什么用返回列表而不是抛异常？** "一次性报告所有错误"优于"逐个失败"。如果用户忘了配 3 个字段，抛异常只会报告第一个，用户修复后重启才能看到第二个。返回列表一次性展示全部，大幅提升开发体验。
- **为什么在 `Program.Main()` 最早期调用？** 这是 fail-fast 策略的延续。配置问题应该在进程启动的 0.1 秒内暴露，而不是等到第一个化工合规请求进来时才崩溃。

```csharp
    public double Bm25Weight { get; set; } = 0.4;
    public double VectorWeight { get; set; } = 0.6;

    // GPU 配置
    public bool GpuEmbeddingEnabled { get; set; } = true;
    public bool GpuSearchEnabled { get; set; } = true;
    public bool RerankerEnabled { get; set; } = true;
    public bool GpuFallbackEnabled { get; set; } = true;

    public string RerankerEndpoint { get; set; } = "http://localhost:8082/rerank";
    public int RerankerCandidateTopK { get; set; } = 20;
    public int RerankerFinalTopK { get; set; } = 5;
```

**【语法层】**
- `bool GpuFallbackEnabled { get; set; } = true`：自动属性 + 默认值，C# 6.0+ 特性。
- `double Bm25Weight = 0.4` + `double VectorWeight = 0.6`：BM25 和向量的加权比例，和为 1.0。

**【功能层】**
- 控制 RAG 系统的每个环节是否启用 GPU 加速

- **`RerankerCandidateTopK = 20` 的含义？** 混合检索（BM25 + Vector）先召回 20 条候选，然后用 Cross-Encoder Reranker 精选 top 5。这是一个常见的 **粗排→精排** 的二阶段检索策略。

## 1.2 ModelConfig.cs — 配置门面（55 行）

```csharp
public static class ModelConfig
{
    private static AppConfig? _config;

    public static void Initialize(AppConfig config)
    {
        _config = config ?? throw new ArgumentNullException(nameof(config));
    }

    private static AppConfig Config => _config
        ?? throw new InvalidOperationException("ModelConfig 尚未初始化");

    public static string ModelId => Config.Llm.ModelId;
    public static Uri Endpoint => new Uri(Config.Llm.Endpoint);
    public static string FunctionCallingModelId =>
        string.IsNullOrEmpty(Config.Llm.FunctionCallingModelId)
            ? Config.Llm.ModelId
            : Config.Llm.FunctionCallingModelId;
}
```

**【语法层】**
- `static class`：不可实例化的静态类，所有成员都是 static
- `?? throw new`：null 合并 + throw 表达式，C# 7.0 特性。等价于 `if (_config == null) throw ...`
- `=>` 表达式体属性：C# 6.0+ 语法糖，等价于 `get { return ... }`
- `??` 操作符在 `FunctionCallingModelId` 中：null 合并，左边为空字符串时取右边

**【功能层】**
- 提供 `AppConfig` 的简化访问接口
- `ModelConfig.ModelId` 替代 `AppConfig.Instance.Llm.ModelId`
- `ModelConfig.Endpoint` 自动将字符串转为 `Uri` 对象
- `FunctionCallingModelId` 带有回退逻辑：未配置时使用主模型

**【设计意图层】**
- **为什么需要一个"门面"类？** 这是 **Facade 模式**。原始设计可能直接在代码中写 `AppConfig.Instance.Llm.ModelId`，但这样暴露了配置的内部结构。`ModelConfig` 作为门面：
  1. 提供更简洁的 API（`ModelConfig.ModelId` vs `AppConfig.Instance.Llm.ModelId`）
  2. 隔离变更：如果将来配置结构重组，只需要改 `ModelConfig` 内部映射，不需要改 50+ 处调用点
  3. 类型转换：`Endpoint` 自动转为 `Uri`，避免每次调用时 `new Uri(...)`
- **`FunctionCallingModelId` 的回退逻辑？** 这是一个"预留扩展点"。当前 FC 模型和主模型是同一个，但未来可以通过配置将 FC 工具规划任务分配给更小更快的模型，将合规结论生成分配给大模型——这是 **模型路由** 的雏形。

  - 大小写兜底：如果有人用 `evalSet.name` 也能正常工作

## 2.1 SessionService.cs — 会话管理的适配器模式（40 行）


**【设计意图层】**

  2. 如果将来要改用 Redis 分布式会话，需要修改所有调用点

  1. 测试时注入 `Mock<ISessionService>`
  2. 更换实现只需修改 DI 注册：`services.AddSingleton<ISessionService, RedisSessionService>()`
- **这是典型的 Adapter 模式**，将不灵活的静态类适配为可注入的接口

### 2.2.1 会话隔离机制（第 18-49 行）

```csharp
private readonly ConcurrentDictionary<string, SessionMemoryData> _sessions = new();
private string _currentSessionId = "__default__";

public void SetSession(string sessionId)
{
    _currentSessionId = string.IsNullOrWhiteSpace(sessionId) ? "__default__" : sessionId;
    _sessions.GetOrAdd(_currentSessionId, _ => new SessionMemoryData());
}
private SessionMemoryData Current =>
    _sessions.GetOrAdd(_currentSessionId, _ => new SessionMemoryData());
```

**【语法层】**
- `ConcurrentDictionary<string, SessionMemoryData>`：线程安全的字典，支持多线程并发读写
- `GetOrAdd(key, factory)`：如果键不存在则创建，原子操作——不会出现两个线程同时创建同一个会话的数据

**【功能层】**
- 每个 `sessionId` 对应一个独立的 `SessionMemoryData`（包含用户画像、事实缓存、对话记录、压缩摘要）
- `SetSession()` 切换当前会话，`Current` 属性获取当前会话的数据

**【设计意图层】**
- **为什么需要会话隔离？** `MemoryService` 是单例（整个进程生命周期只有一个实例）。如果不隔离，用户 A 的对话历史会泄漏给用户 B。`ConcurrentDictionary + sessionId` 确保每个会话的数据完全隔离。
- **为什么用 `ConcurrentDictionary` 而不是 `Dictionary + lock`？** 在 ASP.NET Core 多线程环境下，多个请求可能同时访问不同会话。`ConcurrentDictionary` 内部使用细粒度锁（per-bucket lock），并发性能远优于全局 lock。
- **`GetOrAdd` 的 `_ => new()` 是什么？** Lambda 表达式。只有在键不存在时才执行，避免不必要的对象创建。这是 **Lazy Initialization** 模式。


- `turnsToCompress.Skip(...).Take(...)`：LINQ 分页操作

**【功能层】**
- 每当未压缩对话达到 10 轮时，调用 LLM 将旧对话（保留最近 5 轮）压缩为 300 字的结构化摘要

- **为什么离线压缩而不是在线截断？** 截断（直接删旧对话）会丢失领域知识；压缩（LLM 摘要）保留了关键信息（化学品名、法规编号、合规结论），信息损失最小化。
- **无 LLM 时的降级策略（第 356-379 行）**：用正则提取 GB 编号作为"压缩摘要"——虽然信息量低，但至少保留了最关键的法律引用。

## 2.3 MetricsCollector.cs — 无锁原子计数的可观测性（152 行）

```csharp
public static class MetricsCollector
{
    private static long _llmCallCount;
    private static long _llmTotalDurationMs;
    private static long _llmErrorCount;

    public static void RecordLlmCall(long durationMs, bool success, int retries = 0)
    {
        Interlocked.Increment(ref _llmCallCount);
        Interlocked.Add(ref _llmTotalDurationMs, durationMs);
        if (!success) Interlocked.Increment(ref _llmErrorCount);
    }
}
```

**【语法层】**
- `Interlocked.Increment(ref _llmCallCount)`：**CPU 级别的原子操作**。不经过 CLR 锁，直接在 CPU 总线上通过 `LOCK CMPXCHG` 指令实现。
- `static class` + `static long`：进程全局计数器

**【功能层】**
- 记录 LLM 调用次数、总耗时、错误数、重试次数
- 记录 RAG 检索次数、耗时、缓存命中数
- 记录 API 请求次数和错误数
- 支持慢请求告警（>60 秒）
- 提供 Prometheus 格式的输出

**【设计意图层】**
- **为什么用 `Interlocked` 而不是 `lock`？** 性能考量。`Interlocked` 是无锁的——它利用 CPU 的原子指令（CMPXCHG），不需要进入内核态的锁竞争。在高并发 ASP.NET Core 环境下，`lock` 会导致线程阻塞和上下文切换开销，而 `Interlocked` 几乎没有开销。
- **为什么用 `static class` 而不是 DI 单例？** 指标收集器需要极低的调用开销。如果通过 DI 接口调用，每次记录指标都经过虚方法分派。静态方法调用是最快的——直接跳转到方法地址。对于每秒可能被调用数百次的指标记录，这个优化是有意义的。
- **`GetSnapshot()` 为什么一次性读取所有计数器？** Bug#P2-14 修复。如果分多次 `Interlocked.Read`，在两次读取之间计数器可能被其他线程修改，导致快照不一致。一次性读取保证了"瞬时一致性"。

## 2.4 ModuleDispatcher + ModuleFactory — 策略模式 + 懒加载（121 行）

```csharp
// ModuleDispatcher.cs
public async Task ExecuteModuleAsync(ModuleType type)
{
    if (!_modules.TryGetValue(type, out var module))
    {
        module = _factory.CreateModule(type);  // 懒创建
        _modules[type] = module;               // 缓存
    }
    await module.RunAsync();
}

// ModuleFactory.cs
public IInferenceModule CreateModule(ModuleType type)
{
    return type switch
    {
        ModuleType.CoTSolid => new CoTSolidModule(_llmService, _sessionService, ...),
        ModuleType.CoTStream => new CoTStreamModule(_llmService, _sessionService, ...),
        // ...
        ModuleType.ComplianceCheck => new ComplianceCheckModule(
            _knowledgeBaseService, _llmService, _integrationService, _auditService),
        _ => throw new ArgumentOutOfRangeException(nameof(type))
    };
}
```

**【语法层】**
- `type switch { ... }`：C# 8.0 switch 表达式，比传统 `switch` 语句更简洁
- `_modules.TryGetValue(type, out var module)`：`out var` 声明，C# 7.0 inline 变量声明
- `_ => throw ...`：弃元模式，匹配所有未列出的枚举值

**【功能层】**
- **Dispatcher**：管理模块的懒加载 + 缓存 + 执行
- **Factory**：根据 `ModuleType` 枚举创建对应的模块实例，注入所需依赖

**【设计意图层】**
- **Dispatcher 为什么用 Dictionary 缓存模块？** 避免每次执行都重新创建模块。模块的构造函数需要注入多个服务，创建开销不小。缓存后，同一类型的模块只创建一次。
- **为什么需要 Factory？** 这是**工厂方法模式 + 策略模式**的组合。每个 `ModuleType` 对应一种 AI 推理策略（CoT/ReAct/Reflection/RAG），它们都实现 `IInferenceModule` 接口。Factory 解耦了"策略选择"和"策略创建"。
- **为什么某些模块传入 `_knowledgeBaseService` 而另一些不传？** 不同模块的依赖不同：CoT/Reflection 需要知识库来检索法规；ReAct 只需要 LLM 做推理；UnifiedDialog 只需要编排能力。Factory 在创建时精确控制依赖注入。
- **`switch` 表达式中的 `_ => throw`**：防御性编程。如果将来新增了 `ModuleType` 枚举值但忘记在 Factory 中添加，编译不会报错（switch 表达式需要穷举，但 `_` 弃元"欺骗"了编译器）。这里的 `throw` 确保运行时能立即发现遗漏。

## 3.1 构造函数 + SK Kernel 初始化（第 46-74 行）

```csharp
public LlmService(IKnowledgeBaseService kbService)
{
    _complianceTools = new ChemicalComplianceTools(kbService);

    var thinkingHandler = new OllamaThinkingHandler(this);

    var kernelBuilder = Kernel.CreateBuilder();
    kernelBuilder.AddOpenAIChatCompletion(ModelConfig.ModelId, ModelConfig.Endpoint, "not-needed");
    kernelBuilder.Plugins.AddFromObject(_complianceTools, "ChemicalCompliance");
    _kernel = kernelBuilder.Build();

    InjectThinkingHandler(_kernel, thinkingHandler);

    _httpClient = new HttpClient(new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(5),
        MaxConnectionsPerServer = AppConfig.Instance.VectorSearch.MaxConcurrentEmbeddings,
        EnableMultipleHttp2Connections = true
    })
    {
        Timeout = TimeSpan.FromSeconds(AppConfig.Instance.VectorSearch.EmbeddingTimeoutSeconds)
    };

    _kernel.FunctionInvocationFilters.Add(new FunctionCallDiagnosticsFilter(this));
}
```

**【语法层】**
- `Kernel.CreateBuilder()`：Semantic Kernel 的 Builder 模式，类似于 ASP.NET Core 的 `WebApplication.CreateBuilder()`
- `AddOpenAIChatCompletion(modelId, endpoint, "not-needed")`：使用 OpenAI 兼容协议连接到 Ollama（Ollama 的 `/v1/chat/completions` 端点兼容 OpenAI 格式）。第三个参数 `"not-needed"` 是 API Key——Ollama 不需要，但 SK 的 OpenAI 连接器强制要求此参数。
- `Plugins.AddFromObject(_complianceTools, "ChemicalCompliance")`：将 `ChemicalComplianceTools` 实例中的 `[KernelFunction]` 方法注册为 SK 插件，插件名为 `"ChemicalCompliance"`
- `FunctionInvocationFilters.Add(...)`：添加函数调用拦截器
- `SocketsHttpHandler`：底层 HTTP 连接的配置对象
- `PooledConnectionLifetime = TimeSpan.FromMinutes(5)`：HTTP 连接池中每个连接的最大存活时间

**【功能层】**
1. 创建 `ChemicalComplianceTools` 实例（7 个工具函数）
2. 创建 `OllamaThinkingHandler`（HTTP 拦截器）
3. 构建 SK Kernel，注册 OpenAI 兼容的 Ollama 连接 + 化工合规插件
4. 通过反射注入 OllamaThinkingHandler 到 SK 内部 HttpClient
5. 创建独立的 `_httpClient`（用于向量嵌入 API 调用，不走 SK）
6. 注册 `FunctionCallDiagnosticsFilter`（用于记录每次工具调用）

**【设计意图层】**
- **为什么用 OpenAI 连接器而不是 Ollama 连接器？** 这是一个历史演变的结果。早期使用 `AddOllamaChatCompletion`，但发现它不支持 Function Calling。切换到 `AddOpenAIChatCompletion` 后，SK 会自动启用 OpenAI 风格的 Function Calling（通过 `tool_calls` 字段），而 Ollama 恰好兼容这个协议。
- **第三个参数 `"not-needed"` 的设计意图？** SK 的 OpenAI 连接器强制要求 API Key。Ollama 不需要认证，但 API 不接受空字符串。`"not-needed"` 作为一个占位符满足 SK 的校验，实际上是"无用但必要"的参数。
- **`InjectThinkingHandler` 为什么要用反射？** SK 不暴露内部 HttpClient 的配置接口。要控制 Ollama 的 `think` 参数（控制 Qwen3 的思考模式），必须在 HTTP 请求发送前拦截和修改 JSON body。反射是唯一的方法。
- **两个 HttpClient 的设计意图？** `_kernel` 内部的 HttpClient（通过 OllamaThinkingHandler）用于 LLM 推理，`_httpClient` 用于向量嵌入。两者需要不同的超时和连接池配置。LLM 推理可能耗时 5-6 分钟，嵌入通常 30 秒内完成。分离后可以独立调优。
- **`PooledConnectionLifetime = 5 min` 的考量？** 避免长时间运行的连接因网络设备（防火墙/NAT）超时而被断开。定期回收连接确保连接池中的连接始终有效。

- **为什么 `Temperature = 0.3`？** 化工合规需要确定性。高 Temperature（如 1.0）会产生随机性输出，可能导致同一问题两次回答不一致。0.3 是"低随机性但不完全确定性"的平衡——保留少量创意用于自然语言组织，但核心事实受工具调用约束。
- **buffer flush (50 字符) 的设计意图？** 每次 `Console.Write()` 都有 I/O 开销。如果每个 token（平均 2-4 字符）都单独写，每秒数百次 I/O 调用会显著拖慢显示。累积到 50 字符后一次性输出，兼顾"实时反馈感"和"性能"。
- **`await Task.Delay(10)` 在第 176 行的意义？** 这是一个微妙的调度让步。在紧密的 `await foreach` 循环中，每个 chunk 到达后立即处理下一个，可能让 UI 线程没有机会刷新。10ms 的延迟让控制台有时间渲染输出，用户可以看到平滑的流式效果。

### 3.2.1 think 标签过滤算法（第 120-162 行）

这是整个 LlmService 中最精妙的字符串处理逻辑：

```csharp
while (true)
{
    int thinkEnd = buffer.IndexOf("</think>");
    if (thinkEnd >= 0)
    {
        if (isInThinkBlock)
        {
            buffer = buffer.Substring(thinkEnd + "</think>".Length);
            isInThinkBlock = false;
        }
        else
        {
            string before = buffer.Substring(0, thinkEnd);
            string after = buffer.Substring(thinkEnd + "</think>".Length);
            buffer = before + after;
        }
        continue;
    }

    int thinkStart = buffer.IndexOf("<think>");
    if (thinkStart >= 0)
    {
        string beforeThink = buffer.Substring(0, thinkStart);
        if (!string.IsNullOrWhiteSpace(beforeThink))
        {
            // 输出 think 之前的有效内容
            result.Append(beforeThink);
            Console.Write(beforeThink);
        }
        isInThinkBlock = true;
        buffer = buffer.Substring(thinkStart + "<think>".Length);
        continue;
    }
    break;
}
```

**【语法层】**
- `while (true)` + `continue` + `break`：无界循环，通过 `continue` 回到开头重新检查，通过 `break` 退出
- `buffer.IndexOf("</think>")`：字符串搜索，返回首次出现的索引，-1 表示未找到
- `buffer.Substring(start, length)`：子串提取

**【功能层】**
这个算法的核心任务是：**在流式接收 token 的过程中，实时剥离 `<think>...</think>` 标签内的内容**。由于 token 是流式到达的，`<think>` 标签可能跨越多个 chunk。

处理逻辑：
1. 先查找 `</think>` 结束标签
   - 如果当前在思考块内 → 丢弃思考内容，标记退出
   - 如果当前不在思考块 → 移除结束标签（异常情况处理）
2. 再查找 `<think>` 开始标签
   - 提取并输出标签前的有效内容
   - 标记进入思考块，丢弃后续内容
3. 两个标签都不存在 → 当前不在思考块 → 正常输出

**【设计意图层】**
- **为什么需要流式过滤？** DeepSeek-R1 和 Qwen3 在启用 thinking 模式时，会在输出中嵌入 `<think>...</think>` 标签包裹推理过程。这些内容对终端用户无意义（如"让我分析一下这个化学品的性质...先查国家标准..."），且消耗大量 token。流式过滤确保用户只看到最终答案。
- **为什么不用正则？** 流式场景中，`<think>` 标签可能被拆分到多个 chunk 中（如 `<th` + `ink>`）。正则无法处理跨 chunk 的匹配。基于状态机的手动解析更灵活。
- **`while(true)` 循环的设计意图？** 一个 chunk 中可能同时包含 `</think>` 结束一个思考块和 `<think>` 开始下一个思考块。`while(true)` + `continue` 确保处理完所有可能的标签。

## 3.3 熔断器（Circuit Breaker）（第 501-549 行）

```csharp
private void CheckCircuitBreaker()
{
    lock (_circuitLock)
    {
        if (_consecutiveFailures >= MaxConsecutiveFailures && _circuitOpenTime.HasValue)
        {
            var elapsed = DateTime.UtcNow - _circuitOpenTime.Value;
            if (elapsed < CircuitBreakDuration)
            {
                throw new CircuitBreakerOpenException(...);  // ← 快速拒绝
            }
            _consecutiveFailures = 0;    // 半开状态
            _circuitOpenTime = null;
        }
    }

```

**【语法层】**
- `lock (_circuitLock)`：Monitor 同步锁，确保检查和状态修改是原子操作
- `throw new CircuitBreakerOpenException`：自定义异常类型，由 `GlobalExceptionMiddleware` 映射为 HTTP 503

**【功能层】**
- **关闭状态**：正常调用 LLM
- **打开状态**：连续 3 次失败后，拒绝所有请求 30 秒（抛出异常）
- **半开状态**：30 秒冷却后，允许下一次试探调用。如果成功→关闭；如果失败→重新打开

**【设计意图层】**
- **为什么需要熔断器？** LLM 服务（Ollama/llama.cpp）可能因 GPU OOM、驱动崩溃、模型加载失败等原因宕机。如果不加熔断，每个请求都会尝试连接、等待超时（2 分钟）、然后失败——整个系统会被拖垮。熔断器在检测到连续失败后立即拒绝请求，保护系统资源。
- **30 秒冷却期的设计依据？** 这是经验值。太短（如 5 秒）可能服务还没恢复；太长（如 300 秒）则影响可用性。30 秒是 GPU 服务重启 + 模型重新加载的典型时间。
- **为什么用 `lock` 而不是 `Interlocked`？** 熔断器状态检查是多步骤操作（读 `_consecutiveFailures` + 读 `_circuitOpenTime` + 比较时间 + 修改状态），需要原子性保证。`Interlocked` 只能保证单变量操作的原子性，无法保证多步骤事务。

## 3.4 OllamaThinkingHandler — HTTP 请求拦截（第 927-962 行）

```csharp
private class OllamaThinkingHandler : DelegatingHandler
{
    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken cancellationToken)
    {
        if (request.RequestUri.AbsolutePath.Contains("/api/chat")
            && request.Method == HttpMethod.Post)
        {
            var body = await request.Content.ReadAsStringAsync();

            if (_owner.EnableThinking && !body.Contains("\"think\""))
            {
                // 在 JSON body 末尾注入 "think":true
                var newBody = body.TrimEnd().Substring(0, body.Length - 1)
                    + ",\"think\":true}";
                request.Content = new StringContent(newBody, Encoding.UTF8, "application/json");
            }
        }
        return await base.SendAsync(request, cancellationToken);
    }
}
```

**【语法层】**
- `DelegatingHandler`：ASP.NET Core HTTP 消息处理管道中的装饰器模式基类。继承它意味着可以拦截和修改 HTTP 请求/响应
- `request.Content.ReadAsStringAsync()`：读取请求 body
- `body.TrimEnd().Substring(0, body.Length - 1)`：去掉最后一个 `}`，然后追加 `"think":true}`

**【功能层】**
- 拦截所有发往 Ollama `/api/chat` 的 POST 请求
- 如果 `EnableThinking = true` 且 body 中尚未包含 `think` 参数，则在 JSON body 末尾追加 `"think":true`
- Qwen3 默认启用思考模式。不注入 `think:false` 时，Qwen3 根据 tools 参数自动选择 non-thinking（更快）

**【设计意图层】**
- **为什么用 `DelegatingHandler`？** 这是 ASP.NET Core 的标准 HTTP 拦截模式。它位于 HTTP 管道中，可以透明地修改请求和响应。比直接修改 SK 源码更加优雅和非侵入。
- **为什么不在 body 开头插入？** JSON 对象的最后一个 `}` 是固定的位置标记。在末尾 `}` 前追加逗号+新字段是最简单、最不易出错的 JSON 修改方式。
- **为什么 Qwen3 不显式注入 `think:false`？** 注释中解释了：Qwen3 在检测到 `tools` 字段存在时，自动进入 non-thinking 模式。显式注入 `think:false` 可能干扰这个自动判断。只在需要显式思考时才注入 `think:true`。

- **为什么同时过滤非化工插件？** SK 内部也有自己的函数调用（如自动重试、错误处理）。这些内部调用不应出现在评测报告中。`pluginName.Equals("ChemicalCompliance")` 确保只记录业务工具。
- **`await next(context)` 之后才记录结果？** 这是 AOP 的 "After Advice"。`await next(context)` 执行实际的工具函数调用，返回后 `context.Result` 包含了工具的执行结果。在调用前只记录了函数名和参数，调用后才补充成功状态和结果。

## 4.1 整体架构：三级降级策略

## 4.2 ConcurrentDictionary 缓存 + LRU 淘汰（第 50-104 行）

```csharp

private async Task<List<RetrievedChunk>> GetCachedOrRetrieveAsync(

    if (RagCache.Count >= RagCacheMaxEntries)
    {
        var staleKeys = RagCache.Where(kvp => kvp.Value.expiresAt <= now)
            .Select(kvp => kvp.Key).ToList();
        foreach (var key in staleKeys)
            RagCache.TryRemove(key, out _);

        // 仍然满则暴力淘汰一半
        if (RagCache.Count >= RagCacheMaxEntries)
        {
            var allKeys = RagCache.Keys.Take(RagCache.Count / 2).ToList();
            foreach (var key in allKeys)
                RagCache.TryRemove(key, out _);
        }
    }

    RagCache[cacheKey] = (chunks, DateTime.UtcNow.Add(RagCacheTtl));
    return chunks;
}
```

**【语法层】**
- `ConcurrentDictionary<string, (List<RetrievedChunk> chunks, DateTime expiresAt)>`：值类型是 C# 7.0 的 ValueTuple
- `TryGetValue(cacheKey, out var cached)`：ConcurrentDictionary 的原子读操作
- `TryRemove(key, out _)`：原子删除，`_` 是弃元（discard）
- `.Where(kvp => kvp.Value.expiresAt <= now)`：LINQ 过滤过期的缓存条目
- `RagCache[cacheKey] = ...`：索引器赋值，对于 ConcurrentDictionary 等价于 `AddOrUpdate`

**【功能层】**
1. 检查缓存 → 命中且未过期 → 直接返回
2. 命中但过期 → 删除 → 重新检索
3. 检索完成后 → 写入缓存（5 分钟 TTL）
4. 缓存满（>=200）→ 先删过期条目 → 仍满则暴力删一半
5. 支持 Reranker：Reranker 可用时召回更多候选 → 精排 → 缓存

**【设计意图层】**
- **为什么缓存键包含 `|{regulationType}|{topK}`？** "苯 危险类别 国标 topK=3" 和 "苯 危险类别 园区规则 topK=5" 是不同的检索请求，需要分别缓存。键的粒度由这三个维度决定。
- **为什么 TTL = 5 分钟？** 知识库是静态的（国标法规不会频繁变动）。5 分钟缓存意味着同一化学品在 5 分钟内的多次查询只检索一次，大幅减少 GPU 嵌入计算和 PostgreSQL 查询负载。
- **为什么 `static` 缓存？** 这意味着**所有 ChemicalComplianceTools 实例共享同一个缓存**。即使多个会话并发查询，缓存跨会话生效。
- **为什么缓存满时先删过期再暴力删一半？** 两步淘汰策略：第一步清理无效条目（优雅）；第二步在仍然满时暴力处理（必要）。"删一半"是经典的 LRU 近似——不需要精确追踪访问时间，随机删除就能保证平均的公平性。
- **为什么用 `Take(RagCache.Count / 2)` 而不是逐个 LRU？** 精确 LRU 需要维护双向链表 + 每次访问更新位置，在大规模并发下有锁竞争开销。随机淘汰是 **近似 LRU**，性能卓越且效果接近。
- **`RerankerCandidateTopK` 的设计意图？** 粗排召回 20 条（比最终需要的 3 或 5 条多很多），送给 Reranker 精选。这遵循了 **粗排 → 精排** 的两阶段检索策略：粗排追求召回率（宁可多召回），精排追求精确率（Cross-Encoder 精准打分）。

## 4.4 正则提取 — ExtractDistanceFromText（第 326-383 行）

```csharp
private static (double? distance, string unit, string source) ExtractDistancePatterns(string text)
{
    var patterns = new[]
    {
        @"(不小于|不应小于|不得小于|≥|>=\s*)\s*(\d+(?:\.\d+)?)\s*(米|m)",
        @"(最小.*?(?:安全|防火)?间距.*?为)\s*(\d+(?:\.\d+)?)\s*(米|m)",
        @"(安全距离.*?)\s*(\d+(?:\.\d+)?)\s*(米|m)",
        @"(间距).*?(\d+(?:\.\d+)?)\s*(米|m)",
        @"(\d+(?:\.\d+)?)\s*(米|m)",  // 最后兜底：任何 "数字 米/m"
    };
}
```

**【语法层】**
- `@""`：逐字字符串（verbatim string），不转义反斜杠
- `(?:\d+(?:\.\d+)?)`：非捕获组中的可选小数部分
- `(米|m)`：捕获"米"或"m"
- 5 个正则按优先级排列：更具体的模式排在前面

**【功能层】**
1. 尝试上下文匹配（定位 facilityType 关键词附近的距离）
2. 按 5 个正则模式依次尝试
3. 找到后从匹配项中提取数字 → `double.TryParse`
4. 返回 `(距离, "米", 上下文文本)`

**【设计意图层】**
- **为什么 5 个正则按此顺序排列？** 正则匹配是短路算法——找到第一个匹配就返回。越具体的模式越靠前，避免泛化模式误匹配。最后的 `(\d+(?:\.\d+)?)\s*(米|m)` 是兜底——匹配文档中任何"数字+米"的组合。
- **上下文提取（`contextHint`）的设计？** `ExtractDistanceFromText` 先尝试在 facilityType 关键词附近（前 50 字符，后 350 字符）搜索距离。这是因为 RAG 检索可能返回整篇 GB50160，包含多个不同场景的安全距离。上下文定位确保提取的是用户关心的那个场景的距离。

## 4.5 GB 编号提取（第 591-598 行）

```csharp
private static void ExtractRegulationRefs(string text, HashSet<string> resultSet)
{
    var matches = Regex.Matches(text, @"GB\s*/?T?\s*\d{4,5}[.\-]\d{2,4}(?:\s*-\s*\d{4})?");
    foreach (Match m in matches)
    {
        var normalized = Regex.Replace(m.Value, @"\s+", " ").Trim();
        resultSet.Add(normalized);
    }
}
```

**【语法层】**
- `GB\s*/?T?\s*\d{4,5}[.\-]\d{2,4}(?:\s*-\s*\d{4})?`：
  - `GB` → 字面匹配
  - `\s*/?T?` → 可选的空格+斜杠+推荐性标识
  - `\d{4,5}` → 4-5 位标准编号
  - `[.\-]\d{2,4}` → 点或短横线 + 2-4 位年份
  - `(?:\s*-\s*\d{4})?` → 可选的修订年份
- `HashSet<string>`：自动去重

**【功能层】**
- 从 RAG 检索结果中提取所有 GB 编号（如 "GB 30000.2-2013"、"GB/T 50160-2008"）
- 标准化：将多余空格压缩为单个空格
- 去重：HashSet 自动过滤重复编号

**【设计意图层】**
- **为什么提取 GB 编号？** 评测系统需要验证"LLM 引用的法规编号是否真实存在于知识库"。如果 LLM 回答中出现了 `GB 99999.1-2099`（不存在的编号），这就是幻觉。
- **HashSet 的设计意义？** 一篇文档可能多次提到同一个 GB 编号。HashSet 确保 `[REGULATIONS: GB 15603, GB 50160]` 中不会出现重复。

## 4.6 降级方法 — Fallback 策略

```csharp
private string CheckHazardCategoryFallback(string substanceName)
{
    // 1. 先查结构化数据库
    var sub = ChemicalSubstanceDatabase.Lookup(substanceName);
    if (sub != null && sub.HazardCategories.Count > 0)
        return $"[REGULATIONS: {string.Join(", ", gbNums)}]\n...";

    // 2. 再查硬编码字典
    foreach (var kvp in HazardCategories)
    {
        if (substanceName.Contains(kvp.Key) || kvp.Key.Contains(substanceName))
            return $"[REGULATIONS: {kvp.Value}]\n...";
    }

    // 3. 诚实声明
    return $"「{substanceName}」未在常见危化品类别中直接匹配...";
}
```

**【设计意图层】**
- **降级顺序：ChemicalSubstanceDatabase → HazardCategories 字典 → 诚实声明**。这体现了"最有信息量的降级优先"原则。结构化数据库比硬编码字典覆盖更全，字典比诚实声明更有用。
- **为什么 `substanceName.Contains(kvp.Key)` 同时反向检查？** 用户可能输入"苯的类别"→ 匹配 "急性毒性" 不行。但 `"苯".Contains("苯")` 匹配不上。反向 `kvp.Key.Contains("苯")`（如 "易燃液体" 包含 "液体"→不匹配，但通过正向 `"苯".Contains("苯")` 也不行）。实际上这里是一个双向模糊匹配，覆盖了"输入是完整类别名"和"输入是化学品名"两种情况。

### 5.1.1 核心数据结构（第 71-114 行）


**【语法层】**

- **为什么内层是 `Dictionary<int, int>` 而不是 `List<int>`？** 需要同时存储"哪个文档"和"出现多少次"两个信息。`Dictionary<文档ID, 词频>` 是最自然的表达。

### 5.1.2 BM25 评分公式（第 164-200 行）

```csharp
double idf = Math.Log((_documents.Count - df + 0.5) / (df + 0.5) + 1);
double tfComp = (tf * (K1 + 1)) / (tf + K1 * (1 - B + B * (doc.Length / safeAvgLen)));
score += idf * tfComp;
```

**【语法层】**
- `Math.Log(...)`：自然对数

**【功能层】**
这是 **BM25 Okapi** 公式的标准实现：

\[
\text{score} = \sum_{t \in query} \underbrace{\log\left(\frac{N - df + 0.5}{df + 0.5} + 1\right)}_{\text{IDF}} \times \underbrace{\frac{tf \cdot (k_1 + 1)}{tf + k_1 \cdot \left(1 - b + b \cdot \frac{L}{L_{avg}}\right)}}_{\text{TF 归一化}}
\]

- \(N\) = 总文档数
- \(df\) = 包含该词的文档数（逆文档频率的分母）
- \(tf\) = 该词在当前文档中的出现次数
- \(L\) = 当前文档长度
- \(L_{avg}\) = 平均文档长度
- \(k_1 = 1.5, b = 0.75\)：调节参数

**【设计意图层】**
- **为什么选 K1=1.5, B=0.75？** 这是 BM25 的"标准参数"，经过数十年信息检索研究的验证。K1=1.5 给词频适中的饱和曲线（词出现 5 次和 50 次的得分差异不大），B=0.75 给长度归一化适中的惩罚（长文档不会因为词多而被过度加分）。
- **IDF 公式中 `+0.5` 和 `+1` 的作用？** 平滑处理。当 df=0（词在所有文档中都不出现）时防止分母为 0，同时保证 IDF 始终为正数。
- **`Math.Max(1.0, _avgDocLength)` 的作用？** Bug#P1-5 修复。如果知识库为空（0 文档），`_avgDocLength` 为 0，除法产生 NaN。`Math.Max(1.0, ...)` 防止除零。

```csharp
    for (int rank = 0; rank < bm25Results.Count; rank++)
    {
        var rrfScore = 1.0 / (rrfK + rank + 1);
        rrfScores[key] = (bm25Results[rank], rrfScore);
    }
    for (int rank = 0; rank < vectorResults.Count; rank++)
    {
        var rrfScore = 1.0 / (rrfK + rank + 1);
        // 同文档累加两个排名的 RRF 分
    }
}
```

**【语法层】**
- `Task.WhenAll(bm25Task, vectorTask)`：**真正的并行**——BM25 和 Vector 检索同时执行，不等待彼此
- `1.0 / (rrfK + rank + 1)`：RRF 的核心公式：每个排名贡献一个递减的分数

**【功能层】**
RRF 公式：\(\text{RRF}(d) = \sum_{r \in R} \frac{1}{k + \text{rank}(r, d)}\)

- 排名 1 → 分数 `1/61 ≈ 0.0164`
- 排名 2 → 分数 `1/62 ≈ 0.0161`
- 排名 60 → 分数 `1/120 ≈ 0.0083`
- 同一文档在 BM25 排第 1 且 Vector 排第 5 → 总分 `1/61 + 1/65 ≈ 0.0318`

**【设计意图层】**
- **为什么用 RRF 而不是简单的加权求和？** 这是 Bug#8 的直接教训。BM25 原始分在 0~150 范围，向量余弦相似度在 0~1 范围，量级差 100 倍。直接加权 `0.4*BM25 + 0.6*Vector` 导致 BM25 完全碾压向量。RRF 只使用**排名**而非**原始分**，天然免除了量纲归一化的问题。
- **k=60 的设计依据？** 这是 RRF 论文的标准参数。k 越大，排名靠前和靠后的分数差异越小；k 越小，靠前的优势越大。60 是经验最优值。
- **`Task.WhenAll` 的设计意图？** BM25（CPU 密集）和 Vector（网络 I/O 密集）是完全独立的操作，并行执行可将检索延迟从 `T_BM25 + T_Vector` 缩短为 `max(T_BM25, T_Vector)`，约节省 40% 时间。

## 5.3 GpuVectorIndexService — 内存向量索引

### 5.3.1 启动时全量加载（第 51-120 行）

```csharp
public async Task InitializeAsync()
{
    var allDocs = await _databaseService.GetAllChemicalDocumentsWithEmbeddingsAsync();

    _lock.EnterWriteLock();
    try
    {
        _index.Clear();
        foreach (var doc in allDocs)
        {
            _index[entry.Id] = entry;
            totalBytes += doc.Embedding.Length * sizeof(float) + doc.Content.Length * sizeof(char);
        }
    }
    finally { _lock.ExitWriteLock(); }
}
```

**【语法层】**
- `ReaderWriterLockSlim`：读写锁。允许多个读操作并发（`EnterReadLock`），写操作独占（`EnterWriteLock`）
- `sizeof(float)`：C# 的 `sizeof` 运算符，获取类型的字节大小

**【设计意图层】**
- **为什么全量加载到内存？** PostgreSQL pgvector 的向量检索需要磁盘 I/O，每次 cosine similarity 需要从 B-tree 索引中读取向量数据。内存中的暴力搜索虽然 O(N)，但因为是纯 CPU 操作（无磁盘 I/O），在小规模（<10 万向量）下比 pgvector 快 3-5 倍。
- **为什么用 `ReaderWriterLockSlim`？** 向量检索（Search）是高频读操作，向量更新（Add/Delete）是低频写操作。读写锁允许无限并发读，只在写入时阻塞读。相比 `lock`（读写全部互斥），吞吐量提升数倍。
- **"模拟 GPU FAISS"的含义？** 当前实现是 CPU 暴力搜索。真正的 FAISS（Facebook AI Similarity Search）使用 GPU 加速的近似最近邻（ANN）算法，在百万级向量上也能毫秒级完成。当前内存方案是 FAISS 的"原型替代"——接口一致，生产环境可无缝替换。

## 5.4 知识库层的多重缓存体系

整个知识库层存在**三重缓存**，每一层解决不同的问题：

| 缓存层                            | 位置                            | 生命周期        | 解决的问题              |
| --------------------------------- | ------------------------------- | --------------- | ----------------------- |
| **QueryCacheService** (LRU+TTL)   | `HybridKBService.RetrieveAsync` | 5 分钟 / 500 条 | 同一查询不重复检索      |
| **RagCache** (ConcurrentDict+TTL) | `ChemicalComplianceTools`       | 5 分钟 / 200 条 | 工具调用间共享 RAG 结果 |
| **GpuVectorIndex** (全量内存)     | 独立的 Index Service            | 进程生命周期    | 避免 pgvector 磁盘 I/O  |

查询链路：`用户查询 → QueryCache(命中→返回) → RagCache(命中→返回) → BM25+Vector 实际检索 → QueryCache写入`

**【设计意图层】**
- **为什么需要多重缓存？** 不同粒度的缓存解决不同场景的重复计算。QueryCache 在知识库层，RagCache 在工具层——两者缓存键不同（QueryCache 用原始查询，RagCache 用 `{query}|{regulationType}|{topK}`），覆盖不同粒度的复用。
- **为什么都是 5 分钟 TTL？** 一致性设计。所有缓存使用相同的过期时间，确保在一次用户对话（通常 ≤5 分钟）中缓存有效，跨对话自动过期。

## 6.1 AgentDialog — 6 步线性流水线（第 54-79 行）

```csharp
public async Task<string> ExecuteAsync(string userInput, SessionContext session)
{
    var processedInput = await PreprocessAsync(userInput);         // [1/6] 预处理
    var intent = RouteIntent(processedInput);                      // [2/6] 意图归类
    var context = await LoadContextAsync(session, intent);         // [3/6] 上下文加载
    var result = await ExecuteBusinessAsync(processedInput, context, intent); // [4/6] 业务执行
    await SaveSessionAsync(session, userInput, result);            // [5/6] 会话保存
    var finalOutput = FormatOutput(result);                        // [6/6] 结果输出
    return finalOutput;
}
```

**【设计意图层】**

这是一个经典的 **Pipeline（管道）模式**，每个步骤有明确的输入和输出：

| 步骤          | 输入          | 输出            | 为什么这一步不可跳过               |
| ------------- | ------------- | --------------- | ---------------------------------- |
| 1. 预处理     | 原始用户输入  | 清理后的文本    | 去掉首尾空格，统一编码             |
| 2. 意图归类   | 清理后文本    | IntentType 枚举 | 决定走化工合规还是通用对话路径     |
| 3. 上下文加载 | 会话ID + 意图 | PipelineContext | 加载历史对话 + 用户画像 + 领域事实 |
| 4. 业务执行   | 输入 + 上下文 | LLM 回答        | 核心：调用 LLM + 工具              |
| 5. 会话保存   | 原始 Q + A    | 持久化          | 将问答对写入对话历史               |
| 6. 结果输出   | LLM 原生输出  | 格式化文本      | 清理 think 标签 + 统一格式         |

**为什么是线性的而不是基于事件的？** 化工合规场景的流程是严格顺序的——必须先知道用户意图才能加载正确的上下文，必须先加载上下文才能执行业务。非线性流程（如事件驱动）会引入不必要的复杂性。

### 6.2.2 Layer2：逐条六维评测

每条用例经历 **6 个维度的评估**：


**六个维度的设计意图：**

| 维度        | 评估什么                 | 为什么重要                                |
| ----------- | ------------------------ | ----------------------------------------- |

| 结论准确率  | 合规判断是否正确         | 最终输出——用户最关心的                    |
| Precision@K | 检索结果中相关文档占比   | 是否检索到了噪声                          |
| Recall@K    | 相关文档是否被检索到     | 是否漏掉了关键法规                        |
| 忠实度      | 结论是否基于知识库原文   | 反幻觉——GB 编号是否真的存在               |

## 6.3 ReflectionVerifier — 代码级事实核查（280 行）

这是整个项目中最"硬核"的反幻觉机制：

```csharp
/// <summary>
/// 代码级反思验证引擎 — 不是 LLM，不产生幻觉。
/// 基于正则匹配 + 知识库反向检索，对 LLM 结论进行客观事实核查。
/// </summary>
public class ReflectionVerifier
{
    public async Task<BusinessVerificationReport> VerifyBusinessFactsAsync(string conclusion)
    {
        // 1. 从 LLM 结论中提取所有法规编号（正则）
        foreach (var (pattern, type) in RegulationPatterns)
        {
            foreach (Match match in pattern.Matches(conclusion))

                var chunks = await _kbService.RetrieveChemicalRegulationAsync(
                    normalized, topK: 3);

                // 3. 判断：知识库中是否存在该编号？

            }
        }

        // 4. 计算 FactualPrecision = 已验证声明数 / 总声明数
        report.FactualPrecision = (double)regVerified / regClaims;
    }
}
```

**【设计意图层】**
- **"不是 LLM，不产生幻觉"的含义？** 这是一个革命性的设计决策。传统方法用另一个 LLM 来"验证"第一个 LLM 的输出——但验证者本身也可能幻觉。ReflectionVerifier 用纯代码（正则 + 知识库反向检索）代替 LLM 验证，确保验证过程本身 100% 可靠。

- **`FactualPrecision` 与 Faithfulness 的关系？** FactualPrecision 是 Faithfulness 的核心组成部分。Faithfulness = "LLM 的每条法规声明在知识库中是否真实存在"。如果 LLM 编造了 `GB 99999.1-2099`，ReflectionVerifier 会发现它在知识库中不存在，标记为幻觉。

### 7.2.2 LLM 并发保护 — SemaphoreSlim（第 57 行 + Controller 第 70 行）

```csharp
// 注册：全局一个信号量，最多 2 并发
builder.Services.AddSingleton(new SemaphoreSlim(2, 2));

// Controller 中使用：
if (!await _llmGate.WaitAsync(TimeSpan.FromSeconds(5)))
{
    return StatusCode(503, new { error = "服务繁忙，请稍后重试", retryAfter = 10 });
}
```

**【设计意图层】**
- **为什么限制为 2 并发？** CPU 推理场景下，Qwen3-8B 每个请求消耗约 8GB 内存和大量 CPU。3+ 并发会导致 OOM 或请求全部超时。2 并发是实际测试的安全上限。
- **为什么用 `SemaphoreSlim` 而不是队列？** 信号量是最简单的并发控制原语。`WaitAsync(5秒)` 提供了"等待获取许可"和"超时拒绝"两种行为——如果 5 秒内获取不到许可，直接返回 503。这比无限等待队列更友好（用户可以立即收到"繁忙"响应，而不是无限等待）。
- **503 + `retryAfter`** 的设计意图：HTTP 503 是"服务不可用"的标准状态码，`retryAfter` 告诉客户端 10 秒后重试。这是 RESTful API 的最佳实践。

```csharp
[HttpPost("check")]
[Authorize(Policy = "Auditor")]
public async Task<IActionResult> CheckCompliance([FromBody] ComplianceRequest request)
{
    // 1. 缓存命中 → 直接返回
    var cached = _cache.Get(request.Query);
    if (cached != null)
        return Ok(cached);

    // 2. LLM 并发保护
    if (!await _llmGate.WaitAsync(TimeSpan.FromSeconds(5)))
        return StatusCode(503, ...);

    try
    {
        // 3. 执行合规审核
        var response = await _agentDialog.ExecuteEvalFastAsync(request.Query);

        // 4. 幻觉检测
        var verification = await ConclusionVerifier.VerifyAsync(response, toolCalls, ...);

        // 5. 审计日志
        await _auditService.LogOperationAsync(...);

        // 6. 存入缓存
        _cache.Set(request.Query, ...);

        return Ok(new ComplianceResponse { ... });
    }
    finally { _llmGate.Release(); }
}
```

**【设计意图层】**

请求处理流程的精心设计：

```
Request → 参数校验 → 缓存检查 → 并发控制 → LLM推理 → 幻觉检测 → 审计 → 缓存 → Response
```

- **缓存检查在并发控制之前**：缓存命中不需要占用 LLM 槽位。如果 100 个相同查询并发到达，第一个执行 LLM，其余 99 个直接从缓存返回——不需要信号量。
- **`finally { _llmGate.Release() }`**：确保即使 LLM 推理抛出异常，信号量也能被释放。这是 **RAII（资源获取即初始化）** 在 C# 中的体现。
- **审计日志的设计**：等保三级要求记录所有"敏感操作"。`LogOperationAsync` 记录了查询内容、使用了哪些工具、验证了哪些法规——这是合规审计的证据链。

## 8.2 降级策略全景图

Agent1 拥有整个项目中**最完整的降级体系**，覆盖从 LLM 服务到知识库检索的每个环节：

```
LLM 层面:
  ├── 熔断器: 3次连续失败 → 30秒拒绝所有请求 (Circuit Breaker)
  ├── 重试: 失败后重试 2 次 (指数退避: 2s, 4s)
  └── Thinking 降级: 反射注入失败 → 程序正常启动 (no-op)

RAG 检索层面:
  ├── QueryCache: 缓存命中 → 跳过检索
  ├── RagCache: 工具间共享缓存
  ├── GPU 向量 → pgvector → 空结果
  └── Reranker → 本地启发式 → 直接截断

工具调用层面:
  ├── RAG 检索 → 结构化数据库(ChemicalSubstanceDB) → 硬编码字典 → 诚实声明
  └── 3 级 Fallback 串联

嵌入层面:
  ├── 批量嵌入(32条/批) → 逐条嵌入
  ├── 嵌入超时 → 逐条重试
  └── 嵌入失败(null) → 跳过向量库(BM25 仍写入)
```

**设计哲学**：每个环节都有 Plan B。系统的韧性不依赖于任何单一组件的可用性。这是**生产级系统的核心特征**。
