### R2026-003：Embedding 失败返回随机向量污染 PostgreSQL

| 字段 | 内容 |
|------|------|
| **发现日期** | 2026-05-26 |
| **严重等级** | 🔴 P0 — 向量数据库被随机数据污染，检索质量严重下降 |
| **发现场景** | 审查异常降级路径——每个 try-catch 的 return 值追踪到最终消费方 |
| **影响模块** | `LlmService.cs` GetEmbeddingAsync L264-L269 → `HybridKnowledgeBaseService.cs` |
| **根因** | Ollama embedding API 失败时 catch 返回 768 个随机 float 向量，调用方未检查直接写入 PostgreSQL。向量检索时返回随机排序结果 |
| **修复** | GetEmbeddingAsync 返回 `float[]?`（失败返回 null），调用方检查 null 跳过写库 |
| **教训** | 每个 try-catch 降级分支必须追问："这个降级返回值会被谁消费？会产生什么副作用？" |
| **追问深度** | 3 层（降级代码 → 返回值追踪到持久化层 → 随机数据污染检索质量） |

**思维链路**

| # | 节点类型 | 关键发现 | 决策 | 否决的路径 |
|:---:|------|------|------|------|
| N1 | 现象确认 | catch { return fallback; } 返回随机向量 | 随机值作为"计算结果"使用 → 污染下游 |
| N2 | L1→L2 追问 | 返回值去了哪里？→ HybridKnowledgeBaseService 中 `record.Embedding = embedding` → `AddChemicalDocumentAsync` 写库 | 降级的副作用比失败本身更危险 |
| N3 | 实现决策 | 返回 null + 调用方跳过写库 vs 抛出异常 | 选 null 返回：调用方自主决策，不完全阻断流程 | 抛异常：可能导致整个知识库加载中断 |

### R2026-005：TXT 文件绕过 TextCleaner → SemanticChunker 完整管道

| 字段 | 内容 |
|------|------|
| **发现日期** | 2026-05-26 |
| **严重等级** | 🟡 P1 — TXT 类知识库文档分块质量远低于 PDF/DOCX |
| **发现场景** | 对比不同文件格式的处理路径——PDF 4 步 vs TXT 3 步 |
| **影响模块** | `ChemicalRAG.cs` LoadAndSplitFile / LoadDirectoryAsync |
| **根因** | TXT 文件使用简陋的 `SplitTextIntoChunks`（固定 500 字符按行切分），完全跳过 TextCleaner（封面/目录/噪声过滤）和 SemanticChunker（按条款/章节语义分块） |
| **修复** | TXT 也走同一套 TextCleaner → SemanticChunker 管道，与 PDF/DOC 对齐 |
| **教训** | 两条处理路径的步骤数应该一致——少了哪步就是丢了哪种处理能力 |
| **追问深度** | 2 层（路径步骤数不一致 → 管道对称性缺失） |

**思维链路**

| # | 节点类型 | 关键发现 | 决策 |
|:---:|------|------|------|
| N1 | 现象确认 | PDF 路径：PdfExtractor→TextCleaner→SemanticChunker（4步）；TXT 路径：ReadAllText→SplitBy500（3步） | TXT 缺了清洗和语义分块，分块质量远低于 PDF |
| N2 | L1→L2 追问 | 为什么设计阶段让 TXT 走了不同路径？开发者的假设是"TXT 是纯文本不需要清洗"——但这忽略了 TXT 也可能含噪声（页眉页脚数字编号）和需要语义分块（法规条款） | 假设驱动的设计决策需要显式记录，否则后来者无法判断是刻意的优化还是遗漏 |
| N3 | 实现决策 | TXT 文件也走完整管道（TextCleaner → SemanticChunker） | 步骤对称性修复：不同格式的处理路径应统一到同一管道 |

### R2026-006：向量检索降级返回 BM25 结果被重复融合

| 字段 | 内容 |
|------|------|
| **发现日期** | 2026-05-26 |
| **严重等级** | 🟡 P1 — 同一文档的 BM25 分数被算了两次 |
| **发现场景** | 审查异常降级路径——catch 返回的 BM25 结果在 HybridRetrieveAsync 中又被当作"向量结果"参与加权融合 |
| **影响模块** | `HybridKnowledgeBaseService.cs` VectorRetrieveAsync L213-L227 |
| **根因** | 向量检索失败时降级返回 BM25 结果，融合阶段把这些结果当作"向量结果"（vectorScore）与正常 BM25 结果加权，同一文档分被重复计算 |
| **修复** | 降级时返回空列表，融合代码只用正常 BM25 结果 |
| **教训** | 降级逻辑的副作用往往比失败本身更危险——降级结果被二次使用时尤甚 |
| **追问深度** | 2 层（降级代码 → 返回值在融合阶段的重复消费） |

**思维链路**

| # | 节点类型 | 关键发现 | 决策 | 否决的路径 |
|:---:|------|------|------|------|
| N1 | 现象确认 | VectorRetrieveAsync catch 块返回 BM25 结果 → HybridRetrieveAsync 中作为 vectorScore 参与融合 | 同一 BM25 分被用了两次：一次作为 BM25 得分，一次被当作"向量检索结果" |
| N2 | L1→L2 追问 | 降级逻辑的副作用传播路径：catch → 返回 BM25 结果 → 类型是 `List<ScoredChunk>`（与正常向量返回类型相同）→ 融合代码无法区分来源 | 类型系统不能区分"正常结果"和"降级结果"是根本问题——如果返回类型能区分（如 `Result<T, Degraded<T>>`），融合代码就不会误用 |
| N3 | 横向对比 | R2026-003（随机向量污染）同属于降级副作用族：catch 返回的兜底值被下游当作正常数据处理 | 两条降级副作用 Bug 的共同教训：降级分支的返回值类型绝不能与正常路径相同——否则下游必然误用 |
| N4 | 实现决策 | 降级时返回空列表，融合代码只用正常 BM25 结果 | 降级 ≠ 替代——降级应该是"跳过本路、依赖另一路"而非"用另一路冒充本路" | 方案B：给降级结果打标记——增加复杂度，且融合层仍需改 |

### R2026-008：BM25/向量数量级差 100 倍，加权完全失效

|------|------|
