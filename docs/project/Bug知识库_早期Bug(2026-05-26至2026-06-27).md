### R2026-001：重排序 key 对不上 — Metadata["Priority"] 查不到 priorityLevels

| 字段 | 内容 |
|------|------|
| **发现日期** | 2026-05-26 |
| **严重等级** | 🔴 P0 — 优先级重排序完全失效 |
| **发现场景** | 全项目 RAG 代码静态审查。审查者追踪 `priorityLevels` 字典 key 的来源 |

| **根因** | `priorityLevels` 字典 key 是法规类型（"国标"/"园区规则"/"历史案例"），但代码查的是 `Metadata["Priority"]`（值为 "高"/"中"/"低"）。`ContainsKey("高")` 永远返回 false，所有文档 priority 加分为 0。|

| **教训** | 当两个数据结构的 key 空间不同时，一定是设计阶段的语义不统一。审查时用"数据流追踪法"——顺着字段从写入追到读取 |
| **追问深度** | 3 层（代码现象 → key 语义空间不一致 → 设计阶段缺乏字段值域定义） |

**思维链路**

| # | 节点类型 | 关键发现 | 决策 | 否决的路径 |
|:---:|------|------|------|------|
| N1 | 现象确认 | `priorityLevels = {"国标"→3000, "园区规则"→2000}` 但代码查 `Metadata["Priority"]` | 两个数据结构 key 空间不同 → 必然查不到 |

### R2026-003：Embedding 失败返回随机向量污染 PostgreSQL

| 字段 | 内容 |
|------|------|
| **发现日期** | 2026-05-26 |
| **严重等级** | 🔴 P0 — 向量数据库被随机数据污染，检索质量严重下降 |
| **发现场景** | 审查异常降级路径——每个 try-catch 的 return 值追踪到最终消费方 |
| **影响模块** | `LlmService.cs` GetEmbeddingAsync L264-L269 → `HybridKnowledgeBaseService.cs` |
| **根因** | Ollama embedding API 失败时 catch 返回 768 个随机 float 向量，调用方未检查直接写入 PostgreSQL。向量检索时返回随机排序结果 |
| **修复** | GetEmbeddingAsync 返回 `float[]?`（失败返回 null），调用方检查 null 跳过写库 |
| **教训** | 每个 try-catch 降级分支必须追问："这个降级返回值会被谁消费？会产生什么副作用？" |
| **追问深度** | 3 层（降级代码 → 返回值追踪到持久化层 → 随机数据污染检索质量） |

**思维链路**

| # | 节点类型 | 关键发现 | 决策 | 否决的路径 |
|:---:|------|------|------|------|
| N1 | 现象确认 | catch { return fallback; } 返回随机向量 | 随机值作为"计算结果"使用 → 污染下游 |
| N2 | L1→L2 追问 | 返回值去了哪里？→ HybridKnowledgeBaseService 中 `record.Embedding = embedding` → `AddChemicalDocumentAsync` 写库 | 降级的副作用比失败本身更危险 |
| N3 | 实现决策 | 返回 null + 调用方跳过写库 vs 抛出异常 | 选 null 返回：调用方自主决策，不完全阻断流程 | 抛异常：可能导致整个知识库加载中断 |

### R2026-008：BM25/向量数量级差 100 倍，加权完全失效

| 字段 | 内容 |
|------|------|
| **发现日期** | 2026-05-26 |
| **严重等级** | 🔴 P0 — 混合检索中向量贡献形同虚设 |
| **发现场景** | 审查加权融合公式——两个数的数量级差多少倍？ |
| **影响模块** | `HybridKnowledgeBaseService.cs` HybridRetrieveAsync |
| **根因** | BM25 原始分范围 0~150，向量余弦相似度 0~1，差 100 倍。`bm25Score*0.4 + vectorScore*0.6` 中 BM25 完全碾压向量分（如 50×0.4=20 >> 0.6×0.6=0.36），向量权重 0.6 形同虚设 |
| **修复** | BM25 分先除以本批次最大值归一化到 0~1，使两种分数量纲一致后再加权融合 |
| **教训** | 加权求和的先决条件是量纲一致。审查时问："这两个数要加在一起，数量级差多少倍？" |
| **追问深度** | 4 层（现象 → 量纲不一致数学根因 → 归一化方案对比 → 后续架构演进为 RRF） |

**思维链路**

| # | 节点类型 | 关键发现 | 决策 | 否决的路径 |
|:---:|------|------|------|------|
| N1 | 现象确认 | `0.4*BM25 + 0.6*Vector` 中 BM25 分 0~150、向量分 0~1 | 量纲差 100 倍 → 加权公式无效 |
| N2 | L1→L2 追问 | 为什么没人在测试中发现？因为 RRF 后来替代了加权求和 | 当前代码路径使用加权求和，效果等于纯 BM25 |
| N3 | 方案分支 | Min-Max归一化 vs Z-Score标准化 vs 直接换 RRF | 选 Min-Max：批次内可控，保留分布形状 | Z-Score：小批次不稳定；RRF：后续架构升级任务 |
| N4 | 架构决策 | 后续 Sprint 4 中整体替换为 RRF（k=60）作为更成熟的融合方案 | 当前 Min-Max 为快速修复，后续架构升级 |
